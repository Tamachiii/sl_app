# INVARIANTS.md — Behavioral & Schema Invariants

Load this file when the change touches: routing/scroll-shell, dark mode, RLS, `set_logs` schema, rest timer, messaging/notifications triggers, offline mutations, coach session review, stats persistence, or the role-aware `UserMenu`. Otherwise stay in `CLAUDE.md`.

## Shell, routing, viewport

- **HashRouter intentional** (GitHub Pages). URLs contain `/#/`. Vite `base` is `/sl_app/`. Pages are `React.lazy`-loaded in `routes.jsx`.
- **Bare `/sl_app/` (no hash) redirects to the role home.** iOS PWAs cold-launch at the manifest `start_url` (`/sl_app/`), not at the last-visited hash route, so an authenticated re-launch lands at HashRouter pathname `/`. The `RedirectToRoleHome` index route inside `AppShell` (in [routes.jsx](../src/routes.jsx)) bounces to `/${role}` — without it, the wildcard catches `/` and renders `NotFound`. Unauthenticated users are intercepted earlier by `ProtectedRoute → /login`.
- **Outer page must not scroll.** `html, body, #root` are `overflow: hidden; position: fixed; inset: 0`. `AppShell` is `h-full flex-col` (NOT `h-dvh` — iOS Safari disagrees and spawns a second scrollbar). Only `main` scrolls. Don't touch — this keeps the mobile keyboard from pushing the sticky `BottomNav` mid-page. The inner wrapper inside `main` is `h-full flex flex-col` (not `min-h-full`) so flex-1 + min-h-0 children — currently only Messages thread/composer — get a hard height budget; pages with naturally tall content still scroll via `main` because it has `overflow-y-auto`.
- **iOS Safari auto-zooms focused `<input>` / `<textarea>` / `<select>` < 16px.** Every text-entry form element is 16px. Don't drop below. File pickers, radios, checkboxes, sliders unaffected.
- **Tailwind 4, CSS-based config.** `@theme` + `@custom-variant` in `src/index.css`. No `tailwind.config.js`.
- **Dark mode = class-based CSS remap, not `dark:` utilities.** Extend `src/index.css`. Inline `style={{ color }}` does NOT flip — use classes. `disabled:bg-*` variants also don't pick up `.dark .bg-*` remaps; use `disabled:bg-ink-100`.

## React / hooks discipline

- **Rules of Hooks:** never call `useMemo` (or any hook) after an early return like `if (isLoading) return <Spinner/>`.
- **`useWeek.js` owns `useUpdateWeek` AND `useUpdateSession`** — not `useSession.js`.
- **Test wrapper:** use `renderWithProviders` from `src/test/utils.jsx` (wraps ThemeProvider + QueryClientProvider + AuthContext + MemoryRouter). `matchMedia` polyfill lives in `src/test/setup.js`.

## `set_logs` — per-set targets, outcomes, RPE

- **Per-set targets live on `set_logs`, not `exercise_slots`.** Each set_log row stores both prescription (`target_reps`, `target_duration_seconds`, `target_weight_kg`, `target_rest_seconds`) and student actuals (`done`, `failed`, `rpe`, `weight_kg`). The legacy `exercise_slots.{reps, weight_kg, duration_seconds, rest_seconds}` columns are kept as deprecated mirrors of set 1 — slated for removal in a follow-up migration. `useAddSlot` materializes one set_log per planned set; `useUpdateSlot` fans uniform target edits to all logs; `useUpdateSetTarget` writes to a single log; `useResetSlotToUniform` re-syncs every log to set 1. `isSlotUniform(slot)` and `formatSlotPrescription(slot)` in `lib/volume.js` decide compact vs. per-set rendering.
- **Students log off-plan actuals on `set_logs.actual_reps` / `actual_weight_kg`; the coach-owned `target_*` columns stay immutable to students.** When a student can't follow a set as written, [SetRow.jsx](../src/components/student/SetRow.jsx) exposes an "Actual" pill that opens two inputs prefilled from the prescribed target; [`useLogActual`](../src/hooks/useSetLogs.js) (offline-safe, `MUTATION_KEYS.logActual`) UPDATEs only the `actual_*` columns. The client **normalizes a value equal to its target back to `null`**, so a populated `actual_*` always denotes a genuine deviation — that's the invariant `hasLoggedActual(log)` in [volume.js](../src/lib/volume.js) relies on, and what `formatActual(log)` renders (falling back to the target for the un-overridden dimension). The coach sees these in an "Off-plan" band per slot in [SessionReview.jsx](../src/components/coach/SessionReview.jsx) (no new coach RLS — the existing FOR ALL policy already covers them). The shared-row coach/student column split (coach owns `target_*`, student owns actuals) was previously client-discipline only; it is now **hardened by the `pin_set_log_targets_for_student` BEFORE UPDATE trigger**, which reverts any student attempt to mutate `target_*`. Coach writes resolve a different `auth.uid()` than the slot's student, so `useUpdateSlot` / `useUpdateSetTarget` pass through untouched. `set-logs` is already in `PERSISTED_QUERY_ROOTS`, so the actuals write has offline parity for free.
- **Structural deviations: students can swap/skip an exercise, skip a set, or add an extra set — none of which touch the coach's prescription.** Exercise-level swap/skip live in the `slot_deviations` table (one row per slot, `UNIQUE(exercise_slot_id)`, `kind ∈ {swap,skip}`, `substitute_exercise_id` FK to the coach's library — **library-only, no free-text**, so swaps stay known exercises for stats). RLS clones `slot_comments` (student owns the row, writes gated to the active non-archived program, coach reads); offline via [`useSaveSlotDeviation`](../src/hooks/useSlotDeviations.js) (upsert/delete on the natural key, `'slot-deviations'` is in `PERSISTED_QUERY_ROOTS`). Per-set deviations are two booleans on `set_logs`: `skipped` (intentionally dropped — DB CHECK `set_logs_skipped_not_resolved` keeps it mutually exclusive with done/failed; written by [`useSetSkipped`](../src/hooks/useSetLogs.js), offline) and `is_student_added` (an extra set with NULL targets). **Adding/removing an extra set is ONLINE-ONLY** ([`useAddStudentSet`](../src/hooks/useSetLogs.js)/`useRemoveStudentSet`) — a brand-new-row INSERT can't be safely queued offline (the offline lane only UPDATE/UPSERT/DELETEs existing rows, and two offline adds would collide on `UNIQUE(exercise_slot_id, set_number)`); the UI gates it on `useOnlineStatus`, like `VideoUploadButton`. A new deviation notifies the coach via the `notify_coach_on_slot_deviation` trigger (`kind='session_deviation'`, in-app + best-effort Web Push, AFTER INSERT only so edits don't re-notify). Student UI: [SlotDeviationBar.jsx](../src/components/student/SlotDeviationBar.jsx) (swap/skip) + per-set controls in [SetRow.jsx](../src/components/student/SetRow.jsx); coach UI: deviation banner + skipped/extra pills in [SessionReview.jsx](../src/components/coach/SessionReview.jsx) / [SlotProgress.jsx](../src/components/coach/SlotProgress.jsx).
- **A set_log has three outcome states: pending, done, failed.** `done` and `failed` are mutually exclusive (DB CHECK `set_logs_done_xor_failed`). `useToggleSetDone` and `useSetFailed` each clear the opposite flag in the same patch so a swipe between outcomes never trips the constraint. A failed set may not carry an `rpe` value either (DB CHECK `set_logs_no_rpe_when_failed`); `useSetFailed` nulls `rpe` in the same patch so a student who rated a set then later marked it failed doesn't leave an orphan rating. UI: on mobile, [SetRow.jsx](../src/components/student/SetRow.jsx) commits a swipe right-to-left as done and left-to-right as failed (commit threshold 64px, gated on horizontal-dominant motion so vertical scroll still wins); tapping the indicator cycles `neutral → done → failed → neutral` so a single button reaches every state without swiping. The done→failed step is one write — `patchForFailed(true)` clears `done` in the same UPDATE, so the DB CHECK never sees an intermediate both-true row. Failed sets disable the RPE input (rating a set you didn't finish isn't meaningful). On the done transition the RPE selector auto-expands so the student can rate without an extra tap; failed sets never auto-expand because RPE is locked. Stats in [useStudentProgressStats.js](../src/hooks/useStudentProgressStats.js) only count true `done`; group auto-progression in [SessionView.jsx](../src/components/student/SessionView.jsx) treats a set as **resolved** iff `failed OR (done AND rpe != null)` — a done-without-RPE set keeps the group open so the auto-expanded RPE panel survives long enough for the student to record a value. Failed bypasses (no RPE required).

## Rest timer

- **Rest timer is an app-wide singleton with one rendering site.** [hooks/useRestTimer.js](../src/hooks/useRestTimer.js) holds one `{ logId, endsAt }` in module-scope and exposes it via `useSyncExternalStore`. Validating a new set calls `startRestTimer(logId, seconds)` which **replaces** the previous timer. Remaining seconds are derived from `endsAt - Date.now()` (timestamp-based, not a tick counter), and the hook listens to `visibilitychange` + `focus` so the timer stays correct after the tab is backgrounded or the phone is locked. `clearRestTimer(logId)` is a no-op unless the active timer matches — undoing a stale set never kills the current rest. Rendering lives in **one** place: [RestTimerBanner.jsx](../src/components/student/RestTimerBanner.jsx) — a compact pill mounted in the right slot of `SessionView`'s top bar (the slot opposite the back button) — so the indicator survives exercise-card transitions without pushing scroll content down. SetRow only writes to the singleton on done/undone transitions; it never reads or renders remaining time. The pill shows `Rest m:ss` while running, flashes "Rest done" on expiry, and auto-hides ~5s later.
- **Out-of-band rest-timer effects ride the singleton via two hooks, mounted in `SessionView` only.** [hooks/useRestTimerEffects.js](../src/hooks/useRestTimerEffects.js) acquires `navigator.wakeLock('screen')` while a timer is active (re-acquires on `visibilitychange → visible` because the browser auto-releases on hide), schedules a synthesized WebAudio beep + `navigator.vibrate` at `endsAt`, and mirrors `Rest m:ss · <title>` into `document.title` while the page is hidden so app-switcher glances show the countdown. The AudioContext is created/resumed on the first `pointerdown` so iOS lets it play unattended at expiry. [hooks/useRestTimerPush.js](../src/hooks/useRestTimerPush.js) is the Web Push bridge — see the next section. Neither hook reads or renders remaining time; they only react to `endsAt`/`logId` changes.

## Web Push (rest-timer "Rest done" lock-screen notification)

- **Live Activities / Dynamic Island are native-iOS-only.** PWA fallback is a Web Push notification fired at `endsAt`. Two tables back it: `push_subscriptions` (per-device subscription owned by the user; full CRUD via RLS keyed on `user_id = auth.uid()`) and `scheduled_pushes` (one row per pending notification with `fire_at`, `payload`, `status`, `canceled_at`, `sent_at`). Both were added in [2026_05_11_push_notifications.sql](../supabase/migrations/2026_05_11_push_notifications.sql); no triggers, RLS is the only client guardrail. The Edge Function uses the service role and double-checks `user_id` on every row it reads.
- **Custom service worker, not generated.** `vite-plugin-pwa` runs in `injectManifest` mode against [src/sw.js](../src/sw.js); the generated SW is gone. The custom SW still precaches the app shell + Google Fonts via workbox (so offline behaviour is unchanged) and adds two listeners: `push` shows the notification (using `tag` to dedupe stale notifications) and `notificationclick` focuses or opens the deep-link in `data.url`. Workbox is pulled in transitively by `vite-plugin-pwa`; don't add it to `package.json` explicitly.
- **Two Edge Functions handle delivery, split by call shape.** [dispatch-rest-push](../supabase/functions/dispatch-rest-push/index.ts) is **user-invoked** — the client posts `{ scheduleId }` with its own JWT, the function auths the caller, loads the `scheduled_pushes` row with the service role, sleeps until `fire_at`, re-reads to honor a late `canceled_at`, then fans out. [send-push](../supabase/functions/send-push/index.ts) is **internal-only** — it requires `Authorization: Bearer <service-role-key>` and is called by the DB trigger `notify_student_on_session_feedback` via pg_net. It takes `{ user_id, payload }` and immediately fans out. Both share the web-push + VAPID stack; 404/410 from the push service drops the dead subscription in either function.
- **Supabase Vault feeds the trigger; the function checks `INTERNAL_BEARER`.** `notify_student_on_session_feedback` reads `app_functions_url` and `app_service_role_key` from `vault.decrypted_secrets`. The value stored in `app_service_role_key` is sent as `Authorization: Bearer <value>` to send-push, which compares it against its `INTERNAL_BEARER` env var (set via `supabase secrets set`). **The two must hold the same value** — we don't reuse Supabase's auto-injected `SUPABASE_SERVICE_ROLE_KEY` for this check because newer projects get an `sb_secret_*` key whose full value can't be retrieved outside the dashboard, so the trigger-side and function-side values would drift. Without these secrets the trigger's push block silently no-ops (warning logged) and the in-app `notifications` row still gets written — so the feature degrades cleanly on dev environments. `ALTER DATABASE postgres SET app.*` is denied on Supabase's managed Postgres — don't reach for GUCs. **send-push must be deployed with `--no-verify-jwt`** so the INTERNAL_BEARER check is the only authorization gate.
- **Delays > 350s are refused.** The Supabase Edge Function wall-time limit is 400s; both client (`useRestTimerPush`) and server clamp at 350s with a 50s buffer. Typical rest periods (30–300s) are well within. Rests longer than that get no push — only the in-app beep + wake-lock.
- **VAPID keys are environment-scoped.** Public key ships to the client at build time via `VITE_VAPID_PUBLIC_KEY` (`.env`). Private key + a `mailto:` subject live in Supabase function secrets (`VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). Generate once with `npx web-push generate-vapid-keys --json` and set via `supabase secrets set ...`. If `VITE_VAPID_PUBLIC_KEY` is empty, `isPushSupported()` reports false and the Profile toggle renders the "not supported" copy instead of attempting to subscribe.
- **iOS support requires the PWA be installed.** Web Push on iOS Safari is gated on iOS 16.4+ AND the user adding the app to the Home Screen. We don't try to detect installation explicitly — `PushManager.subscribe` will throw and the toggle surfaces the error. Don't bypass `userVisibleOnly: true` (Apple rejects silent pushes).

## RLS / DB conventions

- **RLS is strict.** New tables need both student- and coach-side policies walking session → profile via `student_profile_for_session()` / `coach_profile_for_session()` helpers in `schema.sql`. Migrations go in `supabase/migrations/<date>_<name>.sql` *and* append to `schema.sql`.
- **`profiles.full_name` is self-editable; `id`, `role`, `created_at` are pinned.** The `Users update own profile` policy lets a signed-in user UPDATE their own row; the `profiles_pin_immutable_columns` BEFORE UPDATE trigger reverts any attempt to change `id`/`role`/`created_at` in the same payload, so a student can't promote themselves to coach via the Profile rename form. If a future Profile feature needs to mutate a new column, that column is automatically allowed by the policy — no extra grant needed — but think twice before opening up anything role-adjacent.
- **Past-program sessions are read-only on the student surface.** A session is locked iff `programs.is_active = false` OR `sessions.archived_at IS NOT NULL`. Enforced UI-side in `SessionView` via `isReadOnly` (derived from `session.program_is_active` + `archived_at`) and DB-side by student RLS on `set_logs` / `session_confirmations` / `slot_comments` (helpers `program_active_for_session`, `program_active_for_slot`). Coach writes are never gated this way.

## UserMenu / profile surface

- **`UserMenu` is role-aware.** Pass `profileHref="/student/profile"` on student pages → the avatar becomes a direct `<Link>` to the Profile page (no popover). Coach pages omit the prop → avatar opens the legacy popover with theme/language/sign-out inline. The student popover has been retired; theme, language, and sign-out live exclusively in [StudentProfile.jsx](../src/components/student/StudentProfile.jsx). When adding a new student-side top-level page, remember to pass `profileHref` so the avatar keeps working.
- **Student bottom-nav has exactly 4 tabs: Home, Sessions, Stats, Messages.** Goals is **not** a tab — it's reached from the Profile page's "Active goal" card via "View all". Bookmarks and deep links to `/student/goals` still work. Adding a fifth tab cramps mobile layout — extend Profile instead.
- **Student Profile is the avatar-tap destination on every student page.** It owns: display-name edit, coach card, lifetime totals, active goal, theme/language, email + change-password + sign-out. Don't add duplicate copies of these settings elsewhere on the student side.

## Messaging / notifications

- **Notifications are SECURITY DEFINER trigger-driven.** The `notifications` table has SELECT/UPDATE policies for the recipient only — there is **no client INSERT policy**. Events get into the table exclusively via DB triggers (`notify_coach_on_session_confirm` on `session_confirmations`; `notify_student_on_session_feedback` on `messages` when `session_id IS NOT NULL`). Adding a new event type = new trigger + new client `describeNotification` branch + new i18n key. The bell lives inside `ui/UserMenu` so every top-level page gets it for free; realtime updates are wired through `useNotificationsRealtime` mounted once in `AppShell`. Like messages, the table is in `supabase_realtime` with `REPLICA IDENTITY FULL`.
- **Feedback notifications also fan out a Web Push.** Inside `notify_student_on_session_feedback`, after the in-app `notifications` INSERT, the trigger calls `net.http_post` (pg_net) to the [`send-push`](../supabase/functions/send-push/index.ts) Edge Function. send-push fans the payload out to every `push_subscriptions` row for the recipient — same web-push + VAPID stack used for the rest timer. The trigger pulls `app_functions_url` + `app_service_role_key` from Supabase Vault; if either is unset or the HTTP call fails, the trigger logs a warning and continues — the in-app bell path is never blocked. Push delivery is one-shot (no `scheduled_pushes` row) because the event fires immediately; the unique partial index on `messages.session_id` already keeps it idempotent. The payload's `data.url` deep-links to `/sl_app/#/student/session/<id>` so `notificationclick` lands on the structured feedback card in `SessionView`.
- **Coach feedback messages render as session-reference cards.** Coach-authored messages with `session_id` set show a tappable "Re: <session>" card above the bubble — coach-side it deep-links to `/coach/student/:studentId/session/:sessionId/review`, student-side to `/student/session/:sessionId`. The Messages nav tab carries an unread-count badge fed by `useUnreadMessageCount`. The coach enters a thread either from `/coach/messages` or via the **Message** button on the per-student Profile tab.
- **Student surfaces feedback in two places.** [SessionView.jsx](../src/components/student/SessionView.jsx) reads `useSessionFeedback(sessionId)` and renders the body inline as a "Coach's feedback" card between the progress bar and slot groups when a feedback row exists — this is the structured destination the `SessionReferenceCard` deep-link from Messages lands on. [SessionCard.jsx](../src/components/student/SessionCard.jsx) shows a small "feedback" pill in its trailing block when `hasFeedback` is true; both [StudentSessions.jsx](../src/components/student/StudentSessions.jsx) and the next-session card in [StudentHome.jsx](../src/components/student/StudentHome.jsx) feed it from `useMyFeedbackSessionIds()` (a single batched query for the student-recipient feedback rows). New incoming feedback invalidates the `[messages]` subtree via `useMessagesRealtime`, so the pill appears without a manual refresh.
- **Messaging is realtime + RLS-scoped.** `messages` rows have `sender_id`, `recipient_id` (both `profiles.id`), and an optional `session_id` (FK to `sessions`, ON DELETE SET NULL) used by the coach-feedback flow. RLS lets either party SELECT, only the sender INSERT (and only when the pair is coach-student via `profiles_are_coach_student()`); when `session_id` is non-null the policy also requires sender = `coach_profile_for_session(session_id)` and recipient = `student_profile_for_session(session_id)` so the link can't be forged. Only the recipient UPDATEs — the `BEFORE UPDATE` trigger pins every column except `read_at` (including `session_id`). The sender DELETEs their own ordinary chat messages; the policy gates DELETE on `session_id IS NULL` so coach feedback rows (which set `sessions.reviewed_at` via `notify_student_on_session_feedback`) can't be removed and the one-shot review invariant holds. The table is in `supabase_realtime` with `REPLICA IDENTITY FULL`; [hooks/useMessages.js](../src/hooks/useMessages.js) opens **one** channel from `AppShell` (`useMessagesRealtime`) and invalidates the `[messages]` subtree on INSERT/UPDATE/DELETE. `useSessionRefsForMessages` does a single batched fetch of titles/dates for the unique `session_id`s referenced by the visible thread. The Messages nav tab carries an unread-count badge fed by `useUnreadMessageCount`. Conversations roll-up is a client-side fold over recent rows — fine at coach scale, swap for an RPC if the table grows.

## Coach session review

- **Coach session review is one-shot per session.** A session can be reviewed at most once — whether the coach left feedback or not. State lives on `sessions.reviewed_at timestamptz`. Two write paths set it: (1) the `notify_student_on_session_feedback` trigger stamps `reviewed_at = NEW.created_at` when a feedback message is inserted (idempotent — `WHERE reviewed_at IS NULL`), and (2) [`useMarkSessionReviewed`](../src/hooks/useSession.js) UPDATEs the row directly when the coach clicks "Finish without feedback". The top-of-page back arrow does NOT mark reviewed — it's a "leave and come back" gesture; only Send-feedback and Finish-without-feedback are completion gestures. [SessionReview.jsx](../src/components/coach/SessionReview.jsx) renders three branches: [SessionFeedbackSent.jsx](../src/components/coach/SessionFeedbackSent.jsx) (feedback exists), [SessionReviewedNoFeedback.jsx](../src/components/coach/SessionReviewedNoFeedback.jsx) (`reviewed_at` set but no feedback), or [SessionFeedbackComposer.jsx](../src/components/coach/SessionFeedbackComposer.jsx) (not yet reviewed). [SessionsFeed.jsx](../src/components/coach/SessionsFeed.jsx) shows a green "Reviewed" pill on cards whose session has `reviewed_at` set; [`useAllConfirmations`](../src/hooks/useSessionConfirmation.js) surfaces it. Feedback itself remains one-shot independently — a UNIQUE partial index on `messages(session_id) WHERE session_id IS NOT NULL` guarantees ≤ 1 feedback row per session, and the messages UPDATE trigger pins `body` + `session_id` so feedback is immutable once sent.

## Coach Students-page layout & dashboards

- **Coach dashboard week-strip data is folded into one query.** [useCoachDashboardPrograms](../src/hooks/useProgram.js) returns, per student, `{ programName, activeWeek, weekDays }` where `weekDays` is a 7-slot M..S array of `{ dayNumber, session, confirmed }`. Day-mapping uses `sessionDayNumber()` from [lib/day.js](../src/lib/day.js) (prefers `scheduled_date` over `day_number`) and prefers an active session over an archived sibling on the same day. [StudentWeekStrip.jsx](../src/components/coach/StudentWeekStrip.jsx) renders the strip purely from `weekDays` + `todayDayNumber()` — status mapping (completed / today / upcoming / missed / rest) is local to the component, no extra fetches per card.
- **Coach Students-page layout owns the student lookup.** [CoachHome.jsx](../src/components/coach/CoachHome.jsx) resolves the `:studentId` from `useStudents()` and exposes the resolved student to all four sub-tabs (Profile, Programming, Goals, Stats) via `<Outlet context={{ student }} />`. Each tab section reads it with `useOutletContext()`. `/coach/students/:id` redirects to `…/programming` (the index sub-route) to preserve the prior landing UX. The legacy `/coach/student/:id/goals` URL redirects to `…/students/:id/goals`. The legacy `…/students/:id/messaging` deep link redirects to `…/profile` (where the **Message** action now lives, alongside **View sessions**).

## Student home week strip

- **The Home day strip is calendar-based, not training-week-based.** [StudentHome.jsx](../src/components/student/StudentHome.jsx) shows a navigable calendar week (`weekOffset` state, 0 = the real current week, ‹ › arrows + "Today" reset). Sessions **with** `scheduled_date` place on their true calendar date — pulled from every training week of the active program — so a "week 1" session dated next Monday shows in next week's strip, never bleeding into the current one. Sessions **without** `scheduled_date` (or with an unparseable one) have no calendar anchor and keep the legacy behavior: rendered by `day_number` from the active training week (first week with an open session) on the current calendar week only. **Every same-day collision — dated vs dated, dated vs undated, and `todaysSession` — resolves through `preferSession`: active beats archived, then pending beats confirmed, then first-in-program-order wins.** The pending-beats-confirmed leg is load-bearing: without it a confirmed dated session from another training week hides a session still due that day, disables its cell, and flips the greeting to "done". `scheduled_date` is a bare `YYYY-MM-DD` — always parse it with `parseISODate` from [lib/day.js](../src/lib/day.js) (local time), never `Date.parse`/`toISOString` which shift across timezones. The "Next session" card pulls from the active week **plus dated sessions of every other week** (a date is a real chronological position; undated non-active-week sessions stay out), ordered by effective date (`scheduled_date`, else `day_number` projected onto the current week), and shows the real date in its subtitle when one exists — so the strip, greeting, and Next card always agree. Day-cell `aria-label`s include the day-of-month (`Monday 13 — Push Day`) because the button's label masks its inner text from AT; the range header is `aria-live="polite"` so week navigation is announced.

## Stats persistence

- **Stats page selections are persisted in URL + localStorage.** Program scope lives in the URL (`?scope=` on `/student/stats`, `?statsScope=` on `/coach/students/:id/stats`) so a refresh holds — but a tab switch drops the search params, so [lib/statsPrefs.js](../src/lib/statsPrefs.js) mirrors `{ scope, exerciseId }` to localStorage too. On mount, if the URL has no scope param, the parent hydrates it from localStorage. The exercise selection inside [ExerciseProgressChart.jsx](../src/components/student/ExerciseProgressChart.jsx) reads/writes its own `localStorage` slot via the `storageKey` prop. Keys are namespaced per surface — `sl_stats_prefs:self` for the student, `sl_stats_prefs:coach:<studentId>` for each coach view — so a coach hopping between students never drags one student's selection onto another. Stale ids fall back gracefully via the existing `scopeIsValid` and `exercises.some(...)` checks.

## Offline-safe student writes

- **Offline-safe student writes are wired through one allow-list.** Persistence + replay are handled by [`lib/queryClient.js`](../src/lib/queryClient.js) (PersistQueryClient + IDB store + `shouldPersistQuery` allow-list: `session`, `set-logs`, `slot-comments`, `session-confirmation`, `set-videos`) and [`lib/offlineMutations.js`](../src/lib/offlineMutations.js) (mutationFns + `registerOfflineMutationDefaults`). Any new student-side mutation that must survive offline → reload → resume needs three things: a stable `mutationKey` from `MUTATION_KEYS`, its mutationFn registered in `MUTATION_FNS`, and `networkMode: 'online'` (the default — pauses-while-offline, fires-on-reconnect; **`'offlineFirst'` would silently fail with `retry: 0`**). Replay-idempotency is the caller's job: prefer UPSERT over INSERT (`useConfirmSession` upserts on `session_id`, `useSaveSlotComment` upserts on `exercise_slot_id`) so a queued write replayed against an already-mutated row no-ops instead of tripping a UNIQUE constraint. `AppShell` calls `resumePausedMutations()` on every `online` event; the user-facing surface is [`components/ui/OfflineBanner.jsx`](../src/components/ui/OfflineBanner.jsx), backed by [`hooks/useOnlineStatus.js`](../src/hooks/useOnlineStatus.js). Video uploads are deliberately **out of scope** — `VideoUploadButton` is gated on `useOnlineStatus()` and flips to a "Connect to record video" hint when offline (Supabase Storage has no resumable-upload story we can lean on). Coach writes are not queued. Logout/login wipes both the in-memory client and the persisted IDB blob via `ClearOnUserChange` in `App.jsx`.
