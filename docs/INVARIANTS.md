# INVARIANTS.md — Behavioral & Schema Invariants

Load this file when the change touches: routing/scroll-shell, dark mode, RLS, `set_logs` schema, rest timer, messaging/notifications triggers, offline mutations, coach session review, stats persistence, the role-aware `UserMenu`, or anything to do with **what comes next / when a session was trained** (the queue model, `performed_on`/`performed_at`, day strips). Otherwise stay in `CLAUDE.md`.

## Shell, routing, viewport

- **HashRouter intentional** (GitHub Pages). URLs contain `/#/`. Vite `base` is `/sl_app/`. Pages are `React.lazy`-loaded in `routes.jsx`.
- **Bare `/sl_app/` (no hash) redirects to the role home.** iOS PWAs cold-launch at the manifest `start_url` (`/sl_app/`), not at the last-visited hash route, so an authenticated re-launch lands at HashRouter pathname `/`. The `RedirectToRoleHome` index route inside `AppShell` (in [routes.jsx](../src/routes.jsx)) bounces to `/${role}` — without it, the wildcard catches `/` and renders `NotFound`. Unauthenticated users are intercepted earlier by `ProtectedRoute → /login`.
- **Outer page must not scroll.** `html, body, #root` are `overflow: hidden; position: fixed; inset: 0`. `AppShell` is `h-full flex-col` (NOT `h-dvh` — iOS Safari disagrees and spawns a second scrollbar). Only `main` scrolls. Don't touch — this keeps the mobile keyboard from pushing the sticky `BottomNav` mid-page. The inner wrapper inside `main` is `h-full flex flex-col` (not `min-h-full`) so flex-1 + min-h-0 children — currently only Messages thread/composer — get a hard height budget; pages with naturally tall content still scroll via `main` because it has `overflow-y-auto`.
- **iOS Safari auto-zooms focused `<input>` / `<textarea>` / `<select>` < 16px.** Every text-entry form element is 16px. Don't drop below. File pickers, radios, checkboxes, sliders unaffected.
- **Tailwind 4, CSS-based config.** `@theme` + `@custom-variant` in `src/index.css`. No `tailwind.config.js`.
- **Dark mode = class-based CSS remap, not `dark:` utilities.** Extend `src/index.css`. Inline `style={{ color }}` does NOT flip — use classes. `disabled:bg-*` variants also don't pick up `.dark .bg-*` remaps; use `disabled:bg-ink-100`.
- **The app is DARK-ONLY and there is no theme toggle.** `class="dark"` ships on `<html>` in [index.html](../index.html), so the first paint is dark with no light flash, and `ThemeProvider` only re-asserts it — `toggleTheme`/`setTheme` are deliberate no-ops so a stale caller cannot flip it, and a `sl_app_theme: light` left in localStorage from the old toggle is ignored. Reason: an installed iOS PWA colours its status bar from the manifest's single static `theme_color`, so a light theme could never match the strip once the app left Safari. **Keep writing components against the light utilities** (`bg-white`, `text-gray-900`) — the `.dark` remaps are what render them, so hardcoding ink values instead breaks the one-line path back to a light theme. Reinstating the toggle = restore `ui/ThemeToggle.jsx` from git and give `theme` its state back; no CSS archaeology.
- **The iOS status-bar / Dynamic Island strip is coloured by the MANIFEST, and nothing else.** An installed iOS web app ignores `theme-color` metas entirely — those only govern in-browser tabs — so `theme_color`/`background_color` in [vite.config.js](../vite.config.js) are `#111110`. A manifest is static, so that value cannot follow the in-app theme toggle: it is dark because the app is dark-first, and a coach on the light theme gets a dark strip and splash. That is the accepted trade.
- **`manifest.webmanifest` must stay OUT of the service-worker precache.** [src/sw.js](../src/sw.js) filters it out of `__WB_MANIFEST`. While it was precached, Safari asked the worker for the manifest and got the stale copy back, so a `theme_color` change never reached iOS *even after removing and re-adding the app* — which made the strip colour look unfixable for several rounds. Nothing offline depends on it: the manifest matters at install time and iOS keeps its own copy after that.
- **Do not add `apple-mobile-web-app-status-bar-style: black-translucent`.** It is the only thing that makes the strip track the theme toggle, and it was tried on-device — but it leaves the initial containing block one status bar short of the screen, so the shell ends early and a dead strip appears along the bottom that lifts `BottomNav` off the edge. Neither `100dvh`, nor `inset: 0`, nor dropping the legacy `apple-mobile-web-app-capable` pairing sized that away. The strip colour is not worth a broken layout.
- **Still true for Safari tabs and Android:** `ThemeProvider` rewrites every `theme-color` entry via `paintStatusBar` (the stored theme may disagree with `prefers-color-scheme`), [index.html](../index.html) keeps a **media-less** `theme-color` last as a fallback for UAs that ignore `media`, and `html` itself is painted — not just `body` — since with `viewport-fit=cover` the safe-area strips fall outside the AppShell's painted box.

## React / hooks discipline

- **Rules of Hooks:** never call `useMemo` (or any hook) after an early return like `if (isLoading) return <Spinner/>`.
- **`useWeek.js` owns every week AND session mutation** — `useCreateWeek`, `useUpdateWeek`, `useDeleteWeek`, `useReorderWeeks`, and `useCreateSession` / `useUpdateSession` / `useArchiveSession` / `useDeleteSession`. Not `useSession.js` (which owns the session *tree* read and its slots), and not `useProgram.js` (which owned `useCreateWeek` until it was moved back here).
- **Any write that changes a week, a session or an exercise slot must invalidate `['program']`.** The Program Sheet (the Programming tab) renders the whole block — week labels, session titles, weekday pills and per-session exercise counts — from `useProgram`'s `['program']` entry. `['week', id]` is now read by almost nothing, so invalidating only that is a silent no-op: the write reaches the DB and the sheet keeps rendering the stale value until its staleTime expires. This bit `useUpdateSession` (a day move wrote through but the pill did not change), `useArchiveSession`, `useDeleteSession`, `useAddSlot` and `useDeleteSlot` — all now drop `['program']` too. Add it to any new session/slot mutation.
- **Any write that moves a session in or out of a calendar-week slot must invalidate `['coach-dashboard-programs']`** — the Athletes-roster week strips come from their own summary query, so they don't refresh off `['program']` or `['week']`. Use the exported `invalidateCoachDashboard(qc)` from [useProgram.js](../src/hooks/useProgram.js) rather than repeating the key.
- **Never fan a list of session ids back into `.in('session_id', […])`.** The GET URL grows ~37 bytes per id and hard-fails once a coach accumulates a few hundred sessions. Filter through the embedded join instead (`session:sessions!inner(week:weeks!inner(program:programs!inner(…)))` + `.eq('session.week.program.…')`), as `useAllConfirmations`, `useCoachDashboardPrograms`, `useWeekConfirmedSessionIds` and `useStudentProgressStats` all now do.
- **Counting rows means `{ count: 'exact', head: true }`, never `data.length`.** PostgREST silently truncates an unbounded response at `db-max-rows` (1000) and returns no error, so a length-based count reads as a plausible wrong number. If the rows themselves are needed, read them with `fetchAllRows` (next bullet).
- **A read whose result grows with an athlete's history goes through `fetchAllRows`, never through `.limit(<a big number>)`.** PostgREST answers one request with at most `db-max-rows` rows (1000 in production) and reports nothing when it cuts; a client limit can only lower that ceiling. [`fetchAllRows(buildQuery, { pageSize, column, ascending })`](../src/lib/supabasePaging.js) asks again until a page comes back short. It pages by KEYSET — `order=<column>.asc`, then `<column>=gt.<last key>` — because an offset shifts when a row is inserted between two requests and a value does not; rows are de-duplicated on the key. Four rules follow. `buildQuery` returns a NEW query on every call, with its filters and without `.order()`, `.limit()` or `.range()`. The select must include the key column (`id` by default) — a row without it throws on the first page, not on the day a second page is needed. The key must be unique among the rows the query matches (`id`; `logged_on` within one athlete's `bodyweight_logs`; `session_id` in `session_confirmations`). And the result comes back in KEY order, which for a uuid is no order: a caller that needs dates sorts the rows itself (`useStudentProgressStats` sorts confirmations newest first, `readDoneSetHistory` sorts sets oldest first). A full page is never taken for the end, and a full page that brings nothing new throws instead of stopping. Today's callers: `useStudentProgressStats` (done sets, swaps, confirmations), `readDoneSetHistory` in `lib/doneSetHistory.js` (the done sets and swaps that `useStudentRecords` and `useLastPerformance` derive from), `fetchBodyweightSeries` in `useBodyweight.js` (the bodyweight series behind `useStudentRecords`), `useStudentLifetimeStats` (volume rows), `useStudentHistoricalSessions` (confirmations). `src/lib/supabasePaging.test.js` reads every source file and fails on a `.limit(n)` with `n` above `PAGE_SIZE`; the one read still listed there as waiting is the conversation list in `useMessages.js`.
- **`PAGE_SIZE` (1000) must not exceed the project's API "Max rows" setting.** The loop ends on a page shorter than the page size, so a server that caps lower makes every page look like the last one and the truncation is back, silently, for every caller. If Max rows is ever lowered in the dashboard, lower `PAGE_SIZE` in `src/lib/supabasePaging.js` in the same change. Raising Max rows needs nothing.
- **A hook test that reads a growing table mocks Supabase with `fakePostgrest`, not with a resolved value.** A `mockResolvedValue` hands the whole fixture back whatever the request says, which is how three hooks passed their tests while cutting at 1000 rows in production. [`fakePostgrest(tables)`](../src/test/fakePostgrest.js) serves tables by name, sorts on `.order()`, applies `.gt()` / `.lt()`, and never returns more than `maxRows` (1000) rows whatever `.limit()` it is sent; every other filter is recorded on `db.requests`, not applied, so the fixture is what the WHERE clause lets through and the test asserts the filters. A fixture of 1001 rows is then enough to prove a read pages.
- **Test auth is mocked, never provided:** `useAuth`'s context is module-private, so wrapping a component in your own `AuthContext.Provider` silently provides a value nothing reads and the component renders signed-out. Always `vi.mock('../../hooks/useAuth', ...)` instead. `src/test/utils.jsx` exports only `createTestQueryClient`; supply Router/Theme wrappers per test as needed. `matchMedia` polyfill lives in `src/test/setup.js`.

## `set_logs` — per-set targets, outcomes, RPE

- **Per-set targets live on `set_logs`, not `exercise_slots`.** Each set_log row stores both prescription (`target_reps`, `target_duration_seconds`, `target_weight_kg`, `target_rest_seconds`) and student actuals (`done`, `failed`, `rpe`, `weight_kg`). The legacy `exercise_slots.{reps, weight_kg, duration_seconds, rest_seconds}` columns are kept as deprecated mirrors of set 1 — slated for removal in a follow-up migration. `useAddSlot` materializes one set_log per planned set; `useUpdateSlot` fans uniform target edits to the logs that are still pending; `useUpdateSetTarget` writes to a single pending log; `useResetSlotToUniform` re-syncs every pending log to set 1. `isSlotUniform(slot)` and `formatSlotPrescription(slot)` in `lib/volume.js` decide compact vs. per-set rendering.
- **Students log off-plan actuals on `set_logs.actual_reps` / `actual_weight_kg`; the coach-owned `target_*` columns stay immutable to students.** When a student can't follow a set as written, [SetRow.jsx](../src/components/student/SetRow.jsx) exposes an "Actual" pill that opens two inputs prefilled from the prescribed target; [`useLogActual`](../src/hooks/useSetLogs.js) (offline-safe, `MUTATION_KEYS.logActual`) UPDATEs only the `actual_*` columns. The client **normalizes a value equal to its target back to `null`**, so a populated `actual_*` always denotes a genuine deviation — that's the invariant `hasLoggedActual(log)` in [volume.js](../src/lib/volume.js) relies on, and what `formatActual(log)` renders (falling back to the target for the un-overridden dimension). The coach sees these in an "Off-plan" band per slot in [SessionReview.jsx](../src/components/coach/SessionReview.jsx) (no new coach RLS — the existing FOR ALL policy already covers them). The shared-row coach/student column split (coach owns `target_*`, student owns actuals) was previously client-discipline only; it is now **hardened by the `pin_set_log_targets_for_student` BEFORE UPDATE trigger**, which reverts any student attempt to mutate `target_*` — and what the set IS (next bullet). Coach writes resolve a different `auth.uid()` than the slot's student, so `useUpdateSlot` / `useUpdateSetTarget` pass through untouched. `set-logs` is already in `PERSISTED_QUERY_ROOTS`, so the actuals write has offline parity for free.
- **The athlete owns what they DID on a set; what the set IS belongs to the coach, and the athlete's own UPDATE cannot change it.** `pin_set_log_targets_for_student` (migration `2026_10_11_06_pin_student_writes.sql`, review P14) puts seven columns back to `OLD` when the writer is the athlete of the set: the four `target_*`, `is_student_added`, `exercise_slot_id` and `set_number`. `is_student_added` is what the `Students delete own set logs` policy trusts — flipped to `true`, a prescribed set could be deleted and inserted again with other targets; a set given another `set_number` or another `exercise_slot_id` leaves its place in `UNIQUE(exercise_slot_id, set_number)` free for a forged one. Whose set it is, is asked of `OLD.exercise_slot_id`, never of `NEW`: the slot is one of the columns held. **Silent**, like the pin on the targets: the UPDATE answers "1 row" and the columns keep their values — never read a row count as "written", read the row. A new column that says what a set is (a prescription column, a link to another row) joins the list in that function; a new column for what the athlete did does not. The coach is not the athlete of the set and passes through — `reconcileSetLogCount` in `src/hooks/useSession.js` renumbers the athlete's extra sets (park at `set_number + 100000`, then place) — and so does a statement without a user id. No athlete-side hook may send one of the seven columns in an `update`: it would be dropped without an error. `supabase/tests/pins.test.js` holds it.
- **Structural deviations: students can swap/skip an exercise, skip a set, or add an extra set — none of which touch the coach's prescription.** Exercise-level swap/skip live in the `slot_deviations` table (one row per slot, `UNIQUE(exercise_slot_id)`, `kind ∈ {swap,skip}`, `substitute_exercise_id` FK to `exercise_library`, held to the library of the program's coach by `trg_check_deviation_substitute_in_coach_library` — **library-only, no free-text**, so swaps stay known exercises for stats). RLS clones `slot_comments` (student owns the row; INSERT, UPDATE and DELETE ask the three questions of every athlete write — own row, active program, session neither archived nor reviewed; coach reads); offline via [`useSaveSlotDeviation`](../src/hooks/useSlotDeviations.js) (upsert/delete on the natural key, `'slot-deviations'` is in `PERSISTED_QUERY_ROOTS`). Per-set deviations are two booleans on `set_logs`: `skipped` (intentionally dropped — DB CHECK `set_logs_skipped_not_resolved` keeps it mutually exclusive with done/failed; written by [`useSetSkipped`](../src/hooks/useSetLogs.js), offline) and `is_student_added` (an extra set with NULL targets). **Adding/removing an extra set is ONLINE-ONLY** ([`useAddStudentSet`](../src/hooks/useSetLogs.js)/`useRemoveStudentSet`) — a brand-new-row INSERT can't be safely queued offline (the offline lane only UPDATE/UPSERT/DELETEs existing rows, and two offline adds would collide on `UNIQUE(exercise_slot_id, set_number)`); the UI gates it on `useOnlineStatus`, like `VideoUploadButton`. A new deviation notifies the coach via the `notify_coach_on_slot_deviation` trigger (`kind='session_deviation'`, in-app + best-effort Web Push, AFTER INSERT only so edits don't re-notify). Student UI: [SlotDeviationBar.jsx](../src/components/student/SlotDeviationBar.jsx) (swap/skip) + per-set controls in [SetRow.jsx](../src/components/student/SetRow.jsx); coach UI: deviation banner + skipped/extra pills in [SessionReview.jsx](../src/components/coach/SessionReview.jsx) / [SlotProgress.jsx](../src/components/coach/SlotProgress.jsx).
- **Relative strength (×BW) is opt-in per exercise and PR selection never folds in bodyweight.** `exercise_library.load_mode` is **NULLABLE** (`full` = logged weight IS the total load; `added` = logged weight sits on top of bodyweight, so system load = bodyweight + added; **NULL = unclassified**, behaves exactly like before — added/logged-load e1RM, no ×BW). NULLABLE (not `DEFAULT 'full'`) is deliberate: a default would silently label the weighted-calisthenics majority and show a *wrong* low ×BW on deploy. [`buildRecords`](../src/lib/records.js) leaves the PR headline + SORT on the bodyweight-independent added/logged-load e1RM (so a heavier student can't manufacture or reshuffle a PR, and the est-1RM number is unchanged from before this feature); `relStrength` (the ×BW pill) is computed SEPARATELY as the **MAXIMUM** over all qualifying sets of (system-load e1RM ÷ bodyweight at that set), via a `bodyweightAt(dateIso)` resolver from the `bodyweight_logs` series (`useStudentRecords`; coach flow resolves `profile_id` from the students row — the "Coaches read their students' bodyweight" RLS policy permits it). Tracking it as a true max — not deriving it from the added-load PR set, which needn't be the strongest RELATIVE single — is what a review caught: the PR set and the peak-×BW set can differ, and a bodyweight-only set on an `added` movement (system load = bodyweight) still counts. Unknown bodyweight → `relStrength=null`, pill omitted (never `0×`/NaN). `useLogBodyweight` MUST invalidate `['student-records']` (the series lives inside that query's `queryFn`, not its key) or a freshly-logged weight never unlocks the pill. **`useLastPerformance` and tonnage/volume (`lib/volume.js`, `useStudentProgressStats`) stay load_mode-blind by design** — ×BW and tonnage can tell slightly different stories for the same added-load lift; do NOT "fix" one to match the other. The natural next column is a `bw_fraction` for partial-bodyweight movements (push-up ≈0.64) — deferred; `text`+`CHECK` leaves room.
- **Student program authoring is an approval-gate model, ONLINE-ONLY for v1 (Phase 3.4).** `programs.created_by` (NULL for coach rows) + `status` (`draft`/`approved`, DEFAULT `approved` so the coach flow is untouched) + a `CHECK (NOT (status='draft' AND is_active))` (a draft can never be the active block). A student authors a draft's structure (weeks/sessions/exercise_slots + slot-level scalars) via ADDITIVE RLS gated on the SECURITY-DEFINER-STABLE `program_is_own_draft`/`week_is_own_draft`/`session_is_own_draft` helpers — **descendant policies MUST reach `programs` through these definers, never an inline subquery, or Postgres raises "infinite recursion in policy"** (the same firewall as the `*_for_slot`/`*_for_session` family). Students **never write `set_logs`** while drafting — [`approve_program`](../supabase/migrations/2026_07_21_student_program_authoring.sql) (coach-only SECURITY DEFINER; self-authorizes with `auth.uid() IS NULL OR v_coach_id IS DISTINCT FROM auth.uid()`, where `v_coach_id` is `students.coach_id`) materializes them from the slot scalars at approval and flips `status='approved'`, so `pin_set_log_targets_for_student` needs no draft exception. The `pin_program_authoring_columns` BEFORE UPDATE trigger makes `created_by` **and `student_id`** immutable for everyone (pinning `student_id` blocks a draft author from re-pointing their draft to another student — tenant isolation; the security review caught this) and blocks the author (`auth.uid() = created_by`) from moving `status`/`approved_at` — only the coach can approve — and from changing `submitted_at` once it is set (next bullets). Verified live: a student can build their own draft and cannot self-approve or draft for another student; a non-coach `approve_program` is rejected. **Authoring is OFFLINE-CAPABLE (3.4d):** the draft is edited in an optimistic `['draft-tree', programId]` cache with **client-minted `crypto.randomUUID()` ids**, and every edit dispatches ONE keyed `saveDraftTree` mutation carrying the WHOLE flat snapshot to [`save_draft_tree(p_tree jsonb)`](../supabase/migrations/2026_07_24_save_draft_tree.sql). That RPC is **SECURITY INVOKER** (rides this same own-draft RLS + the exercise-in-coach-library WITH CHECK + the pin trigger — zero new trust surface), UPSERTs the program row (never deletes it, so `created_by`/`student_id`/`approved_at`/the one-draft index survive) and **DELETEs children by `program_id` then re-INSERTs from the jsonb** — a declarative full-replace that is **idempotent + reorder-proof** ONLY because a draft carries no `set_logs`/`slot_comments`/`slot_deviations`, so the cascade is inert (re-running a snapshot converges; stacked snapshots replay FIFO to the same end state; the `weeks(program_id,week_number)`/`sessions(week_id,sort_order)` uniques never transiently collide). The submit edge is a SEPARATE `UPDATE ... WHERE submitted_at IS NULL` so `notify_coach_on_program_submit` (AFTER UPDATE) fires exactly once even when create+submit happen in one offline session (an AFTER UPDATE trigger never fires on the INSERT branch). The five per-edit hooks are plain optimistic-cache editors (no `useMutation`); only `useSaveDraftTree`/`useDiscardDraft` are keyed (dedicated `draft-tree` FIFO scope, isolated from the set-log `offline-writes` lane). Persisted roots gain `my-draft`/`draft-tree`/`exercise-library`. Approval-race (`draft_not_editable`)/two-device (`23505`)/RLS (`42501`) → the client reconciles (invalidate); `exercise_unavailable` → keep the local tree + a specific toast. **The resume-time reconcile in `App.jsx`/`AppShell` MUST be guarded by `hasUnsyncedDraftSave` — a review caught that an UNCONDITIONAL `resumePausedMutations().then(invalidate)` clobbers the optimistic tree when a save errors (a transient RPC 500 while the GET succeeds refetches the pre-edit/null server state and silently destroys the whole offline session).** The save's onError/onSuccess/`skipErrorToast` live in the mutation DEFAULTS (`lib/offlineMutations.js`), not the hook, so a hydrated post-reload resume behaves identically (not silent). The XOR `CHECK` on `exercise_slots` (exactly one of reps/duration) is enforced at THREE layers — `SlotRow.commit` clamps reps ≥ 1, `buildSnapshot` re-coerces, and the RPC coerces again — because a both-null slot would abort the whole-tree replay. Verified live under RLS: idempotent re-run stays 1/1/1, coach notified once, non-owner write RLS-blocked. **The submit→review loop (3.4c):** the student sets `submitted_at` (own-draft UPDATE) → the `notify_coach_on_program_submit` AFTER UPDATE trigger fires ONLY on the `submitted_at` NULL→set transition of a `draft` (so `approve_program`, which sets `submitted_at=NULL`, never re-fires it) and notifies the coach (`program_submitted`, bell + best-effort push). The coach then either `approve_program` (→ `program_approved`, lands **approved + inactive**; the coach Sets active separately — the copy must NOT claim auto-activation) or [`send_back_program`](../supabase/migrations/2026_07_22_program_submit_notify.sql) (coach-only SECURITY DEFINER, self-authorizes on `students.coach_id = auth.uid()`; clears `submitted_at` so the student can revise and re-submit, which re-fires the notify trigger; → `program_sent_back`). Both client hooks (`useApproveProgram`/`useSendBackProgram`) are online-only and invalidate on `vars.studentId`, so callers MUST pass it.
- **A session of a DRAFT carries no `reviewed_at`, no `archived_at`, no `performed_at` and no `scheduled_date` — whoever writes it.** `trg_pin_draft_session_columns` (`pin_draft_session_columns()`, `BEFORE INSERT OR UPDATE` on `sessions`, migration `2026_10_11_06_pin_student_writes.sql`, review P13) sets the four to NULL while `programs.status = 'draft'`. `Students author own draft sessions` is `FOR ALL`: the author writes every column of the sessions of their draft, and a draft sent in with `reviewed_at` set gave, once approved, sessions that never reached the coach's "to review" list and refused feedback as already given. **The rule is keyed on the status of the program, never on who writes**: `sessions.performed_at` is written by `sync_session_performed_at`, a SECURITY DEFINER trigger that runs inside the athlete's own request — on an approved program the athlete may well have authored. A pin "for the author" or "for the athlete" undoes that write, and confirmed sessions lose their training date (`supabase/tests/pins.test.js`, "once approved, a program its athlete wrote is trained and reviewed like any other", fails on exactly that). Consequences: the coach cannot archive or date a session of a draft either — the write is accepted and not kept, both are done after approval; a session moved into a draft loses the four; a new session column that records what happened to a session after approval joins the list in that function. `approve_program` clears the four on the sessions of the program it approves, for the drafts written before the trigger existed. Silent, like the other pins. **The function is `STABLE`, and a later `CREATE OR REPLACE` must keep the keyword**: the policy judges the program through `week_is_own_draft` (`STABLE`), as the statement saw it when it started, and a `VOLATILE` trigger function reads it as it is by the time the row is reached — so a stamp that waits for a row lock while the coach approves was "own draft" for the policy and "approved" for the pin, and landed on the approved program. An author reaches that with the API alone, a few connections stamping at once. No single-connection test sees it; `supabase/tests/pins.test.js`, "a stamp on its way while the coach approves …", holds it on three. KNOWN residual gaps: (1) the trigger judges a session when it is written — a program flipped from `approved` back to `draft` (no path of the app does it; a coach calling the API by hand could) keeps its stamped sessions until each is next written; (2) the price of `STABLE` — a week created earlier in the SAME statement as its session (a data-modifying CTE) is not seen. The policies do not see it either, so the author and the coach are refused (`42501`); only a caller row-level security does not apply to (the owner, the service role) gets a stamped session into a draft that way. `save_draft_tree` writes the weeks, then the sessions, in two statements — keep it so.
- **A submission is made once.** For the author of a draft, `pin_program_authoring_columns` keeps `submitted_at` as it is once it is not NULL (migration 06, review B4): `notify_coach_on_program_submit` fires on every NULL → set edge, and an author who could clear the column and set it again notified the coach, bell and push, as often as they liked. The way back is the coach's — `send_back_program`, after which the author submits again and the coach is told again, once — and `approve_program` clears it with the approval; neither is the author. A "withdraw my submission" feature for the athlete is therefore an RPC with its own rule, not an UPDATE of the column. KNOWN residual gap: an author can still discard a draft, write a new one and submit it — one notification per draft.
- **Adopting a swap into the program is a coach-only, forward-only, SECURITY DEFINER RPC (Phase 3.1).** [`adopt_swap(p_slot_id, p_substitute_id, p_dry_run)`](../supabase/migrations/2026_07_18_adopt_swap.sql) is the ONLY write path (coaches have SELECT-only on `slot_deviations` and the multi-slot rewrite must be atomic). Because a definer bypasses RLS it **self-authorizes**: it refuses a caller without a user id and asserts `coach_profile_for_session(session)` is not distinct from `auth.uid()` and that `p_substitute_id` is in the *caller-coach's own* `exercise_library` (verified live: a non-coach caller gets `not authorized`). **Forward-only via a REAL ordinal bound**, NOT the optional "confirmed" flag (a student can fully train a session without ever tapping Confirm, so "unconfirmed" is not "future"). It flips `exercise_id` X→Y only on slots that are: same program, `exercise_id=X`, session not archived, a DIFFERENT session than the reviewed one, **strictly later in program order** (`week_number`/`sort_order`), **have no logged `set_logs`** (`set_log_is_logged`: done, failed, skipped, an RPE or an actual) and no set with a video, no `slot_comments` row, no `session_confirmations` row, and no `slot_deviations` row of their own. That structurally excludes the reviewed slot AND any already-trained past session, so history is never rewritten. The dialog's "past sessions keep their history" promise is truthful because dry-run and apply share this exact predicate. `set_logs.target_*` (X's numbers) are **kept as a seed** the coach retunes — never repointed. `p_dry_run=true` returns `{applied: count}` for the confirm dialog's blast radius and writes nothing; the coach passes the substitute id they SAW (race-safe vs a student undo); double-submit is a graceful 0-count no-op. Notifies the student (`kind='swap_adopted'`, bell + best-effort push). Client: [`useAdoptSwap`](../src/hooks/useAdoptSwap.js) is **online-only** (atomic server rewrite can't queue offline). This is the first Phase 3 "collaborate" increment; full student program-authoring (`programs.created_by`/`status`, student-write RLS, offline INSERT) stays deferred. `adopt_skip` shares that predicate word for word, so what its dry run counts is what its DELETE removes, and none of it is held by a delete guard: the function never raises on a slot the athlete has touched, it leaves it out.
- **A set_log has three outcome states: pending, done, failed.** `done` and `failed` are mutually exclusive (DB CHECK `set_logs_done_xor_failed`). `useToggleSetDone` and `useSetFailed` each clear the opposite flag in the same patch so a swipe between outcomes never trips the constraint. A failed set may not carry an `rpe` value either (DB CHECK `set_logs_no_rpe_when_failed`); `useSetFailed` nulls `rpe` in the same patch so a student who rated a set then later marked it failed doesn't leave an orphan rating. UI: on mobile, [SetRow.jsx](../src/components/student/SetRow.jsx) commits a swipe right-to-left as done and left-to-right as failed (commit threshold 64px, gated on horizontal-dominant motion so vertical scroll still wins); tapping the indicator cycles `neutral → done → failed → neutral` so a single button reaches every state without swiping. The done→failed step is one write — `patchForFailed(true)` clears `done` in the same UPDATE, so the DB CHECK never sees an intermediate both-true row. Failed sets disable the RPE input (rating a set you didn't finish isn't meaningful). On the done transition the RPE selector auto-expands so the student can rate without an extra tap; failed sets never auto-expand because RPE is locked. Stats in [useStudentProgressStats.js](../src/hooks/useStudentProgressStats.js) only count true `done`; group auto-progression in [SessionView.jsx](../src/components/student/SessionView.jsx) treats a set as **resolved** iff `skipped OR failed OR (done AND rpe != null) OR its slot has a skip deviation` (`isLogResolved`) — a done-without-RPE set keeps the group open so the auto-expanded RPE panel survives long enough for the student to record a value; failed and skipped bypass (no RPE there), and logs under a skip-deviated exercise resolve wholesale because SlotGroupCard only hides them. The progress BAR reuses the same predicate with one divergence: it also counts `done` without an RPE (`l.done || isLogResolved(...)`). Keep the two in sync via `isLogResolved` — hand-inlining the disjunction is how skipped sets once pinned the accordion and capped progress below 100% for every deviated session.
- **A set the athlete has logged is read-only for the coach: never deleted, and its targets never rewritten.** "Logged" is ONE predicate, `isLoggedSet` in [lib/loggedSets.js](../src/lib/loggedSets.js): `done`, `failed`, `skipped`, or a non-null `rpe`, `actual_reps` or `actual_weight_kg`. It is the predicate of the `block_*_delete_with_logged_sets` triggers, and the file also holds its two query forms (`LOGGED_SET_OR_FILTER`, `onlyPendingSets`) so that no hook writes its own. A set that carries a `set_log_videos` row is protected the same way (`isProtectedSet`). In [useSession.js](../src/hooks/useSession.js) the three paths that delete rows — a lower set count (`useUpdateSlot` → `reconcileSetLogCount`), `useRemoveSet` and `useDeleteSlot` — call `readSlotLogs` and throw `loggedSetsError()` **before their first write**: `useUpdateSlot` writes `exercise_slots.sets` ahead of the delete, so a refusal that came after it would leave a slot whose count no longer matches its rows. `reconcileSetLogCount` reads again right before the delete, because the athlete can tick a set in between. The three target writes go through `onlyPendingSets`, and a write that matches no row is not an error: the database keeps a logged row's targets without raising, and the client makes the same choice. Two things to keep when editing this: **the error's message must contain "logged set"** — that substring is how `lib/mutationErrors.js` picks `errors.hasLoggedTraining`, for the client's refusal and for the database's alike — and **`useSession`'s embedded `set_logs` must select `LOGGED_SET_COLUMNS`**, because the editor renders its locks from that projection: a flag missing there is a logged set shown as editable.

## Rest timer

- **Rest timer is an app-wide singleton with one rendering site.** [hooks/useRestTimer.js](../src/hooks/useRestTimer.js) holds one `{ logId, endsAt }` in module-scope and exposes it via `useSyncExternalStore`. Validating a new set calls `startRestTimer(logId, seconds)` which **replaces** the previous timer. Remaining seconds are derived from `endsAt - Date.now()` (timestamp-based, not a tick counter), and the hook listens to `visibilitychange` + `focus` so the timer stays correct after the tab is backgrounded or the phone is locked. `clearRestTimer(logId)` is a no-op unless the active timer matches — undoing a stale set never kills the current rest. Rendering lives in **one** place: [RestTimerBanner.jsx](../src/components/student/RestTimerBanner.jsx) — a compact pill mounted in the right slot of `SessionView`'s top bar (the slot opposite the back button) — so the indicator survives exercise-card transitions without pushing scroll content down. SetRow only writes to the singleton on done/undone transitions; it never reads or renders remaining time. The pill shows `Rest m:ss` while running, flashes "Rest done" on expiry, and auto-hides ~5s later.
- **Out-of-band rest-timer effects ride the singleton via two hooks, mounted in `SessionView` only.** [hooks/useRestTimerEffects.js](../src/hooks/useRestTimerEffects.js) acquires `navigator.wakeLock('screen')` while a timer is active (re-acquires on `visibilitychange → visible` because the browser auto-releases on hide), schedules a synthesized WebAudio beep + `navigator.vibrate` at `endsAt`, and mirrors `Rest m:ss · <title>` into `document.title` while the page is hidden so app-switcher glances show the countdown. The AudioContext is created/resumed on the first `pointerdown` so iOS lets it play unattended at expiry. [hooks/useRestTimerPush.js](../src/hooks/useRestTimerPush.js) is the Web Push bridge — see the next section. Neither hook reads or renders remaining time; they only react to `endsAt`/`logId` changes.

## Web Push (rest-timer "Rest done" lock-screen notification)

- **Live Activities / Dynamic Island are native-iOS-only.** PWA fallback is a Web Push notification fired at `endsAt`. Two tables back it: `push_subscriptions` (per-device subscription owned by the user; full CRUD via RLS keyed on `user_id = auth.uid()`, and `claim_push_subscription` to take a device over from the account that used it before — only with the keys stored with it) and `scheduled_pushes` (one row per pending notification with `fire_at`, `payload`, `status`, `canceled_at`, `sent_at`). Both were added in [2026_05_11_push_notifications.sql](../supabase/migrations/2026_05_11_push_notifications.sql); no triggers, RLS is the only client guardrail. The Edge Function uses the service role and double-checks `user_id` on every row it reads.
- **Custom service worker, not generated.** `vite-plugin-pwa` runs in `injectManifest` mode against [src/sw.js](../src/sw.js); the generated SW is gone. The custom SW still precaches the app shell + Google Fonts via workbox (so offline behaviour is unchanged) and adds two listeners: `push` shows the notification (using `tag` to dedupe stale notifications) and `notificationclick` focuses or opens the deep-link in `data.url`. Workbox is pulled in transitively by `vite-plugin-pwa`; don't add it to `package.json` explicitly.
- **Two Edge Functions handle delivery, split by call shape.** [dispatch-rest-push](../supabase/functions/dispatch-rest-push/index.ts) is **user-invoked** — the client posts `{ scheduleId }` with its own JWT, the function auths the caller, loads the `scheduled_pushes` row with the service role, sleeps until `fire_at`, re-reads to honor a late `canceled_at`, then fans out. [send-push](../supabase/functions/send-push/index.ts) is **internal-only** — it requires `Authorization: Bearer <INTERNAL_BEARER>`, a secret of its own that is not the service-role key, and is called by the notification triggers via pg_net. It takes `{ user_id, payload }` and immediately fans out. Both share the web-push + VAPID stack; 404/410 from the push service drops the dead subscription in either function.
- **Supabase Vault feeds the triggers; the function checks `INTERNAL_BEARER`.** Every notification trigger reads `app_functions_url` and `app_service_role_key` from `vault.decrypted_secrets` and sends the second as `Authorization: Bearer <value>` to send-push, which compares it with its `INTERNAL_BEARER` secret (set with `supabase secrets set`). **The two must hold the same value**, and that value is not the service-role key, whatever the vault name says: it is a random string made for this purpose, because whoever has it can push any text and any link to any user. We don't reuse Supabase's auto-injected `SUPABASE_SERVICE_ROLE_KEY` for the check either: newer projects get an `sb_secret_*` key whose full value can't be read back outside the dashboard, so the two ends would drift. Without the vault secrets the trigger's push block silently no-ops and the in-app `notifications` row still gets written — so the feature degrades cleanly on dev environments. `ALTER DATABASE postgres SET app.*` is denied on Supabase's managed Postgres — don't reach for GUCs. The vault's copy is changed with `vault.update_secret(id, '<new>')`, never with `UPDATE vault.secrets`: the owner's role may not write that table, and the value is stored encrypted. Rotation is the owner's, by hand: `docs/runbook/30-edge-functions.md`, section 4, whose statements `supabase/tests/push-secrets.test.js` reads off the page and runs.
- **`supabase/config.toml` says, for every Edge Function, whether the gateway asks for a user JWT.** `verify_jwt = false` for send-push (its caller is the database, which has no user JWT), `true` for dispatch-rest-push. The deploy is a plain `supabase functions deploy <name> --use-api`; `--no-verify-jwt` is never passed by hand, because the flag overrides the file. Without the file a deploy that forgets the flag puts the gateway's 401 in front of send-push, and every push of the app stops with no error anywhere: the triggers never read the answer. `supabase/functions/deploy.test.js` fails when a function directory has no `[functions.<name>]` table, when `verify_jwt` is not written out, or when the flags are not the ones in production. The file carries nothing else (`src/test/authConfig.test.js`), and `supabase config push` stays forbidden.
- **A function the gateway does not guard opens with `admitInternalRequest`, and nothing runs for a caller it refuses.** `supabase/functions/_shared/auth.js` is the whole gate: `POST` only (a preflight gets a 405 and no `Access-Control-*` header, so a browser cannot call the function), the bearer compared with `timingSafeEqual` (never `===`, whose duration tells how long the matching prefix is), a body of `MAX_BODY_BYTES` at most, counted while it is read, and a JSON object. An unset secret refuses everyone with a 500 — `"Bearer undefined"` must never open anything. A refusal is plain text that starts with the function's name (`send-push: unauthorized`): the check of the runbook tells the function's refusal from the gateway's by that text, so do not reword it without the page. Do not add CORS headers to an internal function, and do not read the body before the bearer is judged.
- **What an Edge Function decides lives in `supabase/functions/_shared/*.js`; `index.ts` is an adapter.** A shared module uses web standards only (`Request`, `Response`, streams) — no `Deno.*`, no `jsr:` or `npm:` import — and takes its dependencies as arguments, so vitest runs it under Node (`// @vitest-environment node`). Deno is not installed where the tests run. The adapter reads the environment and wires things together, and is tested too: `supabase/functions/_test/harness.js` (`loadFunction`) imports an `index.ts` with a stand-in `Deno` global and its remote imports replaced, and returns the handler it passed to `Deno.serve`. A shared module is imported by a relative path with its extension (`'../_shared/auth.js'`): `supabase functions deploy --use-api` uploads the files it finds by matching the `import` lines with a regular expression, comments included, and `supabase/functions/deploy.test.js` runs that expression over every function to see that it finds each file and nothing else.
- **Nothing in the repository deploys a function or sets a secret.** The owner does, following `docs/runbook/30-edge-functions.md`. The check that page gives for after a deploy is read off the page and run by `supabase/functions/runbook.test.js` against `send-push/index.ts` itself, behind a real port, and against what a wrong deploy answers; it sends the secret only to something that has first answered as send-push.
- **Delays > 350s are refused.** The Supabase Edge Function wall-time limit is 400s; both client (`useRestTimerPush`) and server clamp at 350s with a 50s buffer. Typical rest periods (30–300s) are well within. Rests longer than that get no push — only the in-app beep + wake-lock.
- **VAPID keys are environment-scoped.** Public key ships to the client at build time via `VITE_VAPID_PUBLIC_KEY` (`.env`). Private key + a `mailto:` subject live in Supabase function secrets (`VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). Generate once with `npx web-push generate-vapid-keys --json` and set via `supabase secrets set ...`. If `VITE_VAPID_PUBLIC_KEY` is empty, `isPushSupported()` reports false and the Profile toggle renders the "not supported" copy instead of attempting to subscribe.
- **iOS support requires the PWA be installed.** Web Push on iOS Safari is gated on iOS 16.4+ AND the user adding the app to the Home Screen. We don't try to detect installation explicitly — `PushManager.subscribe` will throw and the toggle surfaces the error. Don't bypass `userVisibleOnly: true` (Apple rejects silent pushes).

## RLS / DB conventions

- **RLS is strict.** New tables need both student- and coach-side policies walking session → profile via `student_profile_for_session()` / `coach_profile_for_session()` helpers in `schema.sql`. A helper a policy calls must be executable by `authenticated`: a new one joins the `FUNCTION PRIVILEGES` block at the end of `schema.sql` and the `HELPERS` list of `supabase/tests/function-acl.test.js`. A database change is a migration in the format of `supabase/migrations/README.md` *and* the same change merged into `schema.sql`. A new table enables row-level security in the migration that creates it and is defined above the `TABLE PRIVILEGES` block of `schema.sql`; `supabase/tests/table-acl.test.js` fails on one that has none.
- **A coach-wide read names the coach; RLS is not the tenant filter.** RLS answers "what may this account read", and an account may read the rows it coaches *and* the rows in which it is the athlete: `students` has both SELECT policies, the athlete's own `programs` and `session_confirmations` follow, and `exercise_library` is readable by the athletes of its owner. For a coach who is also somebody's athlete — an account promoted to coach that keeps its `students` row, or a forged link — the two sets differ, and an unfiltered read puts that coach in their own roster with their own block, and another coach's exercises in their pickers. So [`useStudents`](../src/hooks/useStudents.js) filters `coach_id = user.id`; [`useCoachDashboardPrograms`](../src/hooks/useProgram.js) (both of its reads) and [`useAllConfirmations`](../src/hooks/useSessionConfirmation.js) embed `student:students!inner(coach_id)` and filter on it; [`useExerciseLibrary`](../src/hooks/useExerciseLibrary.js) filters `coach_id` when the role is coach. Two things to keep: **a filter on an embedded row only drops the parent row when every embed on its path is `!inner`** — remove one `!inner` and the request still answers 200, with the filter doing nothing, which is why the hook tests assert the select as well as the filter — and **a new read across all of a coach's athletes needs the same filter**. A read that is given one athlete's id is scoped by that id and does not. `useStudents` returns an empty list to an athlete, which is right: `MessageThread` calls it for both roles and reads it only as a coach.
- **`schema.sql` and the migrations must describe the same database, and a test proves it.** `supabase/tests/parity.test.js` loads the frozen production baseline (`supabase/tests/fixtures/prod_baseline_2026_09_30.sql`), applies every `required` and `optional` migration of `supabase/migrations/manifest.json` in order, and compares the catalog with `schema.sql` object by object (`supabase/tests/catalog.js`: functions with their settings and privileges, policies, triggers, columns, constraints, indexes, table privileges, default privileges, enums, publications, comments, seeded rows). A change made to only one of the two turns it red. A table that a SQL file fills is listed in `REFERENCE_DATA` of `catalog.js`, so that its rows are compared one by one: the test refuses rows in any other table, where it could only compare how many there are. The baseline is `schema.sql` as the live review of 2026-09-30 compared it with production; its SHA-256 is pinned, and it is never edited to make the test pass. `contract` migrations are left out of `schema.sql` until they have been applied, so that `schema.sql` keeps describing production.
- **Every migration signs the ledger, and refuses to run twice or out of order.** `app_private.app_migrations (name, applied_at)` holds one row per applied migration, inserted by the migration inside its own transaction and removed by its rollback file. A migration raises `SLM01` when its name is already there and `SLM02` when the migration it requires is not; a rollback raises `SLM03` when there is nothing to roll back and `SLM04` when a later migration still needs what it would remove. A migration that brings a rule raises `SLM05` when rows that are already in the database break it and would keep the hole in use (migration 05: a `students` link whose coach is not a coach): its audit counts them, its runbook page lists and removes them, and the file is run again — it never deletes them itself. `supabase/tests/migration-conventions.test.js` runs every migration through refused-out-of-order → applied → refused twice → rolled back → applied again, and compares the catalog at each step, so a rollback that leaves an object behind fails. It then applies the list once more with the `optional` migrations left out: a `required` or `contract` migration that uses what an optional one made fails there. `schema.sql` inserts the names of the migrations merged into it, so a database installed from it starts with a complete ledger.
- **`app_private` is out of the API's reach, and has no RLS on purpose.** The schema is not in the exposed schemas and `anon`, `authenticated` and `service_role` hold no privilege on it (`supabase/tests/migration-ledger.test.js`). The ledger is not in `public` because a `public` table needs RLS, and a table with RLS and no policy reads as empty to a read-only role, so a check of the ledger before a deploy would read "nothing is applied". Never add `app_private` to the exposed schemas, and never grant an API role `USAGE` on it.
- **`supabase/tests/snapshots/rls-matrix.txt` is the record of who can do what.** `rls-matrix.test.js` measures, for anon, two athletes, their coach, another coach and the service role, how many rows of each table they can read, insert, update and delete, and compares the result with that file. A migration that rewrites policies or grants and means to change nothing must leave it untouched; one that means to change a cell regenerates the file and commits the diff. A cell reads `denied` when the whole statement is refused for want of a privilege — on the table, or on a function one of its policies calls: since migration `2026_10_13_14_table_grants_lockdown.sql` that is every `anon` cell of a table of `public`: without a session there is no privilege on any of them.
- **Nothing in the repository applies SQL to production, and nothing may.** It is applied one checkpoint at a time, following `docs/RUNBOOK.md` and the pages under `docs/runbook/`: a backup, then for each migration its audit, the migration, the audit again, and the ledger at the end — by the owner, or by Claude in a session the owner opens for that checkpoint, on the conditions the index gives ("Who runs a checkpoint"). No script, workflow or test runs a migration against the live project, no agent does as part of a package, and `supabase db push`, `supabase migration up` and `supabase migration repair` are never used: the folder is not a CLI migration history. A command or a query that a runbook page gives is read off the page and run by a test (`supabase/tests/rpc-auth.test.js`, `supabase/tests/function-acl.test.js`, `supabase/tests/auth-accounts.test.js`, `src/test/authConfig.test.js`), and `src/test/runbookIndex.test.js` holds the index to the manifest and to those pages — so a command is changed on its page, and the tests follow the page.
- **`profiles.full_name` is self-editable; `id` and `created_at` are pinned for everyone, `role` for every request that carries a user id.** The `Users update own profile` policy lets a signed-in user UPDATE their own row — every column of it — and the `profiles_pin_immutable_columns` BEFORE UPDATE trigger is what keeps the role out of their hands: when `auth.uid()` is not NULL it puts `role` back, **silently** (the rename in the same payload is saved, no error — read the row, not the row count). "With a user id" is the request, not the role the statement runs as: a `SECURITY DEFINER` function called from the app is still that user and writes no role either. Without a user id — the SQL editor, `supabase db query`, the service-role key — the role is written (migration `2026_10_11_07_profile_rules.sql`, review P20: the pin used to apply to every caller, so the documented promotion answered `UPDATE 1` and did nothing). A request without a session is not such a caller: `anon` has no policy on `profiles` and reaches no row — which is the only thing that holds it, so never give `anon` an UPDATE policy there. If a future Profile feature needs to mutate a new column, the policy already allows it; a new column the user must NOT write (anything role-adjacent) has to be added to that trigger function, or it is theirs. `supabase/tests/profiles.test.js` holds it.
- **A role change never contradicts who coaches whom.** The same trigger refuses, with `23514` and a sentence, to make a coach of an account that is somebody's athlete (`students.profile_id`) and to take the role from a coach who has athletes (`students.coach_id`). It is the rule of `trg_check_students_link` — every link joins a `coach` to a `student` — asked when the other side of it moves; without it the promotion that now works would be a way to write exactly the rows that gate refuses. Raised, not silent: the caller is the owner. Consequences: the role comes first and the links after it (a fixture promotes, then links — `createUser({ role: 'coach' })` in `supabase/tests/harness.js`); an athlete with logged training cannot become a coach on the same account (their link cannot be deleted), a coach gets an account of their own; a coach is made an athlete again only once their athletes have moved. KNOWN residual gap: the two triggers read each other's table without a lock, so a link written and a role changed in two transactions at the very same moment can pass each other. Both are owner-only writes.
- **A new account is always `role='student'`, and always has a name.** `handle_new_user` (the `on_auth_user_created` trigger on `auth.users`) never reads the role from the sign-up metadata — the anon key is public, so that metadata is attacker-controlled (2026_07_12) — and stores a `full_name` that is never empty (migration `2026_10_11_07_profile_rules.sql`, review B10): `raw_user_meta_data->>'full_name'` without the white space around it, else the part of the e-mail address before the `@`, else `'Athlete'`. An account made with *Add user* in the dashboard carries no name at all, and an empty one passes every `COALESCE(name, 'Your athlete')` of the push triggers: the coach read " completed Session 3". The function runs inside the INSERT that creates the account, so it **must never raise and never produce NULL** (`profiles.full_name` is NOT NULL), and it **must stay `SECURITY DEFINER`** (the INSERT is GoTrue's, which holds nothing on `public`): either mistake closes account creation for everyone ("Database error saving new user"). The migration does not write the trigger on `auth.users` — the table is the platform's — and refuses to run where no trigger calls the function. KNOWN residual gaps: (1) the profiles created before the migration keep their empty name until somebody types one (`docs/runbook/migrations/07-profile-rules.md`, "Accounts without a name"; line 10 of its audit counts them); (2) nothing stops a user from saving a name of blanks through the API — the app does not send one — and the push triggers still read `COALESCE(name, …)`.
- **A coach is made by the owner of the database, with one statement, and by nobody else.** `update public.profiles set role = 'coach' …` from the SQL editor (the statement, by e-mail address, and what it answers: `docs/runbook/migrations/07-profile-rules.md`, "Making a coach"). The app has no screen for it and no API path reaches it: there is no RPC for it on purpose — a function that changes a role is called without a user id or changes nothing. Each coach is a tenant of their own: a new coach starts with an empty roster and an empty library, and sees nothing of another coach's.
- **`students` is the root of authorization, and no signed-in user creates, deletes or moves a link.** Every "Coaches …" policy asks this table who coaches whom, so a row that should not exist gives its `coach_id` the reach of a coach over its `profile_id`. The table has NO `INSERT` policy and NO `DELETE` policy (migration `2026_10_11_05_students_role_gate.sql`, review P7 / L2): a link is made and removed by the owner of the database in the SQL editor, or with the service-role key. `Coaches update their students` stays, for the coach of the row who is a coach, with a `WITH CHECK` — for the columns that are not the link. `trg_check_students_link` (`check_students_link()`, `BEFORE INSERT OR UPDATE`) holds what a row may say **for every writer, `postgres` and the service role included**: `coach_id` is a profile with the role `coach`, `profile_id` one with the role `student`, and they are two profiles (`23514`); with a user id, `id`, `profile_id` and `coach_id` do not change at all (`42501`, `the coach-athlete link … cannot be changed from the app`), whatever role the statement runs as — so a function that moves an athlete is not granted to `authenticated`. A row whose link does not move is not judged again: a column next to it can always be written. Never add a write policy on `students` that reads `coach_id = auth.uid()` alone — any account can put its own id there, which is how an athlete made itself the coach of its coach. The app only reads the table. KNOWN residual gap: the trigger judges a link when it is written, not when a role changes — promoting a profile that is somebody's athlete, or demoting a coach who has athletes, leaves a link the gate would refuse; `profiles.role` is written by the owner only. `supabase/tests/students-gate.test.js` holds all of it.

It refuses, before any write: `program_not_found` (no such program that the caller can read — somebody else's athlete and a wrong id are the same answer), `not authorized` (`42501`: the caller reads it and may not write it — its athlete), `program_is_draft`, `program_in_trash`.
  - **`reorder_sessions(p_week_id, p_ids)`** and **`reorder_weeks(p_program_id, p_ids)`** take EVERY child of the parent, once each, in the order wanted — archived sessions included, because the unique key counts them — and return nothing. Afterwards `sort_order` is 0 to n-1 and `week_number` 1 to n, whatever the numbers were: a phase that an interrupted reorder left at 100000 and more is put right by the same call. A list that is not exactly the children is refused with `reorder_ids_mismatch` (its `details` count what is missing, foreign, or there twice) — which is what a page loaded before a session was added, moved or deleted sends: refetch, then try again. Also `week_not_found` / `program_not_found` and `not authorized` as above. A list that is the order already writes nothing.
  - **The refusals are `P0001` with that fixed word as the message** (HTTP 400), except `not authorized`, which is `42501` and reaches the toast as `errors.notAllowed`; the others fall to `errors.generic` in `mutationErrorKey` until a hook maps them.
  - **Two calls for the same athlete, phase or block wait for each other** (the parent is locked first), so the last one sent is the one that stays — the database needs no per-week scope from the client to stay consistent; a scope only keeps the optimistic cache in step.
  - **`useReorderPrograms` has no function**: `programs.sort_order` has no unique key, so its two passes cannot collide.
- **Duplicating a session, a phase or a block, and copying sessions to another phase, each have a function that makes the whole copy or none — and the hooks' own requests do not.** Migration `2026_10_13_12_copy_rpcs.sql` (the database's half of review P52) adds four `SECURITY INVOKER` functions, executable by a signed-in user: what is copied is what the caller can read, where it goes is where the caller can write, so a coach copies for their own athletes and from one of them to another, and nobody else does. `useDuplicateSession`, `useCopySessions`, `useDuplicateWeek` and `useDuplicateProgram` do not call them yet: each still sends one request per row or per table (thirty to forty for a block), each request a transaction of its own, so a request that is lost leaves a session with no exercise, or exercises with no set, in the block the athlete trains. The contract:
  - **`duplicate_session(p_session_id, p_title_suffix default ' (copy)')`** puts the copy RIGHT AFTER its source — the sessions that follow move down by one, archived ones included — and returns `{ session_id, week_id, sort_order, title, slots, set_logs, slots_left_out }`. A session without a title is called `Session` before the suffix; with `''` or `null` the title is copied as it is. The copy is never archived.
  - **`copy_sessions(p_session_ids, p_dest_week_id)`** makes one copy per entry of the list, in the order of the list, after every session the phase holds (archived ones included), with the titles as they are and none archived, and returns `{ session_ids, week_id, slots, set_logs, slots_left_out }` — `session_ids` in the order of the list. An entry the caller cannot read refuses the whole list (`session_not_found`); an empty list copies nothing.
  - **`duplicate_week(p_week_id, p_dest_program_id default null, p_label_suffix default ' (copy)')`** adds the phase as the LAST phase of its program — or of `p_dest_program_id`, which is how "copy this phase to…" reaches another block or another athlete — with its sessions in their order, numbered from 0, the archived ones still archived. A phase without a name gives a copy without one. Returns `{ week_id, program_id, week_number, label, sessions, slots, set_logs, slots_left_out }`.
  - **`duplicate_program(p_program_id, p_target_student_id default null, p_name_suffix default ' (copy)')`** makes a block for the athlete of the source, or for `p_target_student_id` — the id of a row of `students`, what `programs.student_id` holds, not a profile. The copy is `approved`, **not active**, out of the trash and the coach's (`created_by` NULL) whatever its source is (a draft, a block in the trash, the block being trained), last in the athlete's list, its phases numbered from 1 with their names as they are. Returns `{ program_id, student_id, name, sort_order, weeks, sessions, slots, set_logs, slots_left_out }`.
  - **The answer is an object, and the id is in it under a fixed key.** Keys are added, never renamed. The arguments that have a default may be left out of the call.
  - **The refusals are `P0001` with a fixed word as the message** (HTTP 400): `session_not_found`, `week_not_found`, `program_not_found`, `student_not_found` (nothing with this id that the caller can read — somebody else's athlete and a wrong id are the same answer) and `copy_source_changed` (what was to be copied was deleted or moved while the call waited: refetch, then try again). `not authorized` is `42501` (the caller reads the place and may not write it — the athlete) and reaches the toast as `errors.notAllowed`; the others fall to `errors.generic` in `mutationErrorKey` until a hook maps them. Nothing was written in any of those cases.
  - **Two copies into one phase, one program or one athlete's list wait for each other**, and so do a copy and a reorder of the same phase: the parent is locked first, in the order `reorder_sessions` and `reorder_weeks` take it.
- **A copy is the prescription, and nothing of what was trained.** Copied: a session's title and recommended weekday; everything the coach wrote on an exercise (`exercise_id`, `sets`, the slot's own numbers, `sort_order`, `superset_group`, `notes`, `record_video_set_numbers`); the number and the four `target_*` of each prescribed set. Not copied: `scheduled_date`, `reviewed_at`, `performed_at`; `done`, `failed`, `skipped`, `rpe`, `weight_kg`, `actual_*`, `logged_at`, `failed_at`; the sets the athlete added (`is_student_added`); `slot_comments`, `slot_deviations`, videos, confirmations. `archived_at` is carried by `duplicate_week` and `duplicate_program` only. A set of a draft does not exist before `approve_program`, so the copy of a draft holds exercises without sets: the athlete's app adds them when the session is opened (`useEnsureSetLogs`). This is what `useDuplicate.js` copies, column for column — `supabase/tests/copy-rpcs.test.js` holds the two against each other — with two differences: the copy of a session stands right after its source instead of at the end of the phase, and a duplicated phase or block has its sessions numbered from 0 and its phases from 1 whatever the numbers of the source were.
- **`slots_left_out` is not zero when exercises could not be copied, and the app must say so.** A slot takes an exercise of the library of its program's coach (`trg_check_slot_exercise_in_coach_library`). After `transfer_student`, an athlete's older blocks still name the former coach's exercises: a copy of one holds the sessions and the exercises that are in the new coach's library, and `slots_left_out` counts the others — the function does not fail. Without a change of coach it is always `0`. A hook that calls one of the four shows a message when it is not.
- **A column added to `programs`, `weeks`, `sessions`, `exercise_slots` or `set_logs` is listed in `WHAT_A_COPY_IS`** at the top of `supabase/tests/copy-rpcs.test.js` as `copied` or `left`, or the DB suite fails. A copied column is added to the three `INSERT`s between the marks `-- >>> the copy` and `-- <<< the copy`, which are the same lines in the four functions, in the migration that re-creates them and in `schema.sql` (`supabase/migrations/README.md`, "A migration that adds a column to a program, a phase, a session, an exercise slot or a set").
- **The missing sets of a session, and the registration of a device for notifications, each have a function that does it for the account that calls — and the app's own requests do not use them yet.** Migration `2026_10_13_13_ensure_claim_rpcs.sql` (the database's half of review L8, P22 and P15) adds two `SECURITY DEFINER` functions, executable by a signed-in user, each of which asks who calls before it does anything. `useEnsureSetLogs` still reads which sets exist and inserts the others from the exercises in its cache, so a set the coach has removed since comes back (P22); `enablePush` and `reconcilePushSubscription` still upsert `push_subscriptions` under the owner-only policies, so the second account on a shared device is refused — silently by `usePushAutoHeal`, with an error code the toggle has no words for — and the device goes on receiving the first account's notifications (P15). The contract:
  - **`ensure_set_logs(p_session_id)`** returns an `integer`: how many rows of `set_logs` it added, `0` when none was missing. For every exercise of the session it adds every number from 1 to `exercise_slots.sets` that has no row — read in the database at the moment of the call, never sent by the app — not done, with the targets of the exercise (`reps` or `duration_seconds`, `weight_kg`, `rest_seconds`), which is what the editor and `approve_program` write. A row that stands on a number is left alone, an extra set of the athlete included; nothing that exists is touched; a second call adds nothing. It refuses, before any write: `not authorized` (`42501`) when the request carries no user id or the session is not the caller's own — somebody else's session, the session of an athlete the caller coaches and no such session are the same answer; `program_not_active` when the session is the caller's in a program that is not the block being trained (a past block, a draft, a block in the trash); `session_not_writable` when the coach has archived or reviewed it. A confirmed session that is not reviewed yet is still completed.
  - **`claim_push_subscription(p_endpoint, p_p256dh, p_auth, p_user_agent default null)`** returns `{ subscription_id, outcome }`. `outcome` is `created` (nobody held the endpoint: a new row for the caller), `refreshed` (the caller held it: the keys sent are stored, `last_seen_at` is now, and the user agent is replaced unless it is left out or `null`) or `rehomed` (another account held it **with these two keys**: the row keeps its id and is the caller's now — the other account no longer reads it, and receives nothing on that device). It refuses, before any write: `not authorized` (`42501`) without a user id; `subscription_incomplete` when the endpoint or one of the two keys is `null`, empty or blank; `endpoint_keys_mismatch` when another account holds the endpoint and the keys sent are not the ones stored with it. Any signed-in account may call it — an athlete, a coach, an account nobody coaches — as any account may register a device today.
  - **The refusals other than `not authorized` are `P0001` with that fixed word as the message** (HTTP 400) and fall to `errors.generic` in `mutationErrorKey` until a hook maps them; `not authorized` reaches the toast as `errors.notAllowed`. Nothing was written in any of those cases. Keys and outcomes of the answer of `claim_push_subscription` are added, never renamed.
  - **A hook that calls `ensure_set_logs` does not call it for a session it shows as read-only**: the function refuses, and every opening of a past session would log an error. It needs no client-side list of what is missing to be correct — the function decides — only to know whether a call is worth sending.
  - **Two calls at once are harmless**: two `ensure_set_logs` for one session wait for each other's rows and the second answers `0`; two claims of one endpoint are served one after the other, and the second is judged against what the first left.
- **`app.trusted_set_log_insert` is the mark of `ensure_set_logs`, and nothing else may set it.** The function sets it to `'on'` for the transaction around its one `INSERT` and back to `'off'` before it returns. Nothing reads it yet: it is how the contract migration that will turn an athlete's own `INSERT` into an extra set without targets (review L6, Checkpoint Z) tells a prescribed set the function adds from one the athlete inserts by hand — `auth.uid()` is the athlete in both. An API user cannot set it because they run no statement of their own: a function executable by `authenticated` that sets a setting named by its caller would hand every athlete the word. `ensure-claim.test.js` reads the body of the function: one `INSERT`, between the two lines.
- **A push subscription changes hands only with its keys.** `push_subscriptions` holds one row per endpoint, and `auth` is a secret the browser shares with the database — readable by the owner of the row and by the service role only. `claim_push_subscription` moves the row of another account to the caller on that proof and on nothing else; somebody who has learnt an endpoint cannot point it at their account. The four owner-only policies of the table stay: the app deployed before wave 2 writes the table itself.
- **No mutation failure is silent** (2026_07_13). `queryClient`'s `MutationCache.onError` routes every unhandled mutation error through [`lib/mutationErrors.js`](../src/lib/mutationErrors.js) (PG SQLSTATE / constraint-name → i18n key) into a global toast ([`lib/toast.js`](../src/lib/toast.js) + [`ui/ToastHost`](../src/components/ui/ToastHost.jsx) in AppShell). A mutation that renders its OWN inline error opts out with `meta: { skipErrorToast: true }` (the message composers, `useHardDeleteProgram`). Production crashes report to the `client_errors` table via [`lib/errorReporter.js`](../src/lib/errorReporter.js) (window.onerror + unhandledrejection + `ErrorBoundary.componentDidCatch`) — insert-own / coach-read RLS, `role` pinned to the real profile role, `url` redacted of auth-token hashes, skipped entirely when unauthenticated. Coach triage view: a collapsible list at the bottom of the Athletes roster (CoachHome).
- **A SECURITY DEFINER RPC refuses a caller without a user id first, and compares with `IS DISTINCT FROM`.** A definer bypasses RLS, so the line that compares the caller with the owner of the data is the whole gate. Written `IF v_coach_id IS NULL OR v_coach_id <> auth.uid() THEN RAISE`, it lets everyone without a session through: with `auth.uid()` NULL the comparison is NULL, not true, and an `IF` on NULL skips its branch. `adopt_swap`, `adopt_skip`, `decline_promote_request`, `approve_program` and `send_back_program` authorize with `IF auth.uid() IS NULL OR v_coach_id IS DISTINCT FROM auth.uid() THEN RAISE EXCEPTION 'not authorized'` (migration `2026_10_03_02_rpc_auth_null_guard.sql`, review finding P1). Keep that line, as written, whenever one of them is re-created — `CREATE OR REPLACE` replaces the whole body. `supabase/tests/rpc-auth.test.js` calls each of the five as the service role, a token of role `authenticated` with no `sub`, `postgres`, another coach, the athlete, another athlete and an athlete of another coach, and requires `not authorized` and an unchanged database; it also lists the SECURITY DEFINER functions of `public` that are neither triggers nor `STABLE` and fails when one appears that is not in its table of calls. The service role and `postgres` are refused too: neither has a user id. `anon` no longer reaches the body — since migration 03 it may execute no function, and the same test requires `permission denied for function …` for it — but the line in the body stays the gate for every caller that does hold EXECUTE.
- **No function of `public` is executable without a session, and a signed-in user executes an allow-list.** Supabase grants `anon`, `authenticated` and `service_role` EXECUTE, by name, on every function `postgres` creates in `public`, on top of the EXECUTE PostgreSQL gives `PUBLIC`; `REVOKE … FROM public` next to a function removes one of those four grants. Migration `2026_10_11_03_function_grants_lockdown.sql` takes everything back from `PUBLIC`, `anon` and `authenticated` and grants `authenticated` an explicit list: the helpers the policies call and the RPCs the app calls. A policy is evaluated with the privileges of the user who queries the table, so **a helper that is missing from the list fails every query on every table whose policies name it** (`permission denied for function …`) — so does a function in a column default, a check constraint, a view or an index expression. A trigger function gets no grant: a trigger fires whatever the privileges of the user whose statement fires it (GoTrue fires `handle_new_user` as `supabase_auth_admin`, which may not execute it). `service_role` and the owner keep everything. In `schema.sql` the list is the `FUNCTION PRIVILEGES` block at the end of the file, the only place that grants or revokes on a function; it stays below every function of the file. `supabase/tests/function-acl.test.js` holds all of it against the catalog — anon and `PUBLIC` execute nothing, `authenticated` exactly the lists `HELPERS` and `RPCS` of that file, every function a policy depends on (read from `pg_depend`) is a helper of the list, every name `src/` passes to `supabase.rpc()` is an RPC of the list — and a function that joins `public` fails it until it is listed or is a trigger function.
- **A function `postgres` creates starts closed.** Since the same migration, the default privileges of `postgres` give a new function no EXECUTE for `PUBLIC` in any schema (a global default: the `PUBLIC` grant is PostgreSQL's built-in one, and a per-schema default can only add to it) and none for `anon` or `authenticated` in `public`. A function created by a migration, or by hand in the SQL editor, is executable by `postgres` and `service_role` until a `GRANT` names someone else. A migration that adds a function says so next to it (`REVOKE ALL ON FUNCTION … FROM PUBLIC, anon, authenticated`, then `GRANT EXECUTE … TO authenticated` when a policy or the app calls it) — rules in `supabase/migrations/README.md`, "A migration that creates or re-creates a function". The defaults of `supabase_admin`, the platform's own role, are untouched: `postgres` cannot change them, and nothing of the app is created by that role.
- **Every function runs with `search_path = public, pg_temp`.** All functions of `public` carry `SET search_path = public, pg_temp` and write the names in their bodies with a schema (`public.sessions`, `auth.uid()`, `net.http_post`, `vault.decrypted_secrets`). Without the clause a `SECURITY DEFINER` function resolves names with the caller's path; with `public` alone, a temporary object of the caller still comes first. `CREATE OR REPLACE` **drops a `SET` clause the new text does not repeat** (and keeps the grants): repeat it whenever a function is re-created, in the migration and in `schema.sql`. `function-acl.test.js` fails on any function of `public` whose setting is not exactly that one.
- **No table of `public` is reachable without a session, and a signed-in user holds the four privileges about rows — nothing else.** Supabase grants `anon`, `authenticated` and `service_role` every privilege, by name, on every table `postgres` creates in `public`: row-level security was the only gate, and it is a gate for rows. `TRUNCATE` is not subject to it and fires none of the `DELETE` triggers that guard logged training — `TRUNCATE public.profiles CASCADE`, run as `anon` or as any signed-in user, emptied every table of the app. Migration `2026_10_13_14_table_grants_lockdown.sql` (review L24) takes everything on every table, view and sequence of `public` away from `anon` and `PUBLIC`, and leaves `authenticated` `SELECT`, `INSERT`, `UPDATE` and `DELETE` on a table — the four the policies judge — and `USAGE` on a sequence; `TRUNCATE`, `REFERENCES`, `TRIGGER` and `MAINTAIN` are the owner's and the service role's. In `schema.sql` this is the `TABLE PRIVILEGES` block at the end of the file, the only place that grants or revokes on a table of `public`; it stays below every table, view and sequence of the file. `supabase/tests/table-acl.test.js` holds it against the catalog, for every table there is. A `SECURITY INVOKER` function runs with these rights: one that needs more than rows — a `TRUNCATE`, a `REINDEX` — fails for every signed-in user, and is written `SECURITY DEFINER` with its own check of who calls instead. A row lock (`SELECT … FOR UPDATE`, which the functions of migrations 11 and 12 take) asks for `UPDATE`, which stays.
- **Every table of `public` has row-level security, and a table `postgres` creates starts with the privileges of the others.** The default privileges of `postgres` in `public` give a new table nothing for `anon` and the four privileges for `authenticated` — so a table created without `ALTER TABLE … ENABLE ROW LEVEL SECURITY`, by a migration or by hand in the SQL editor, is read and written in full by every signed-in account. `table-acl.test.js` fails on a table without row-level security, and on a view that is not `WITH (security_invoker = true)`: a view reads its tables with the rights of its owner, whom row-level security does not hold, and shows every row to whoever may read it. A migration that adds a table follows "A migration that creates a table, a view or a sequence" in `supabase/migrations/README.md`. The defaults of `supabase_admin`, the platform's own role, are untouched — `postgres` cannot change them.
- **Nothing is read or written without a session.** A request that carries only the anon key is refused by every table of `public` — `permission denied for table …`, `42501` — before a policy is evaluated, and by every function (migration 03). The app sends none: the login page talks to `/auth/v1` only, and the one way there is a session that expired and could not be renewed, where `mutationErrorKey` shows the refusal as `errors.notAllowed` and a read fails instead of resolving to no rows. A feature that must serve something without a session cannot do it with a policy alone: it needs a deliberate `GRANT … TO anon` on one table or one function, which `table-acl.test.js` and `function-acl.test.js` refuse until the rule is changed there, with the reason.

## Messaging / notifications

- **Notifications are SECURITY DEFINER trigger-driven.** The `notifications` table has SELECT/UPDATE policies for the recipient only — there is **no client INSERT policy**. Events get into the table exclusively via DB triggers (`notify_coach_on_session_confirm` on `session_confirmations`; `notify_student_on_session_feedback` on `messages` when `session_id IS NOT NULL`). Adding a new event type = new trigger + new client `describeNotification` branch + new i18n key. The bell lives inside `ui/UserMenu` so every top-level page gets it for free; realtime updates are wired through `useNotificationsRealtime` mounted once in `AppShell`. Like messages, the table is in `supabase_realtime` with `REPLICA IDENTITY FULL`.
- **A notification about something the athlete can take back is removed with it, while it is unread.** Two AFTER DELETE triggers of migration `2026_10_13_09_review_lifecycle.sql` (review P57, L12): `trg_retract_session_completed_notification` on `session_confirmations` deletes the unread `session_completed` rows of the session (matched on `payload->>'session_id'` and `payload->>'confirmation_id'`), and `trg_retract_slot_deviation_notifications` on `slot_deviations` deletes the unread `session_deviation` and `promote_requested` rows of the exercise slot (`payload->>'slot_id'`). So confirm, undo, confirm leaves one line in the coach's bell, and a skip that is undone leaves none. A row the coach has read stays: it is their history, and its link may lead to a review page that says the session is not confirmed. Both fire on a cascade too — a session or an exercise that is deleted. They are the only DELETE on `notifications`: there is still no client policy for it, and `useNotificationsRealtime` already listens to every event. **A new kind of notification about a row that can be taken back names that row in its payload and gets its own AFTER DELETE trigger**; without it the bell keeps a line about something that no longer exists. The push of a confirmation carries the tag `session-confirm-<session id>`: with the id of the confirmation, which is a new one after each undo, the pushes of one session stacked on the lock screen — keep the tag when `notify_coach_on_session_confirm` is re-created.
- **Ordinary chat messages fan out a Web Push too — but never a bell row** (2026_07_12). A second AFTER INSERT trigger on `messages`, `notify_recipient_on_chat_message`, fires only when `session_id IS NULL` (feedback rows keep their dedicated trigger below). It deliberately inserts NO `notifications` row — the Messages-tab unread badge is chat's in-app surface, and a bell entry would double-count. Payload quirks: tag `chat-<sender_id>` collapses a burst from one sender into one lock-screen entry; the deep-link surface and the no-name title fallback both derive from the SENDER's role (recipient surface = the opposite role). Same Vault secrets + best-effort EXCEPTION wrapper as the feedback push; degrades to nothing when unset.
- **A student-surface write is either offline-keyed or explicitly gated — [offlineSafety.test.js](../src/lib/offlineSafety.test.js) enforces it.** The scan reads every `export function use…` in the student-write hook files and fails the build unless each mutation either carries a `mutationKey` (so a hydrated post-reload resume can find its `mutationFn`) or is named in `ONLINE_ONLY` with a reason. Two things to keep true when editing it: **add new student-write hook FILES to `FILES`** (useGoals, useBodyweight and useSetVideo were outside the scan for months), and remember it detects a write hook by `useMutation` *or* a `mutationFn` — a hook that delegates to a local factory would otherwise be skipped as a read hook and pass vacuously. Every `ONLINE_ONLY` entry is a promise that the UI disables the affordance offline; keep that promise.
- **Messaging composers are online-only, by explicit gate.** `useSendMessage` (and `useMarkSessionReviewed`) are NOT in the offline mutation registry, so an offline submit would pause on "Sending…" forever and a reload would silently drop it (no registered mutationFn to resume). Both [MessageComposer.jsx](../src/components/messaging/MessageComposer.jsx) and the coach's [SessionFeedbackComposer.jsx](../src/components/coach/SessionFeedbackComposer.jsx) gate on `useOnlineStatus()` and show an offline hint; the draft stays in the box. If you add a new send surface, add the gate (or do the real fix: register the mutation with a client-generated id).
- **Feedback notifications also fan out a Web Push.** Inside `notify_student_on_session_feedback`, after the in-app `notifications` INSERT, the trigger calls `net.http_post` (pg_net) to the [`send-push`](../supabase/functions/send-push/index.ts) Edge Function. send-push fans the payload out to every `push_subscriptions` row for the recipient — same web-push + VAPID stack used for the rest timer. The trigger pulls `app_functions_url` + `app_service_role_key` from Supabase Vault; if either is unset or the HTTP call fails, the trigger logs a warning and continues — the in-app bell path is never blocked. Push delivery is one-shot (no `scheduled_pushes` row) because the event fires immediately; the unique partial index on `messages.session_id` already keeps it idempotent. The payload's `data.url` deep-links to `/sl_app/#/student/session/<id>` so `notificationclick` lands on the structured feedback card in `SessionView`.

The coach enters a thread either from `/coach/messages` or via the **Message** action at the top of the athlete page (`StudentOverview`).
- **Student surfaces feedback in two places.** [SessionView.jsx](../src/components/student/SessionView.jsx) reads `useSessionFeedback(sessionId)` and renders the body inline as a "Coach's feedback" card between the progress bar and slot groups when a feedback row exists — this is the structured destination the `SessionReferenceCard` deep-link from Messages lands on. [SessionCard.jsx](../src/components/student/SessionCard.jsx) shows a small "feedback" pill in its trailing block when `hasFeedback` is true; [StudentTraining.jsx](../src/components/student/StudentTraining.jsx) feeds it from `useMyFeedbackSessionIds()` (a single batched query for the student-recipient feedback rows). New incoming feedback invalidates the `[messages]` subtree via `useMessagesRealtime`, so the pill appears without a manual refresh.
- **Messaging is realtime + RLS-scoped.** `messages` rows have `sender_id`, `recipient_id` (both `profiles.id`), and an optional `session_id` (FK to `sessions`, ON DELETE SET NULL) used by the coach-feedback flow. RLS lets either party SELECT, only the sender INSERT (and only when the pair is coach-student via `profiles_are_coach_student()`); when `session_id` is non-null the policy also requires sender = `coach_profile_for_session(session_id)` and recipient = `student_profile_for_session(session_id)` so the link can't be forged. Only the recipient UPDATEs — the `BEFORE UPDATE` trigger pins every column except `read_at` (including `session_id`). The sender DELETEs their own ordinary chat messages; the policy gates DELETE on `session_id IS NULL` so coach feedback rows (which set `sessions.reviewed_at` via `notify_student_on_session_feedback`) can't be removed and the one-shot review invariant holds. The table is in `supabase_realtime` with `REPLICA IDENTITY FULL`; [hooks/useMessages.js](../src/hooks/useMessages.js) opens **one** channel from `AppShell` (`useMessagesRealtime`) and invalidates the `[messages]` subtree on INSERT/UPDATE/DELETE. `useSessionRefsForMessages` does a single batched fetch of titles/dates for the unique `session_id`s referenced by the visible thread. The Messages nav tab carries an unread-count badge fed by `useUnreadMessageCount`. Conversations roll-up is a client-side fold over recent rows — fine at coach scale, swap for an RPC if the table grows.

## Coach session review

- **Coach session review is one-shot per session.** A session can be reviewed at most once — whether the coach left feedback or not. State lives on `sessions.reviewed_at timestamptz`. Two write paths set it: (1) the `notify_student_on_session_feedback` trigger stamps `reviewed_at = NEW.created_at` when a feedback message is inserted (idempotent — `WHERE reviewed_at IS NULL`), and (2) [`useMarkSessionReviewed`](../src/hooks/useSession.js) UPDATEs the row directly when the coach clicks "Finish without feedback". The top-of-page back arrow does NOT mark reviewed — it's a "leave and come back" gesture; only Send-feedback and Finish-without-feedback are completion gestures. [SessionReview.jsx](../src/components/coach/SessionReview.jsx) renders four branches at its feedback step: [SessionFeedbackSent.jsx](../src/components/coach/SessionFeedbackSent.jsx) (feedback exists), [SessionReviewedNoFeedback.jsx](../src/components/coach/SessionReviewedNoFeedback.jsx) (`reviewed_at` set but no feedback), [SessionFeedbackComposer.jsx](../src/components/coach/SessionFeedbackComposer.jsx) (not yet reviewed, and confirmed), or [SessionReviewNotConfirmed.jsx](../src/components/coach/SessionReviewNotConfirmed.jsx) (not yet reviewed, and no confirmation to review — see the next entry). [SessionsFeed.jsx](../src/components/coach/SessionsFeed.jsx) shows a green "Reviewed" pill on cards whose session has `reviewed_at` set; [`useAllConfirmations`](../src/hooks/useSessionConfirmation.js) surfaces it. Feedback itself remains one-shot independently — a UNIQUE partial index on `messages(session_id) WHERE session_id IS NOT NULL` guarantees ≤ 1 feedback row per session, and the messages UPDATE trigger pins `body` + `session_id` so feedback is immutable once sent.
- **A review needs a confirmation, and the page offers its feedback step only on a confirmation READ SINCE IT OPENED.** The composer — which also carries "Finish without feedback", the only other caller of `useMarkSessionReviewed` — renders for a confirmed session only. The page is reached without a confirmation in ordinary ways: a session in progress opened from the sheet or from a `session_deviation` notification, an archived session that was never trained, and a `session_completed` notification that went stale because the athlete undid the confirmation. A session reviewed in that last state never came back to the inbox, which reads from `session_confirmations`. The database refuses both writes too (the review-lifecycle migration, 09); this is the client half and it does not depend on it. **The cache is not an answer here**: `['session-confirmation', sessionId]` is served for two minutes and persisted across reloads, so [SessionReview.jsx](../src/components/coach/SessionReview.jsx) calls `useSessionConfirmation(sessionId, { refetchOnMount: 'always' })`, takes `openedAt` when it mounts, and derives `confirmationState` from the query's two timestamps: `confirmed` or `none` once `dataUpdatedAt >= openedAt`; `unverified` when the read failed since then (`errorUpdatedAt >= openedAt`) or waits for the network (`isPaused`); `checking` otherwise, which renders nothing. Four rules to keep when editing it:
  - **The successful read is tested first, and nothing un-reads it.** A refetch on window focus that fails later leaves a confirmed session `confirmed`. The composer keeps the coach's unsent text in its own state, so gating it on `isSuccess`, `isError` or `isFetching` would unmount it — and lose the text — on a flaky network. Only a read that returns no row takes the composer away.
  - **"Not confirmed" is a statement about the athlete, made for `none` only.** A failed or parked read shows, in the composer's place, the `unverified` variant of [SessionReviewNotConfirmed.jsx](../src/components/coach/SessionReviewNotConfirmed.jsx) with a "Check again" button, and the status line at the top of the page stays empty. A confirmation the cache already holds is still shown at the top without waiting (its date and the athlete's notes are content); only its absence waits for the read.
  - **`SessionReview` is a keyed wrapper around `SessionReviewPage`** (`key` = student and session ids). The router keeps a route's element mounted when only its params change, and `refetchOnMount` does not fire on a key change: without one mount per session, the first review's `openedAt` would vouch for whatever the cache holds about the second, or leave it in `checking` for good.
  - **The two read-only cards do not look at the confirmation.** Sessions reviewed before the rule existed have none, and keep saying that they were reviewed. Neither do the deviation actions (adopt, remove, decline) or archive: a deviation is notified while the session is still in progress.

  A test that mocks `useSessionConfirmation` for this page has to give the query's `dataUpdatedAt`, or the page stays in `checking` (`confirmationQuery()` in `SessionReview.test.jsx`). `SessionReview.confirmation.test.jsx` runs the page on the real hook and a real query client, so the reading of those timestamps is React Query's behaviour and not an assumption about it.
- **A review needs a confirmation and closes it — and the database holds both, for a request that carries a user id.** Migration `2026_10_13_09_review_lifecycle.sql` (review P57) ties `session_confirmations` to `sessions.reviewed_at` in three places. *A review needs a confirmation*: the trigger `trg_review_needs_confirmation` (BEFORE UPDATE on `sessions`, function `review_needs_confirmation`) refuses `reviewed_at` going from NULL to a value while the session has no confirmation — `42501`, "session … is not confirmed by its athlete — it cannot be marked as reviewed" — which is what `useMarkSessionReviewed` meets, and what `notify_student_on_session_feedback` meets when it stamps the review, so the feedback message is undone with it; the INSERT policy of `messages` asks `session_is_confirmed(session_id)` of a message that names a session, so the API answers a policy refusal first. *A review closes the confirmation*: the athlete's UPDATE and DELETE policies on `session_confirmations` ask `session_writable(session_id)` — neither archived nor reviewed — so "Undo confirmation" on a reviewed session reaches no row. *When the two cross*: a policy judges the database as its statement saw it when it started, so `block_confirmation_delete_when_reviewed` (BEFORE DELETE) reads the session again `FOR SHARE` and raises `42501` for the undo that lost the race, and `review_needs_confirmation` is `VOLATILE` so that it reads the confirmations as they are once the row of the session is locked. Rules to keep:
  - **"Reviewed" does not mean "confirmed".** Sessions reviewed without a confirmation exist from before the migration, and the owner of the database and the service role are not judged (no user id): removing an account cascades to its confirmations, and a review is taken back by hand (`docs/runbook/migrations/09-review-lifecycle.md`, "Taking a review back" — there is no reopening in the app). The trigger judges the transition from NULL to a value only: such a session is still archived, restored, renamed, reordered and moved with `move_session`.
  - **A reviewed session can still be confirmed, and that confirmation is final.** The INSERT policy of `session_confirmations` does not ask about the review, on purpose: `buildQueue` keeps a session in the athlete's list until it is confirmed or archived. Do not add `session_writable` to it.
  - **A function that marks sessions as reviewed for a coach meets the trigger**, one session or many: the whole statement is refused as soon as one of them has no confirmation. Filter on the confirmation in the statement.
  - **`review_needs_confirmation` stays `VOLATILE` and `trg_review_needs_confirmation` keeps a name that sorts after `trg_pin_draft_session_columns`.** `STABLE` reads the confirmation that has just been taken back; a name that sorts before the pin raises on a session of a draft, where the pin of migration 06 is silent. No test on one connection sees the first: `supabase/tests/review-lifecycle.test.js` has three on several connections.
  - **A confirmation sent twice is insert-or-nothing.** An upsert that updates (`ON CONFLICT DO UPDATE`, what the app deployed before wave 1 sends) is judged by the UPDATE policy and raises `42501` once the session is reviewed; `confirmSessionFn` sends `ON CONFLICT DO NOTHING`, which is an INSERT only and writes nothing.
- **`SessionReview`'s back button returns to the page that opened it, and every opener has to say which page that is.** The review is reachable from the sessions feed, from a row of the Program Sheet, from the sheet's archived drawer and from the session editor's banner. Each passes `state: { from: <its own pathname + search> }` to the router, and `handleBack` — which is also what "Send feedback" and "Finish without feedback" end on — navigates there, or to `/coach/sessions` when there is none. Only a string that starts with `/coach/` is accepted. The origin is also written into `sl_last_coach_session` as `from`, next to `studentId` and `sessionId`, and read back for the same session only: the Sessions tab restores a review left open with a redirect that carries no router state. A new link into the review that passes no `from` still works, and sends the coach to the feed.
- **The review carries the way into the editor.** A pill beside "archive" links to `/coach/students/:studentId/s/:sessionId` and clears `sl_last_coach_session`, so the Sessions tab does not bounce back into a review the coach left on purpose. It is labelled "editor", not "edit": for a confirmed session the editor is read-only.
- **`SessionsFeed` treats an arrival with `?student=` as a destination.** The roster's "N to review" chip and the athlete page's "Sessions" action both link to `/coach/sessions?student=<students.id>`. On such an arrival the feed does not restore the review saved in `sl_last_coach_session` (it could be another athlete's), and its default view follows the data: the needs-review inbox when that athlete has something to review, "All" when nothing is left, so the coach never lands on an empty page. `viewChoice` stays `null` until the coach picks a view, which is what lets the default settle after the confirmations load. A card passes the feed's own URL as `from`, so the athlete filter survives a trip into a review.

## Coach Athletes-roster layout

- **Coach roster strip data is folded into one query and comes from the SHARED placement model.** [useCoachDashboardPrograms](../src/hooks/useProgram.js) returns, per student, `{ programName, position, totalSessions, nextSessionTitle, daysSinceLast, weekDays }`. `weekDays` is the 7-slot Mon–Sun array from [`buildDayStrip`](../src/lib/sessionQueue.js) — the SAME function the athlete's own Home strip calls, so the coach's view of a week and the athlete's can never drift (this replaces the old shared `statusOf`). Progress is the athlete's place in the QUEUE, because "W3" said nothing about how far through a block they were once the block stopped running one-week-per-week. Rendering: [StudentWeekStrip.jsx](../src/components/coach/StudentWeekStrip.jsx) paints the pre-resolved states and adds only the today highlight — and today never overrides a day already trained.
- **The Athletes roster merges the old Dashboard + Students tabs.** [CoachHome.jsx](../src/components/coach/CoachHome.jsx) landing (`/coach/students`, no `:studentId`) renders the attention-first roster: a search box + one enriched card per athlete (avatar, queue position + program, `StudentWeekStrip`, attention chips) + the collapsible client-errors triage. Cards + chips + ordering come from the pure [`buildRoster`](../src/lib/coachRoster.js) over `useStudents` + `useCoachDashboardPrograms` + `useAllConfirmations` (no new query). Attention chips: **to-review** (confirmations with `reviewed_at` and `archived_at` both null, grouped by `student_id`), **quiet Nd** (`daysSinceLast >= STALE_AFTER_DAYS`, and never for an athlete who has yet to train), **no active program** (derive from key-absence, *not* a null field, since an active program with nothing scheduled is not a gap). `/coach` and the legacy `/coach/dashboard` both redirect here. Tapping the Athletes tab restores the coach's last athlete — `sl_last_coach_students_path`, written by `CoachHome` and read back by its restore effect (see the coach-persistence section of [ARCHITECTURE.md](ARCHITECTURE.md)) — so a detour through Sessions/Messages/Library returns to the athlete, or to the session editor, they were working in. The **"‹ All athletes" header link clears that key**, which is the only way to pin the roster: make it a plain `<Link>` again and the restore effect bounces the coach straight back into the athlete they just left.
- **A roster card is a link STRETCHED over the card, not an anchor wrapped around it.** The card is a `relative` box; its "open this athlete" `<Link>` covers it with `after:absolute after:inset-0`. That is what allows the "N to review" chip to be a link of its own (to `/coach/sessions?student=<id>`) — an anchor cannot contain an anchor — and the chip needs `relative z-10` to sit above the stretched area, or its tap opens the athlete instead. Any other interactive element added to a card needs the same. `CoachHome.test.jsx` asserts that no `a` contains an `a`.
- **The Programming tab is the whole block as ONE list; there is no week page and no accordion.** [ProgramSheet.jsx](../src/components/coach/ProgramSheet.jsx) renders every session of the block at once — a row per session (weekday pill → `day_number`, title, exercise count, confirmed ✓) with weeks appearing only as [PhaseDivider](../src/components/coach/PhaseDivider.jsx) rules between them, and ONE block-level "show N archived" drawer linking to SessionReview. **A one-phase block and a six-phase block are the same layout** — the old flat/nested split changed the shape of the page under the coach as soon as they added a second week. Session positions are numbered ACROSS phases, and that number is what names an untitled session. Phase-level actions (add session / duplicate / copy to… / reorder phases / delete) live in the divider's ⋯ menu — including entering phase-reorder mode, which has no standing top-level button. **Don't reintroduce a collapse**: the largest block in production is 19 sessions and the average 8, so collapsing costs a tap and hides the very thing the page exists to show. **Session delete is deliberately NOT on the sheet rows**: a destructive icon on every row of the main authoring surface is a mis-tap waiting to happen on a phone, so it lives in the session editor, where the coach has already committed to that one session. `WeekTimeline` and `WeekView` are **deleted**; `/coach/student/:id/week/:weekId` and `…/week/:weekId/session/:sessionId` survive only as redirects.
- **A row of the sheet opens the REVIEW once its session is trained, the editor before that.** [SessionRow.jsx](../src/components/coach/SessionRow.jsx) takes `confirmed` and `trained`; either one sends the row to `/coach/student/:studentId/session/:sessionId/review` with the sheet's URL as `from`. `ProgramSheet` computes `confirmed` from `useProgramConfirmedSessionIds` **or** `sessions.performed_at` — the confirmation's mirror, which arrives with the sheet's own `['program']` query, so a confirmed row does not open the editor while the confirmations are loading — and `trained` from [`useProgramLoggedSessionIds`](../src/hooks/useSession.js) (`['program-logged-session-ids', programId]`): the sessions that hold a logged set and are neither confirmed nor archived. That query leaves confirmed sessions out on purpose (`performed_at IS NULL`): they hold nearly every logged set of a block, and without the filter the read would approach PostgREST's 1000-row cap on a long one. If it is ever truncated the failure is the safe one — the row opens the editor, which locks the logged sets and links to the review itself. A started, unconfirmed row shows a hollow ring where the ✓ will be.
- **The coach's "Last time" reference reads MEASURED performance, and is keyed on the EXERCISE.** [PreviousSessionPanel.jsx](../src/components/coach/PreviousSessionPanel.jsx) shows, per exercise of the session being written, the sets the athlete actually logged — via the same [`useLastPerformance`](../src/hooks/useLastPerformance.js) that powers the athlete's own hint, so the two surfaces cannot disagree. It previously listed the COACH'S OWN past prescription from "the same weekday one week earlier", which was wrong three ways: a prescription is not a performance to beat; it required `week_number === current - 1` so it rendered nothing at all in a one-week block (the normal shape since the queue refactor); and its matching keyed on `day_number`, meaningless once that became an optional hint.
- **`useLastPerformance` is role-aware and MUST be scoped when a coach calls it.** Pass a STUDENTS-table id as `studentRowId` (same convention as `useStudentRecords`/`useStudentProgressStats`): the hook hands it to `fetchDoneSetHistory`, where both the `set_logs` and the `slot_deviations` read filter through the program join, on every page. Omit it and RLS alone scopes to the signed-in student. Skipping the scope in the coach flow is not a no-op — a coach's RLS returns EVERY athlete's logs, so the hint would silently show the most recent number across the whole roster. `studentRowId` is in the hint's query key, and names the history's cache entry, for the same reason. `src/hooks/useLastPerformance.test.jsx` ("whose history") holds all of it: the filter on every page of both reads, no athlete filter on either read without it, and two athletes opened in turn — same session id, same exercise — each getting their own numbers from their own entries.
- **Opening a session, adding an exercise in the editor, or coming back to the tab must not download the athlete's history.** The hint's key is `['last-performance', studentRowId ?? 'self', sessionId, exerciseIds]`, so each of those starts or refetches a query — and that query only picks its exercises out of the list `fetchDoneSetHistory` already holds (see "Stats"). Putting a `supabase.from('set_logs')` back into the hook's `queryFn` brings the scan-per-session back without failing any assertion on the hint itself; the request counts in `src/hooks/useLastPerformance.test.jsx` ("the history is read once") are what notices.
- **Nothing invalidates `['last-performance']`: a hint is renewed by its own `staleTime` (one minute) and by nothing else.** That is enough as long as a mount or a return to the tab re-derives any hint older than that — which is free, since it comes out of the shared history, and a confirmation does renew that. Lengthen the hint's `staleTime`, or stop it refetching on focus, and a session that was opened before another one was trained keeps its older "last time" — the entry is persisted, so across reloads too. Whoever makes that change makes the confirmation invalidate `['last-performance']` in the same commit; re-deriving every cached hint costs one history read between them.
- **Archiving is the coach's cleanup verb, and it lives on the sheet.** It used to be unreachable from Programming entirely: `useArchiveSession`'s only caller was `SessionReview`, which is reachable only for a session the athlete already CONFIRMED or one already archived — so a planned-but-unwanted session that was never trained could only be DELETED. `ProgramSheet` now archives from a selection bar whose selection **spans phases** (archiving a finished mesocycle is one gesture) and restores in place from the block's "N archived" drawer, instead of sending the coach to a full-page review route for a one-tap action. Archiving is the right verb because the DB refuses to delete a session carrying logged sets (`block_session_delete_with_logged_sets`), so for anything actually trained it is the only answer. Any archive write must invalidate `['student-program-details']` too — archiving pulls the session out of the athlete's queue.
- **Bulk session writes are SEQUENTIAL, and settle their caches on `onSettled`.** `useArchiveSessions` and `useCopySessions` ([useWeek.js](../src/hooks/useWeek.js), [useDuplicate.js](../src/hooks/useDuplicate.js)) walk a hand-picked list of ids one at a time: `useCopySessions` must, because each copy asks the destination week for its next free `sort_order` and parallel copies would all get the same one and trip the UNIQUE. Both stamp `error.partial` with how many landed, and invalidate on `onSettled` rather than `onSuccess` — a partial failure still moved rows, so the caches have to refresh either way. (The INVARIANTS ban on fanning ids into `.in(...)` is about UNBOUNDED slot-id lists, not a coach's hand-made selection.)
- **`CopyDialog` picks the destination in full: athlete → BLOCK → week.** It used to resolve straight to the destination athlete's ACTIVE program (`useActiveProgram`), which dead-ended with "No weeks" for an athlete who had none and made it impossible to copy into a block being prepared for later. Copies APPEND to the end of the destination week — there is deliberately no insert-at-position picker, because the coach can now drag sessions into place on the sheet, so a fourth dropdown would buy nothing a reorder doesn't do better.
- **Sessions list by POSITION (`sessions.sort_order`), never by weekday.** This inverts the old rule. `compareSessions` ([lib/day.js](../src/lib/day.js)) ranked by weekday with `sort_order` as a tiebreak, and `compareQueued` then put two dated sessions in date order ahead of that — so the recommended day was the only lever that actually reordered the athlete's queue, and a coach could not say "this one comes first" without also claiming when to train it. Since `2026_08_22_session_order_backfill.sql` every week is renumbered 0..n-1 and position IS the order; `day_number` and `scheduled_date` are hints that sort nothing, and `compareQueued` is deleted. The backfill reproduced the on-screen order exactly (measured: 56 of 253 sessions across 28 of 86 weeks would otherwise have moved on deploy; after it, zero). The coach's control is `useReorderSessions` — an explicit MODE, because on touch a drag handle competes with vertical scroll, reachable beside "+ Session" so it exists in FLAT mode too where there is no week ⋯ menu. Like `useReorderWeeks` it must renumber in TWO passes (park at 100000+, then place): `sessions_week_sort_order_unique` is UNIQUE and NOT deferrable, and the payload must include ARCHIVED rows because the constraint spans them.
- **The session editor's header is one row — back, session name, recommended date, all on one baseline — and DELETE is the app's only delete path.** There is no "SESSION" kicker: the athlete header sits directly above it, so a label naming the kind of thing you are looking at spent a line stating the obvious. Duplicate and "copy to…" were removed from it: the sheet carries both (a duplicate button per row, copy behind the selection bar), so they were a second door onto the same actions costing a band of space above the work. The recommended-date field moved up onto the header row for the same reason. **Delete stayed** — `useDeleteSession` has exactly one caller and archiving does not replace it for a session created by mistake — but it moved to the BOTTOM of the editor: a red button beside the title was the most prominent thing on a screen whose job is writing exercises. It keeps its ConfirmDialog and its navigate-back-on-success.
- **The session editor locks what the athlete has trained, and how much depends on whether they confirmed.** [SessionEditor.jsx](../src/components/coach/SessionEditor.jsx) derives two states. **Confirmed** (`useSessionConfirmation` returns a row, or `session.performed_at` is set): the whole editor is read-only — the title is text, the date and every field are disabled, and add, remove, reorder, unlink and delete are not rendered; `ExerciseSlotRow` gets `readOnly`. **Logged sets, not confirmed** (a session in progress, or one stopped half-way): only the logged sets are locked. [ExerciseSlotRow.jsx](../src/components/coach/ExerciseSlotRow.jsx) disables and marks each logged row, drops its remove button, disables "Remove exercise" while any row of the slot is logged (student-added extras included, since the delete would cascade to them) and replaces the compact one-row view with the per-set table, where pending sets stay editable and "+ Add set" still works. This second state is deliberately not read-only as a whole: re-planning what is left of a session is what the coach opens it for, and it is what the database allows. In both states a banner says which one it is and links to the review, and "Delete this session" is not rendered — the database refuses a session with logged sets. A notes field is `readOnly`, not `disabled`, so it can still be read in full and copied.
- **Session editing renders inside the athlete shell.** `SessionEditor` is a child route at `/coach/students/:studentId/s/:sessionId`, so the athlete header stays mounted while editing. It therefore **must not apply page padding of its own** (`CoachHome` already applies `p-4 pb-6 md:p-8`) and it resolves its `weekId` from `session.week_id` rather than the URL.
- **The single-student view is ONE page with collapsible sections — no tabs.** [StudentOverview.jsx](../src/components/coach/StudentOverview.jsx) stacks Programming (open by default), Goals and Stats as collapsible blocks. **There is no identity block above them — on an athlete route the page header *is* the athlete.** [CoachHome.jsx](../src/components/coach/CoachHome.jsx) swaps its own header when a student resolves: the back link takes the `sl-label` kicker slot where "COACH" sits, and the name takes the `h1` where "Athletes." sits (with the house editorial full stop, guarded so "Sammy Jr." doesn't become "Sammy Jr.."). The old stack — roster title, then back link, then an avatar/name row, then a coaching-since date, then the pills — put the biggest type on the page the coach had just *left* and pushed the actual subject three rows down at half the size. `StudentHeader.jsx` is **deleted**; don't reintroduce a second identity row. **The two headers must stay one shared box** — same block-level kicker, same `h1` classes — so moving roster ↔ athlete changes the words and not a single pixel. Three rules keep that true: the `h1` needs `truncate` (names are unbounded, "Athletes." wasn't); it must **not** take `leading-none` (`truncate` clips at the padding edge and a name has descenders the roster title never did); and the back chevron is a **mono glyph inside the label text**, not an SVG — an `inline-flex` anchor around an icon builds a taller line box than the roster's block kicker *and* indents the label off the title's left edge, which is exactly the jump this replaced. `CoachHome.test.jsx` asserts the shared classes and the absent `<svg>`, since jsdom can't measure the layout itself. Tabs were removed because every tab was a separate destination that remounted and scroll-reset — losing the coach's place mid-edit. Two rules matter: a collapsed section is **unmounted, not hidden** (Stats runs a heavy aggregate and Goals a profile-id resolve — a closed section must cost nothing), and open/closed persists in `localStorage` under `sl_coach_student_sections`. The athlete header deliberately carries **no week strip**: that data comes from the active-program summary query and would contradict the sheet below whenever a non-active block is selected. Every former tab URL (`programming`, `progress`, `profile`, `goals`, `stats`, `messaging`) redirects to the page.
- **The athlete page carries two actions under its header: Message and Sessions.** `AthleteActions` in [StudentOverview.jsx](../src/components/coach/StudentOverview.jsx) links to `/coach/messages/:profileId` — the thread is keyed on `students.profile_id`, not on the students-row id — and to `/coach/sessions?student=<students.id>`. They are the first row of the page body and not part of `CoachHome`'s header, for two reasons: that header box is shared with the roster and must not change shape, and it stays mounted over the session editor, where a row of actions above the work is what the editor's own header was trimmed to avoid. The student comes from the outlet context.
- **The coach's place must survive a trip into the session editor.** Two separate mechanisms, both required: `AppShell`'s `useScrollRestoration` remembers each route's scroll offset and re-applies it across a few animation frames (the target route is `React.lazy`, so on the first frame the container is still the Suspense fallback and has no height to scroll); that is now the WHOLE mechanism for the program sheet, since the sheet no longer collapses anything and has no open-week state to remember (`sl_coach_open_week` is gone). A first visit to a route still starts at the top — only a revisit restores. Don't reintroduce a blanket `scrollTo(0)` on pathname change.
- **Coach roster owns the student lookup.** [CoachHome.jsx](../src/components/coach/CoachHome.jsx) resolves the `:studentId` from `useStudents()` and exposes the resolved student to the sub-tabs via `<Outlet context={{ student }} />`. Each section reads it with `useOutletContext()` — including `StudentGoalsSection`/`StudentStatsSection` nested inside `StudentProgressSection`, since outlet context reaches any descendant. `/coach/students/:id` redirects to `…/programming` (the index sub-route). The athlete route's page-header kicker is the **"‹ All athletes"** link back to the roster. The legacy `/coach/student/:id/goals` URL redirects to `…/students/:id/goals`.

## Training is a QUEUE; the calendar is a consequence

- **A block is an ordered list of sessions, not a schedule.** The next session is the first unconfirmed, non-archived one in program order (weeks by `week_number`, sessions by `compareSessions`) — computed by [`buildQueue`](../src/lib/sessionQueue.js), which also returns `position`/`total` ("Session 7 of 24"), `lastPerformedAt`, `daysSinceLast` and `doneLast7`. **A date never jumps the queue**: a session the coach dated today but placed in a later week does NOT become "next" while earlier work is open. That is the whole point — it is what stops a missed session from cascading into a re-dating exercise. `flattenSessions` sorts two DATED sessions chronologically before falling back to weekday order, because `compareSessions` ranks by weekday alone and would otherwise put the 13th (a Monday) ahead of the 10th (a Friday).
- **`sessions.day_number` is a RECOMMENDED weekday (1 = Mon … 7 = Sun) and is NULLABLE** (2026_08_21). It is advice, never a commitment: order comes from `sort_order`, and nothing is "missed" for being trained on another day. New sessions are created with `day_number: null` — auto-assigning the next free weekday made every session look due on a date nobody chose, and capped a week at 7 because day 8 fell outside every strip. The student draft builder used to write this column as an ORDINAL (a 5th session silently became "Friday"); it now writes null. **A NULL only survives if the write path passes it through**: `save_draft_tree` predates the nullable column and coalesced to `1`, so every student-authored session came back recommending Monday even though the authoring UI has no weekday control at all — fixed in `2026_08_22_draft_day_number_optional.sql`.
- **There is no "missed" state anywhere.** `statusOf`, `deriveWeekStats` and `preferSession` are deleted from `lib/day.js`. Strip placement is [`buildDayStrip`](../src/lib/sessionQueue.js), **shared by the student's Home and the coach's `StudentWeekStrip`** so the two can never tell different stories about the same week. Its states, in the order they win a contested day: `performed` (trained on that date — the record, which nothing may overwrite) > `planned` (a coach-set recommended date for open work) > `archived` (pulled by the coach; kept visible, not blanked to rest), plus `suggested` for an undated queue head projected onto its recommended weekday. Weekday projection is gated on the CURRENT week (`weekdayFallback`) — projecting a recommendation onto a navigated week would invent a plan. Coach-side triage replaces "missed Wed" with **"quiet Nd"** (`STALE_AFTER_DAYS = 10` in [coachRoster.js](../src/lib/coachRoster.js)); an athlete who has never trained shows no chip, because "quiet forever" is not a finding.
- **`scheduled_date` is still a bare `YYYY-MM-DD`** — always parse with `parseISODate` (local time), never `Date.parse`/`toISOString`, which shift across timezones. Day-cell `aria-label`s include the day-of-month (`Monday 13 — Push Day`) because the button's label masks its inner text from AT; the range header is `aria-live="polite"` so week navigation is announced.
- **The student has ONE training surface, and it is the list.** [StudentTraining.jsx](../src/components/student/StudentTraining.jsx) replaced a Home page and a Sessions page that both listed sessions and both offered "start the next one" — two doors onto one question. `/student/sessions` redirects to `/student`, `StudentHome.jsx`/`StudentSessions.jsx` are deleted, and the student bottom nav is **3 tabs** (Training · Stats · Messages), not 4. **There is no Mon–Sun day strip on it**: a seven-column grid with week arrows IS the calendar week, which is the framing the block was rewritten to stop imposing — the month calendar in Stats carries "when did I train" as a retrospective instead. The page states the athlete's place ONCE (program name + "Session 6 of 7"); the old stack of four headings (week range, "Next session", "Session 6 of 7", "Then") is gone. **Finished sessions order by real training date, newest first** — they used to sort by recommended weekday, so a session trained on the 18th sat above one trained on the 21st. Undated legacy rows sink below dated ones rather than jumping to the top. **The next session is a card like any other**: it opens by default because it is what the athlete came for, but it collapses when another is opened rather than holding a screenful for a session that is no longer the subject. `openSessionId` distinguishes `undefined` ("not chosen yet" → the next session opens) from `null` ("deliberately collapsed"), because the next session's id isn't known until the query resolves; the toggle compares against the EFFECTIVE open id, or the first tap on an already-open next card would re-open it. A **`badge`** prop on `SessionCard` carries the meaning the permanent expansion used to — the accent rail alone is easy to lose when scrolling identical rows. `SessionCard` also no longer renders its "start" LABEL on an OPEN card: the code now matches its own comment that the bottom CTA takes over, a duplication that only became visible once the next-up card was both expanded and collapsible.
- **Everything already trained sits in a closed `Drawer`** — one for the active block's own finished sessions ("Done · 5 sessions"), one per past block ("Past program · 15 sessions") — leaving only the next session and the work still ahead in plain sight. A month-long block reaches ~20 completed cards and a year of coaching hundreds, every one of them standing between the athlete and the single question the page answers; the queue position in the header states progress without listing it. `Drawer` takes a **`renderBody` function, not children**, so a closed drawer builds nothing and the cost stays one row however long the history gets. Open state is deliberately NOT persisted: you open a drawer to look one thing up, and a clean page next visit is the right default. The archived-sessions toggle is a quiet page footer rather than a control inside a drawer the student would have to open first. Past blocks render read-only via `SessionCard`'s **`locked`** prop, which stops LOGGING and never LOOKING: it suppresses the start pill, the decorative "start" label and the Start CTA, but a finished session keeps its **Review session** CTA — opening an old session to see what you did is why the history is on the page, and `SessionView` already renders a past block read-only. Dropping `onStart` wholesale instead broke exactly that, leaving Review as an inert button; the bottom CTA is now gated on `onStart` too, so a primary button can never render without a handler again. **The greeting shows at most one line, and only when it says something**: staleness when the athlete has been away, the 7-day count otherwise, and nothing at all on a fresh account — "Trained today" told them what they already knew.
- **A week survives only as an optional PHASE, and a phase has a NAME, never a number.** `weeks.week_number` is still the ordinal the DB sorts on and `adopt_swap`/`adopt_skip` predicate on, but it is never shown: a number is what made a week feel like a fixed-length container, which is the idea the queue refactor removed. An unnamed phase still **draws its divider** — half the phases in production are unnamed, and hiding those rules would silently merge them into the phase above — it simply carries no heading, and its "name this phase" invitation drops out of `sl-label` so a stack of them doesn't shout over the sessions. An empty block's CTA adds a SESSION and creates phase 1 implicitly.

- **Dragging a session across a divider MOVES it between phases, and that is ONE write.** [`planSessionDrag`](../src/lib/sessionMove.js) decides reorder-vs-move purely and returns the FULL ordered id list of every week touched, archived rows appended — `UNIQUE (week_id, sort_order)` spans the whole week, so a payload that omits archived rows renumbers straight into a collision. A cross-phase drag then goes through the `move_session` RPC (`2026_08_22_move_session.sql`, **SECURITY INVOKER** so it rides the coach's existing `Coaches manage sessions` policy rather than adding trust surface), which re-homes the row and renumbers both weeks in one statement, parking every involved id at `100000 + n` first. Split across two round trips, a failure between them leaves a session holding a position that collides in its new week. Reordering *within* a phase stays on `useReorderSessions`.
- **`move_session` still parks at `100000 + n`; `reorder_sessions` does not.** A unique key that is not deferrable is checked row by row, inside one `UPDATE` too: parked at a constant, a session can meet one that an interrupted reorder left at that number, and `move_session` then fails with `sessions_week_sort_order_unique` on such a phase — or goes through, as the ids fall. `reorder_sessions` and `reorder_weeks` park above every number the parent holds (`GREATEST(max, n) + place`) and cannot. A phase left parked is put right by one call of `reorder_sessions` with its sessions in the order they are shown (`docs/runbook/migrations/11-activate-reorder-rpcs.md`, "Sessions or phases left parked").

## The date a session was actually trained

- **`session_confirmations.performed_on` (date) is the truth; `sessions.performed_at` (timestamptz) is its mirror** (2026_08_21). `confirmed_at` is the server clock at INSERT, which for an offline student is the REPLAY moment, not the training one — so it is a fallback, never the primary. The client computes `performed_on` at CONFIRM time via [`performedOnFromLogs`](../src/lib/day.js) from the session's `set_logs.logged_at` (minted when each set was ticked, so it survives an offline queue intact) and it rides in the serialized mutation variables. It takes the EARLIEST logged set: a session running past midnight belongs to the day it began, matching the migration's `MIN` backfill. Resolved in LOCAL time via `isoDate`.
- **The mirror is maintained by its own trigger, `sync_session_performed_at`** — deliberately NOT folded into `notify_coach_on_session_confirm`, which is the notification/Web-Push path (AFTER INSERT only, with an EXCEPTION-wrapped pg_net call). The mirror needs the DELETE branch (undoing a confirmation un-performs the session, so `performed_at` goes back to NULL) and an UPDATE branch. The app's own confirm does not reach the UPDATE branch — it is insert-or-nothing, see "Offline-safe student writes" — but a `performed_on` corrected in SQL does, and so does an installed client that still sends the confirm as an updating upsert. SECURITY DEFINER, because students have no UPDATE grant on `sessions`. `performed_on` is client-supplied, so the trigger clamps a value more than a day in the FUTURE back to `confirmed_at`; past dates are never clamped — confirming days after training is the entire point.
- **Rows written before the column existed degrade quietly, never by inventing a date.** `buildQueue` ignores a confirmed session with no `performed_at` when computing staleness; `buildDayStrip` falls back to the day it was PLANNED for; `useStudentProgressStats` prefers `performed_at` → `performed_on` → `confirmed_at` → (archived only) `scheduled_date`, and a session with none of these is counted in `backlogSessions` rather than parked on a made-up day.

## Stats

- **Time-based stats bucket by the REAL calendar week the student trained in** (2026_08_21), not by the ordinal training week a session was authored under — a block spread over ten days used to land in a bucket corresponding to no actual seven-day span. `weeklyVolume[]` rows are `{ bucket_start, bucket_end, … }` (Mon–Sun of `performed_at`) rendered as date ranges by `formatBucketRange`; `weeksActive` counts calendar weeks trained; `exerciseProgress.byExercise[]` is **one point per SESSION** on a date axis (which retired the `program_id:week_id` composite key that existed only to stop week 1 of two blocks colliding). **A session's PLANNED volume travels with it into the bucket where it was performed**, so planned and performed are always compared over the same days; work not yet done has no date and lands in `backlogSessions` instead of dragging down a week it was never attempted in. `sessionCalendar` plots trained sessions on their REAL date and open ones on the recommended date, so a session trained without any coach-set date finally appears at all.
- **Stats are performance-aware: charts show PERFORMED work, not just the prescription** (2026_07_13). [`useStudentProgressStats`](../src/hooks/useStudentProgressStats.js) builds a `perfBySlot` index from the flat `set_logs` read — DONE rows only (`done = true`), filtered through the program join and read to its end with `fetchAllRows`. `performedReps` = a done set's `actual_reps ?? target_reps` (`??`, so a real 0 is respected; skipped/undone contribute 0); `performedWeight` = `actual_weight_kg ?? target_weight_kg` with bodyweight (null/0) → 1kg. `weeklyVolume[].pull`/`push` are now PERFORMED (prescribed kept as `*_planned`), plus `sets_done`/`sets_prescribed` for adherence; `exerciseProgress.byExercise[].tonnage` is PERFORMED with `plannedTonnage` as the reference. The dashboard renders performed volume over a faint planned ghost track + per-week adherence %, and the exercise chart draws performed tonnage (solid) with a dashed planned line when they diverge. This is what makes the off-plan actuals + deviations features finally visible in the student's motivation loop. Coach `StudentStatsSection` reuses the same hook + chart, so it inherits this for free.
- **The flat `set_logs` list in `useStudentProgressStats` holds DONE sets and nothing else.** Every figure derived from it — `totalSetsDone`, `avgRpe`, `sets_done`, performed volume and tonnage — counts done sets only, so the pending, failed and skipped rows are not downloaded (they were most of the rows and none of the result). Anything that needs the prescribed sets reads them from the program tree (`exercise_slots.sets`, the embedded `set_logs` targets), which is complete. A new figure about failed or skipped sets needs its own read; do not drop the `done` filter to get it — that puts the athlete's whole prescription back into a read that is paged.
- **Of two sets that tie for a best, the EARLIER one holds the record.** `buildRecords` keeps the first set that reaches a value, so the sets must reach it oldest first: `readDoneSetHistory` sorts the done sets by `logged_at` (then `id`), and `useStudentRecords` reduces them in the order it receives them. Pages arrive in id order, which is arbitrary; without the sort a record matched last week could take the date of the record and light the "New PR" badge for a lift that set no record.
- **"Last time" does not depend on the order its rows arrive in.** `useLastPerformance` picks its exercises out of the athlete's whole history (every done set, all exercises — a prior swap sits under another `exercise_id`); `buildLastPerformance` picks the latest prior session per exercise and orders its sets itself, whatever order the list is in. The old newest-first `.order('logged_at')` existed only so that the cut at 1000 rows kept the recent part; there is no cut any more.

- **Personal records + bodyweight** (2026_07_14). [`useStudentRecords`](../src/hooks/useStudentRecords.js) reduces the athlete's done sets — taken from the shared history (`fetchDoneSetHistory`, next bullet), not read by the hook; a coach names the athlete with a `students.id`, which is what `programs.student_id` references, NOT `profiles.id`, and an athlete reading their own passes nothing — into one record per exercise via [`lib/records.js`](../src/lib/records.js): best Epley e1RM (`w × (1 + reps/30)`, but a **single rep returns the weight exactly** — a 1-rep set IS a 1RM), best single set, best reps (bodyweight PR), and a `recent` flag for a PR set in the last 14 days. Effective load = `actual_* ?? target_*`. **Records are SWAP-AWARE:** the history reads the athlete's `kind='swap'` `slot_deviations` alongside the sets (through the same program join, never an unbounded slot-id `.in()`) and hands a swapped set over under the SUBSTITUTE exercise — with **only the logged actuals**, because the slot's pinned `target_*` are the coach's ORIGINAL exercise's numbers and are foreign to the substitute, so they are null on such a set. The consequence is deliberate and must not be "fixed" to match Stats: a swap with no logged actual sets **no** record here, whereas [`useStudentProgressStats`](../src/hooks/useStudentProgressStats.js) still ESTIMATES volume from the prescribed reps (the student did that rep scheme, just a different movement). A PR is a MEASURED fact — crediting the substitute from the coach's prescription would fabricate one. [`useLastPerformance`](../src/hooks/useLastPerformance.js) follows the same rule. `bodyweight_logs` (one row per student per day, upsert on the LOCAL `(student_id, logged_on)` key — use `lib/day.isoDate`/`parseISODate`, never `toISOString`; student owns it keyed on `profiles.id`, coach reads via the students-join) records the bodyweight series. Both surfaced on [StudentProfile](../src/components/student/StudentProfile.jsx) via `BodyweightCard` + `PersonalRecords`; bodyweight logging is online-only (new-row insert can't queue offline). **The `×bodyweight` relative-strength figure shipped on top of this series** (2026_07_23) once `exercise_library.load_mode` gave the library a way to tell ADDED load (weighted calisthenics) from FULL load (barbell): [`buildRecords`](../src/lib/records.js) takes a `bodyweightAt(dateIso)` resolver and emits `relStrength` + `bwAtBest`, rendered as a ×BW pill on [PersonalRecords](../src/components/student/PersonalRecords.jsx). Four rules hold, and none of them may be quietly relaxed. **The est-1RM headline — and PR selection and sort — stay the ADDED/logged-load e1RM**, bodyweight-independent and byte-identical to before the feature, so weight change can never manufacture or reshuffle a PR. **`relStrength` is the PEAK across all qualifying sets** of (system-load e1RM ÷ bodyweight at that set) — a true max, NOT a figure derived from the added-load PR set, because the PR set and the strongest RELATIVE single needn't be the same set (and a bodyweight-only set on an `added` movement, system load = bodyweight, still contributes). **An unclassified `load_mode` (NULL) or an unresolvable bodyweight degrades gracefully to `relStrength = null` and no pill** — never `0×` or NaN; that's why `bodyweightAt` defaults to `() => null`, which keeps every caller that passes no series on the pre-feature output. **Tonnage and volume stay bodyweight-blind by design** — ×BW and tonnage legitimately tell different stories about the same added-load lift, so do NOT "fix" one to match the other. Schema, RLS, and the `useLogBodyweight` → `['student-records']` invalidation rule are in the relative-strength entry under `set_logs` above.
- **An athlete's done-set history is read ONCE, by `fetchDoneSetHistory`, and whatever reduces the whole history derives from that read.** [`lib/doneSetHistory.js`](../src/lib/doneSetHistory.js) holds it. `readDoneSetHistory(studentRowId)` sends the done `set_logs` and the `kind='swap'` `slot_deviations` together, each to its end with `fetchAllRows`, and returns flat rows, oldest first (`logged_at`, then `id`), with the swap already applied: `exerciseId` is the exercise PERFORMED (the substitute on a swapped slot), `exercise` its `{ id, name, type, load_mode }` — or null when the reader may not see that library row —, `swapped` says which, and `target_*` are null on a swapped set, because the slot's pinned targets are the original exercise's numbers. `fetchDoneSetHistory(queryClient, { studentRowId, userId })` keeps that list in the query cache under `['student-records', 'history', <athlete>]`: the STUDENTS-table id in the coach flow, the signed-in user's id when an athlete reads their own. [`useStudentRecords`](../src/hooks/useStudentRecords.js) and [`useLastPerformance`](../src/hooks/useLastPerformance.js) call it from their `queryFn` and reduce; neither reads `set_logs` or `slot_deviations` itself. Each used to scan that five-level join on its own — "Last time" once per session opened and once more per exercise added in the session editor, 152 kB a time in production. Six rules keep it one read:
  1. **The key's root is `'student-records'` on purpose.** `invalidateConfirmationQueries` (confirm, unconfirm) and `useLogBodyweight` invalidate `['student-records']`, and that prefix is the only thing that tells the history an athlete's done sets changed. A new write path that changes what an athlete has done invalidates `['student-records']`, never a narrower key; and the history cannot move under another root without those sites learning it. `src/hooks/sharedHistory.test.jsx` drives the real `useConfirmSession` and fails if a confirmation stops renewing the history.
  2. **It is read with `queryClient.fetchQuery`, never observed with `useQuery`.** With no observer an invalidation only flags the entry and the next derivation pays for the read; callers that arrive while a read is in flight share it. An observer would download the whole list again on every confirmation and every return to the tab. The price of having none: an invalidation that lands while a read is in flight restarts nothing, and the read's own success clears the flag — so the `queryFn` in `fetchDoneSetHistory` compares the entry's `isInvalidated` before and after its read and, when it went up in between, reads once more before anyone gets the list. Keep that comparison if the `queryFn` is rewritten; without it a session confirmed during the read is missing from a list held as fresh for ten minutes. It sees one invalidation per read: a second one during the repeat, or one during a read that began on an entry already flagged, waits for `HISTORY_STALE_MS`.
  3. **Between two invalidations a read is trusted for `HISTORY_STALE_MS` (10 minutes), and dropped from memory after the same time.** Sets ticked on this device since the last read are missing from it until the session is confirmed or the ten minutes have passed. "Last time" never looks at the open session, so this delays only what the NEXT session's hint and the records list show; a coach sees a workout the athlete finished on another device at most ten minutes late. Do not close that window by invalidating on every set tap: that is one full scan per tap, which is what this module removed.
  4. **`'student-records'` stays out of `PERSISTED_QUERY_ROOTS`.** The list runs to hundreds of kB and the persister re-serialises the whole cache on every event. What is persisted for offline use is the small object `useLastPerformance` reduces it to, under `'last-performance'`.
  5. **The athlete scope lives here.** With a `studentRowId` both reads carry `.eq('exercise_slots.sessions.weeks.programs.student_id', …)` on every page; without one NO filter is sent and RLS scopes the rows to the signed-in athlete. A coach caller MUST pass it (see the `useLastPerformance` bullet under "Coach Athletes-roster layout"). Both hooks name the athlete the same way — if one resolved a `students` row and the other did not, one athlete would get two entries and two reads.
  6. **It passes `retry: false`.** The hook that derives from it retries; inheriting the client's default too would multiply the attempts of a read that is several requests long. A failed read is not kept.

  A new figure over an athlete's whole done-set history — a coach-side records list, an e1RM trend — calls `fetchDoneSetHistory`; it does not add a scan. `useStudentProgressStats` is deliberately not a consumer: it is scoped to a block, needs the prescribed side, and ESTIMATES a swapped set from the prescription where this list holds measured numbers only.
- **A swap is a swap even when its substitute cannot be shown.** `readDoneSetHistory` decides on `slot_deviations.substitute_exercise_id`, not on the embedded library row: a set on a swapped slot belongs to the substitute's id whether or not the reader may see that exercise (one from a former coach's library comes back with no row). "Last time" works on the id alone; a record needs a name, so `useStudentRecords` sets none for a set whose `exercise` is null. Handing such a set back to the exercise prescribed would credit work — possibly a record — to a lift that was not done. For the same reason the library embed on `set_logs` is a plain one, not `!inner`: a hidden exercise must not take the set out of the history.

## Stats persistence

- **Stats page selections are persisted in URL + localStorage.** Program scope lives in the URL (`?scope=` on `/student/stats`, `?statsScope=` on `/coach/students/:id/stats`) so a refresh holds — but a tab switch drops the search params, so [lib/statsPrefs.js](../src/lib/statsPrefs.js) mirrors `{ scope, exerciseId }` to localStorage too. On mount, if the URL has no scope param, the parent hydrates it from localStorage. The exercise selection inside [ExerciseProgressChart.jsx](../src/components/student/ExerciseProgressChart.jsx) reads/writes its own `localStorage` slot via the `storageKey` prop. Keys are namespaced per surface — `sl_stats_prefs:self` for the student, `sl_stats_prefs:coach:<studentId>` for each coach view — so a coach hopping between students never drags one student's selection onto another. Stale ids fall back gracefully via the existing `scopeIsValid` and `exercises.some(...)` checks.

## Offline-safe student writes

- **Offline-safe student writes are wired through one allow-list.** Persistence + replay are handled by [`lib/queryClient.js`](../src/lib/queryClient.js) (PersistQueryClient + IDB store + `shouldPersistQuery` allow-list: `session`, `set-logs`, `slot-comments`, `slot-deviations`, `session-confirmation`, `set-videos`, `student-program-details` — its `'active'` variant only, the `'all'` history tree would bloat every persist write — and `my-confirmed-session-ids`) and [`lib/offlineMutations.js`](../src/lib/offlineMutations.js) (mutationFns + `registerOfflineMutationDefaults`). **Persisted query data must be plain JSON** — a Set/Map silently dehydrates to `{}`; that's why `useMyConfirmedSessionIds` caches an ARRAY and derives its Set via `select`. The last two roots are load-bearing for offline cold start: without program details Home dead-ends on a spinner, and without confirmations it renders actively wrong data (week-1 regression, 0/N adherence). Any new student-side mutation that must survive offline → reload → resume needs three things: a stable `mutationKey` from `MUTATION_KEYS`, its mutationFn registered in `MUTATION_FNS`, and `networkMode: 'online'` (the default — pauses-while-offline, fires-on-reconnect; **`'offlineFirst'` would silently fail with `retry: 0`**). **Replay ordering is scope-based:** the registered defaults carry `scope: { id: 'offline-writes' }` so hydrated-after-reload mutations replay strictly FIFO (a parallel replay could land done → un-done out of order); live set-log hooks override it with a per-row scope (`useSetLogs.rowScope`) so same-row writes stay FIFO while different rows never head-of-line-block each other online. Replay-idempotency is the caller's job: a queued write replayed against a row that already exists must not trip a UNIQUE constraint, so nothing in the queue is a bare INSERT. `useSaveSlotComment` and `useSaveSlotDeviation` upsert on `exercise_slot_id` and the last writer wins; `useConfirmSession` is insert-or-nothing on `session_id` and the first writer wins (next bullet). `AppShell` calls `resumePausedMutations()` on every `online` event; the user-facing surface is [`components/ui/OfflineBanner.jsx`](../src/components/ui/OfflineBanner.jsx), backed by [`hooks/useOnlineStatus.js`](../src/hooks/useOnlineStatus.js). **Both of those read their state, they never mirror it** — `useOnlineStatus` is a `useSyncExternalStore` over the `online`/`offline` events, and the banner's paused-write count is `useIsMutating({ predicate: (m) => m.state.isPaused })`. A `useState` + `mutationCache.subscribe` mirror is the trap here: React Query notifies cache listeners *synchronously*, and `useMutation` builds its observer during render, so the mirror fired `setState` while a sibling was still rendering ("Cannot update a component (OfflineBanner) while rendering a different component") — benign in dev, a tear under concurrent rendering. Video uploads are deliberately **out of scope** — `VideoUploadButton` is gated on `useOnlineStatus()` and flips to a "Connect to record video" hint when offline (Supabase Storage has no resumable-upload story we can lean on). Coach writes are not queued. Logout/login wipes both the in-memory client and the persisted IDB blob via `ClearOnUserChange` in `App.jsx`.
- **A confirm is insert-or-nothing: the first confirmation of a session is the one that stays.** `confirmSessionFn` in [`lib/offlineMutations.js`](../src/lib/offlineMutations.js) upserts on `session_id` with `ignoreDuplicates: true` — PostgREST runs it as `INSERT … ON CONFLICT (session_id) DO NOTHING` — and reads the answer with `.maybeSingle()`. A second confirm is not exotic: it is the replay of a confirm whose first attempt reached the server but whose answer was lost, or a second device whose persisted cache still shows the session as unconfirmed. It writes nothing, so the athlete's note, `performed_on` and the `sessions.performed_at` mirror stay those of the first confirm, and the statement never reaches the UPDATE policy on `session_confirmations`. Both halves are load-bearing. Without `ignoreDuplicates` the same call is `DO UPDATE` on every column of the payload: the replay replaces the note with its own (usually NULL) and moves the training date. With `.single()` in place of `.maybeSingle()` the empty answer of a duplicate becomes a `PGRST116` error — a toast and a rolled-back screen for a session that is confirmed. The mutation therefore resolves the inserted row, or `null` for a duplicate: nothing may read its result as "the confirmation", and `useConfirmSession` refetches `['session-confirmation', sessionId]` on settle. A refusal of the INSERT itself (session archived, block no longer active) still fails the mutation. The only way to change a confirmation is undo, then confirm again — a DELETE, then a fresh INSERT, replayed in that order by the `offline-writes` FIFO scope. The cases are in `src/lib/offlineMutations.test.js`, which sends the request through the real supabase-js query builder and answers `fetch` by PostgREST's rules: a mocked `.upsert()` chain cannot tell `DO NOTHING` from `DO UPDATE`.
- **`['exercise-library']` is one key for two requests, and has to stay one key.** [`useExerciseLibrary`](../src/hooks/useExerciseLibrary.js) is shared: the coach's request carries `coach_id = <their id>`, the athlete's carries no filter (theirs would match nothing, and empty the swap picker of `SessionView` and the picker of `StudentProgramAuthor`). The key is the same for both because `exercise-library` is a persisted root and the entry an athlete's device already holds is what names their exercises offline: a key per user or per role would leave that entry unread. The price is that the cache can hold a list fetched without the filter — restored from a device that ran an earlier client, or read before the profile, and with it the role, had loaded (`RoleGate` renders its page while the role is unknown) — and nothing refetches it when the role arrives, since the key does not change. The hook's `select` therefore applies the coach rule to whatever the cache holds. Do not move that rule into the query function alone, and read the library through the hook: `queryClient.getQueryData(['exercise-library'])` returns the list before `select`.
