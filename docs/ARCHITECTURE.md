# Architecture

A tour of how `sl_app` is wired — data model, client-side caching, auth/RLS boundaries, routing, and the app-specific patterns that aren't obvious from reading one file. Start here when a change could ripple across layers. For per-turn working notes and the file-by-file feature map, see [CLAUDE.md](../CLAUDE.md).

## Stack

- **React 19** + **Vite 6** (base `/sl_app/`).
- **React Router 7 HashRouter** — GitHub Pages hosts static files; `/#/` lets deep links survive.
- **TanStack React Query 5** for server state and optimistic updates.
- **Supabase** for auth + Postgres + Row-Level Security.
- **Tailwind 4** (CSS-based config, `@theme` in `src/index.css`).

## Data model

```
profiles (id PK, role: 'coach'|'student', full_name)
  │ coach_id
  ▼
programs (id, coach_id, student_id, title, sort_order, is_active)
  │   -- periodization blocks per student; ≤1 active via partial unique index
  ▼
weeks (id, program_id, week_number UNIQUE(program_id, week_number), label)
  │
  ▼
sessions (id, week_id, title, day_number NULL|1..7, scheduled_date, sort_order, archived_at)
  │                                                  │
  ▼                                                  ▼
exercise_slots (…, sets, reps, weight_kg,        session_confirmations
                rest_seconds, superset_group,     (session_id UNIQUE, student_id,
                notes, record_video_set_numbers)   confirmed_at, notes)
  │ exercise_id    -- reps/weight_kg/duration_seconds/rest_seconds are now
  │                -- DEPRECATED mirrors of set 1; per-set targets live on set_logs
  ▼                                                │
exercises (library:  name, type 'pull'|'push',   slot_comments (student-authored
           difficulty, volume_weight)             comments per slot per session)
  │
  ▼
set_logs (exercise_slot_id, set_number,
          target_reps, target_duration_seconds, target_weight_kg, target_rest_seconds,
          weight_kg, rpe numeric(3,1) 1..10 by 0.5, done, logged_at)
  │
  ▼ 1:1
set_log_videos (set_log_id UNIQUE, storage_path, mime_type, size_bytes)
```

Side tables:

- **`goals`** + `goal_progress` — a goal is set by a coach (`coach_id`), on an exercise of their library (`exercise_id`), for one athlete (`student_id`, a profile id); the athlete logs attempts against it in `goal_progress` and marks it achieved. The goal goes with its athlete's account (`CASCADE`), and holds its coach's profile and its exercise (`RESTRICT`); its attempts follow it. The coach who set a goal reads and manages it, and reads its attempts, while they coach its athlete; `transfer_student` hands the goals over when the athlete changes coach. See [src/hooks/useGoals.js](../src/hooks/useGoals.js).
- **`exercise_library`** — each coach owns a library; slots, swaps and goals reference it by id, and an exercise that any of them names cannot be deleted (`RESTRICT`). The coach archives it instead (`archived_at`, written by `useArchiveExercise` from the library page, which keeps archived exercises in an "Archived · N" drawer with a restore): the pickers leave it out with `isActiveExercise`, and the rows that name it keep reading it. It is read by its coach, by that coach's athletes, and — since migration `2026_10_16_23_library_read_follows_program.sql` — by whoever reads a slot, a swap or a goal that names one of its exercises: after a change of coach, the athlete and the new coach read the former coach's exercises their training uses.

Volume helper [src/lib/volume.js](../src/lib/volume.js) aggregates `difficulty × Σ(target_reps) × volume_weight` per `type` across a session, summing per-set targets out of `set_logs`. Time-under-tension entries (`target_duration_seconds` set, `target_reps` null) are skipped. Slots with no per-set logs yet fall back to `slot.sets × slot.reps`.

## Per-set targets

Prescription used to live on `exercise_slots` as a single `{sets, reps, weight_kg, rest_seconds}` row that multiplied across every set. As of migration `2026_04_25_per_set_targets.sql`, each `set_logs` row carries both the prescription (`target_reps`, `target_duration_seconds`, `target_weight_kg`, `target_rest_seconds`) and the student's actuals (`done`, `rpe`, `actual_reps`, `actual_weight_kg`; the older `weight_kg` is read and written by nothing). One exercise card can now hold heterogeneous sets — drop sets, back-offs, ramped weight — without spawning multiple slots.

- The legacy `exercise_slots.{reps, weight_kg, duration_seconds, rest_seconds}` columns are kept as deprecated mirrors of set 1, slated for removal in a follow-up migration.
- The reps/seconds **unit** is still slot-level — `exercise_slots_unit_one_of` enforces exactly one of the deprecated mirror columns is set, and a parallel `set_logs_target_unit_one_of` enforces it per-row.
- `useAddSlot` materializes one `set_logs` row per planned set with uniform targets. `useUpdateSlot` fans uniform target edits out to every log; changing `sets` reconciles count by inserting from the last row's targets or deleting orphans. `useUpdateSetTarget` writes to a single log. `useResetSlotToUniform` re-syncs every log to set 1's values.
- A copy carries the `set_logs` targets across, never the actuals — a duplicated session arrives clean. The four hooks of `useDuplicate` are one `supabase.rpc()` call each since wave 2: `duplicate_session`, `copy_sessions`, `duplicate_week` and `duplicate_program` (migration `2026_10_13_12_copy_rpcs.sql`) lock the place the copy goes to, read everything that is copied in one statement — so the copy is the block as it was at one instant, whatever is edited meanwhile — and write the sessions, their exercises and the prescribed sets from what was read, all or nothing. They are `SECURITY INVOKER` and ride the coach's policies, like `move_session`. What a copy holds is decided in those functions and nowhere in the client; a hook returns the function's answer, and shows a toast when `slots_left_out` is not 0.
- `lib/volume.js` exports `isSlotUniform(slot)`, `formatSlotPrescription(slot)`, `formatSetTarget(log)`, `getSlotTargetWeight(slot)`, `getSlotTargetRest(slot)`. Compact "3 × 10 @ 80kg" rendering only fires when uniform; the heterogeneous case shows a per-set list. All helpers fall back to slot scalars when set_logs lack target_* (legacy / mocks).
- Coach editor (`ExerciseSlotRow`) auto-expands the per-set table when targets diverge. "Reset to uniform" requires explicit click — there is no implicit "if matching, collapse"; the coach controls when to leave custom mode.

`day_number` on sessions: a **recommended** weekday, `1=Monday … 7=Sunday`, **nullable** since `2026_08_21_day_number_optional.sql` (NULL = no recommendation). `sessions.scheduled_date` (nullable date) is a recommended DATE and wins over `day_number` for display. Neither is a commitment: order inside a block comes from `sort_order`, and `sessions.performed_at` records the day the athlete actually trained. The student surface has no day strip at all — see the queue section of INVARIANTS.md.

## Program periodization (multiple blocks per student)

A student can have many programs but only one is **active** at a time, enforced by partial unique index:

```sql
CREATE UNIQUE INDEX programs_one_active_per_student
  ON programs(student_id) WHERE is_active;
```

(Migration: `supabase/migrations/2026_04_23_programs_crud.sql`.)

- **The one training surface spans all programs; the QUEUE is active-only.** `StudentTraining` calls `useStudentProgramDetails(userId)`, whose one cache entry holds `weeks` — the tree of the ACTIVE block, which `buildQueue` runs over: a past block's unfinished sessions are work the athlete moved on from, not work still due — and `pastPrograms`, the other blocks as a name and two counts. Finished blocks render below as closed drawers made of those headers; the sessions of one are read by `useStudentPastProgram(userId, programId)` when its drawer is opened, and shown read-only.
- **Coaches browse all programs** via `useProgramsForStudent(studentId)` (list without weeks) and open one via `useProgram(programId)` (detail with weeks). `CopyDialog` picks its destination from the same two — the athlete's list, then the phases of the block chosen in it, each named as the sheet names it (`week.label`, or `coach.sheet.unnamedPhase`) and followed by the places its sessions hold in the block ("Sessions 4–6", "Session 7", "No sessions yet"), which tells two phases of the same name apart. `useActiveProgram(studentId)` resolves "the student's current block" and has no caller in the app.
- **`useProgram` takes `programId`, not `studentId`** — breaking rename during the periodization refactor.
- `useSetActiveProgram` is one call of `activate_program`, which switches the athlete's other programs off and this one on in one statement (the partial unique index allows one active program per athlete). `useCreateProgram` always inserts the program inactive and, with `setActive: true`, calls the same function afterwards — never the current block off first. `useEnsureProgram` explicitly inserts `is_active: true` since the column default is `false`.
- Switching a block off stamps `programs.deactivated_at` (a trigger, whichever request does it), and switching it on empties it. The column is the database's: no hook reads or sends it, and a value sent by a signed-in user is left out without an error. For 72 hours from that time the athlete's writes to the block are still accepted by the policies — see "Read-only gate on past-program sessions".
- Deleting the *active* program is blocked while other programs exist — the coach must activate another first.
- **`useStudentProgramDetails`** is the lighter stats-free fetch (weeks → sessions → slots → library) for the Sessions page. Use it when you need full slot structure without aggregation. **`useStudentProgressStats(studentId?, scope='all', { enabled = true })`** is the heavy aggregate fetch; omit `studentId` for self-stats, pass it from the coach view, and pass `scope` to choose 'all' programs (drafts left out), only the 'active' one, or a specific program id. A page passes `enabled: false` until it knows its scope (`resolveStatsScope` in `src/lib/statsPrefs.js`), and gets the previous scope's figures back as placeholder data while a new scope of the same athlete loads.

### SessionCalendar history overlay

`useStudentHistoricalSessions` fetches dated sessions from the student's NON-active programs (`is_active=false`). When `scope === 'active'`, `StudentDashboard` merges them into the calendar payload flagged `historical: true`. In `SessionCalendar`, a day shows the history dot (muted `--color-ink-400`) ONLY when it has no active-program sessions — active takes visual priority. Historical days are still wrapped in the `<Link>` since the "Students read own sessions" RLS policy is scoped to program ownership, not `is_active`, so students can re-open past sessions read-only. A session is on the day it was trained — `performed_at` read as a date by `performedDate` — and on its `scheduled_date` otherwise.

A day before today with a session not confirmed is not drawn as upcoming. `SessionCalendar` gives it a ring of the muted ink (`--color-ink-400` as an inset `box-shadow`) under a fourth entry of the legend, `statsPanels.legendUnconfirmed` (UNCONFIRMED): it is either an open session whose recommended date has passed or a session trained and not confirmed, which `useStudentProgressStats` puts on the day it was trained with `completed: false`. Today and later days keep the accent dot of UPCOMING, since a session can still be done today. Nothing is called missed — the queue has no such state. Each dot carries its state in `data-dot` (`done`, `upcoming`, `unconfirmed`, `history`).

Under any other scope (`'all'` or a specific past program), the history overlay is suppressed — `useStudentProgressStats` already returns every in-scope session, so layering historical sessions on top would be redundant noise. The hook stays separate because it is the lightest possible fetch (no aggregation), and it is not sent at all outside that scope: `useStudentHistoricalSessions({ enabled })`, which `StudentDashboard` passes as `scope === 'active'`.

### Read-only gate on past-program sessions

A session is read-only for its athlete iff its program is not the active one (`programs.is_active = false`, or the program is in the trash), OR `sessions.archived_at IS NOT NULL`, OR `sessions.reviewed_at IS NOT NULL`. The first two are enforced at two layers, the third in the database. The two layers do not draw the first line at the same moment, on purpose: the screens close a block when it stops being the active one; the database closes it 72 hours later (`programs.deactivated_at`, migration `2026_10_13_17_replay_grace_window.sql`), so that what an athlete logged without a connection is still saved when the coach has switched blocks in between.

- **UI gate** — `useSession` hydrates `session.program_is_active` from the embedded `weeks(programs(is_active))`. `SessionView` derives `isClosed` from that and `archived_at`, then hides Confirm / Undo and swaps in a "From a past program — read-only." (or "Archived by your coach — read-only.") banner. `isReadOnly` (`isClosed`, or `session.reviewed_at` set) is what locks `SetRow` toggles + `SlotCommentBox`; `VideoUploadButton` inherits via the same `locked` prop — upload, replace and delete are disabled, play is not. A reviewed session of the active block is read-only without being closed: it shows `ReviewedLock` (the reason and a link to `/student/messages`) where "Undo confirmation" was, and can still be confirmed if it never was. See "A session the coach has reviewed" in [INVARIANTS.md](INVARIANTS.md).
- **RLS gate** — on `set_logs`, `slot_comments`, `slot_deviations` and `set_log_videos` the athlete has four policies: SELECT is permissive (own-row ownership only) so students can still read their own RPEs, done flags, notes and videos when they re-open a past session via the calendar; INSERT / UPDATE / DELETE ask three questions — `student_profile_for_slot(x) = auth.uid()`, `program_active_for_slot(x) = true`, `session_writable_for_slot(x)`. The helpers are SECURITY DEFINER and STABLE: `program_active_for_session(sess_id)` and `program_active_for_slot(slot_id)` walk session → week → program (migration `2026_04_26_lock_inactive_program_writes.sql`) and answer yes for a program out of the trash that is the active one or — approved — was switched off less than 72 hours ago (`programs.deactivated_at`, stamped by `trg_stamp_program_deactivated_at`; migration `2026_10_13_17_replay_grace_window.sql`); `session_writable(sess_id)` and `session_writable_for_slot(slot_id)` read `archived_at` and `reviewed_at` of the session, and `slot_for_set_log(log_id)` gives the slot of a set for the policies of `set_log_videos` (migration `2026_10_12_08_session_write_gates.sql`). The two upload and delete policies on `storage.objects` ask the same three of the slot named by the path. `session_confirmations` has its own four: SELECT by ownership, INSERT with "not archived" and "program active", UPDATE and DELETE with "program active" and `session_writable(session_id)` — a confirmation can be made on a reviewed session, and not changed or taken back (migration `2026_10_13_09_review_lifecycle.sql`). The INSERT policy of `messages` asks `session_is_confirmed(session_id)` of a feedback message. Coach-side policies are unchanged so coaches can still edit past blocks and reviewed sessions.
- **Why a SELECT/write split, not `FOR ALL`** — Postgres applies the policy's USING clause to SELECT too, so a single `FOR ALL` policy with a write gate would also block reads. That's the exact regression we want to avoid: the student must always be able to *view* their history, even on past programs.
- **Backfill** — `useAddSlot` materializes one set_log per planned set since the per-set-targets migration; older slots relied on the client-side `useEnsureSetLogs` safety-net to lazy-fill missing rows on SessionView mount. Once the lock-inactive-program-writes migration ships, that safety-net INSERT is rejected on past-program slots — so any legacy session that never had its logs materialized while still active becomes visually empty. `2026_04_26_backfill_missing_set_logs.sql` runs once at deploy time to fill in those missing rows from the slot's deprecated mirror columns; SessionView switches the hook off on read-only sessions, where `ensure_set_logs` refuses.
- **Server-side materialization** — `ensure_set_logs(p_session_id)` (migration `2026_10_13_13_ensure_claim_rpcs.sql`) adds the prescribed rows that are missing in one session of the calling athlete and returns how many. It reads `exercise_slots` at the moment of the call, so it cannot bring back a set the coach removed, and it holds the exercises `FOR SHARE` while it reads their `sets`, so an edit of the count waits for the rows. It is `SECURITY DEFINER` and asks the three questions of an athlete's write itself (own session, block being trained, session neither archived nor reviewed) through the helpers the policies use. `useEnsureSetLogs` calls it from the athlete's session page, only when the page counts a prescribed set without a row and the device is online; a database that does not have the function (`PGRST202`) is served by three requests of the hook that read the exercises there as well.

This is the boundary that keeps history immutable when a coach swaps the active program — without it, a student can open an old confirmed session via Stats → Calendar and re-write its `confirmed_at`, distorting recent-confirmations ordering and any timestamp-driven aggregates.

| [useNotifications](../src/hooks/useNotifications.js) | `['notifications', 'list', me]` (newest `NOTIFICATIONS_PAGE_SIZE`), `['notifications', 'unread-count', me]` | mark-read and mark-all invalidate `['notifications']`; realtime events patch the list and the count ([lib/notificationCache.js](../src/lib/notificationCache.js)); the channel's resync invalidates `['notifications']`, on the same occasions and with the same options as the messages one |

A query may derive from another one instead of reading the network: its `queryFn` awaits `queryClient.fetchQuery` on the shared key and reduces the result. `fetchDoneSetHistory` in `src/lib/doneSetHistory.js` is one case of a whole derived read; `useReviewCounts` is another, on a database without `coach_review_counts()`: it awaits `queryClient.fetchQuery(reviewInboxQueryOptions(coachId))` and counts the rows, so the feed opened next finds its inbox read. A smaller form of the same idea: a `queryFn` that only needs one value another query holds takes it with `queryClient.ensureQueryData(<the exported query options>)` and goes on with its own reads — `myStudentIdQueryOptions` in `src/hooks/useStudents.js`, used by the two stats queries. That entry does have an observer (`useMyStudentId`), and `ensureQueryData` joins the read the observer has in flight. The shared entry then has no observer, which is the point — invalidating it costs nothing until something derives from it — and three options are set where it is fetched, not inherited: `staleTime` (how old a read a deriving query accepts), `gcTime` (an unobserved entry is otherwise collected after five minutes, before it is stale) and `retry: false` (the deriving query retries).

The client's defaults — stale after two minutes, refetch on mount, on focus and on reconnect when stale, collected five minutes after the last observer — are changed per ROOT in `src/lib/queryClient.js`, never per hook, for the twelve roots that are persisted. All twelve get `gcTime: PERSIST_MAX_AGE_MS` (14 days, the `maxAge` of the persisted cache). Five get a refetch rule from `REFETCH_RULES`: `session`, `slot-comments`, `slot-deviations` and `exercise-library` are read again when a page opens on a copy older than two minutes but not on a return to the app or to the network before `QUIET_MS` (4 hours), unless the entry was flagged; `['last-performance', 'self', …]` has a `staleTime` of `QUIET_MS`. A hook that reads one of these roots sets no `staleTime`, `gcTime` or `refetchOn…` of its own: an option passed to `useQuery` replaces the root's default.

A read can be made before the page that shows it is opened. `useSession` and `useSetLogs` are each a thin `useQuery` over an exported options object (`sessionQueryOptions(sessionId)`, `setLogsQueryOptions(sessionId, slots)`), and the athlete's training list hands the same objects to `queryClient.fetchQuery` / `prefetchQuery` for the next session of the queue (`readAheadSession` in `StudentTraining.jsx`). One definition per read is the point: what was read ahead sits under the key the page asks for, in the shape its `queryFn` builds. A read that should be available before its page is opened gets an options export of this kind; it does not get a second `queryFn`.

### Reorder writes

Reordering the sessions of a phase (`useReorderSessions`) and the phases of a block (`useReorderWeeks`) is **optimistic, and one request**. `onMutate` rewrites every cached `['program', id]` that holds the phase or the block, numbered the way the function leaves them (`sort_order` 0 to n-1, `week_number` 1 to n); `mutationFn` is one `supabase.rpc()` call of `reorder_sessions(p_week_id, p_ids)` or `reorder_weeks(p_program_id, p_ids)`; `onError` restores the snapshot. `useMoveSession` — a session dragged across a divider, one `move_session` call — draws the same way: the session leaves its phase, and both phases are numbered from the two lists the call sends. The functions (migration `2026_10_13_11_activate_reorder_rpcs.sql`) lock the parent, check that the list is exactly its children (archived sessions included), park every row above every number the parent holds and place them — all or nothing. `(week_id, sort_order)` and `(program_id, week_number)` are unique and not deferrable, which is why parking and placing cannot be two requests. `activate_program(p_program_id)` does the same for the two writes of "Set active". All three are `SECURITY INVOKER` and ride the coach's policies, like `move_session`.

`useReorderPrograms` still sends one request per program, in two passes (park at `sort_order = 100000 + idx`, then `idx`): `programs.sort_order` has no unique key, and the database has no function for it.

Two drags never cross on their way to the database. `useReorderSessions`, `useMoveSession` and `useReorderWeeks` take the block's id and share one mutation scope per block; `useReorderPrograms` takes the athlete's `students` row and has one per athlete (`mutationScope` in `src/lib/mutationScope.js`). TanStack Query sends the mutations of a scope one after the other, in the order they were made, while each still draws its optimistic order at once. Their `onSettled` invalidates only when no later write of the scope is waiting (`laterWriteQueued`), so a run of drags ends in one refetch, made by the last. Their `onError` puts its snapshot back under the same condition: the snapshot is the list from before that drag, without the order a later one has drawn.

A hook keeps its scope for as long as it is mounted. `StudentProgrammingSection` mounts `ProgramSheet` with `key={selectedProgram.id}` and `ProgramSwitcher` with `key={studentId}`: rendered again with another id, a hook would hand its new scope to the write it still has pending (`MutationObserver.setOptions`), and TanStack Query would look for that write's turn in a queue it is not in. The hooks of the sheet the coach has left unmount instead, and their writes are sent as they were made.

`ProgramSheet` is dnd-kit sortable at two levels behind **two explicit modes**, because dragging and vertical scrolling compete for the same axis: the drag handles (6-dot grip) exist only while reordering, and every other control steps out of the way so a drag can't be a mis-tap. **Reorder** (footer) makes the session rows draggable across the whole block — including across a phase divider, which MOVES the session into that phase; each divider is also a `useDroppable`, the only way to reach a phase with no sessions to aim at. **Reorder phases** (a divider's ⋯ menu) makes the dividers draggable and hides the sessions, so a phase is dragged as a whole rather than past twenty of its own rows. One `DndContext` serves both — dnd-kit supports many sortable lists inside one context — and `handleDragEnd` dispatches on which mode is active. Touch drag still needs the 200ms press delay (`TouchSensor` activation) so taps don't trigger drags. Tests that render `ProgramSheet` (directly or via `CoachHome`) must mock `useReorderWeeks`, `useReorderSessions` and `useMoveSession` from `hooks/useWeek`. A drag cannot be made in jsdom — dnd-kit measures a layout that is not there — so `ProgramSheet.test.jsx` wraps the real `DndContext` in a `vi.mock('@dnd-kit/core')` that keeps the sheet's `onDragEnd`, and calls it with `{ active, over }` the way a drop does. `StudentProgrammingSection.test.jsx` does the same around the real order hooks and holds the two `key`s: a write that waits when the coach picks another block, or when the page moves to another athlete, is still sent.

## Auth and Row-Level Security

**Client auth**: [src/hooks/useAuth.jsx](../src/hooks/useAuth.jsx) exposes `{ user, profile, role, isLoading, signOuts, signIn, signOut, guardSignOut, updateProfile, updatePassword }`. `profile.role` is the single gate for coach-only vs student-only surfaces. The provider starts from what the device holds — the session supabase-js stores ([src/lib/storedSession.js](../src/lib/storedSession.js)) and the last profile row read ([src/lib/profileCache.js](../src/lib/profileCache.js)) — so an app opened by its owner renders signed in at once, with or without a network; `auth.getSession()` and `auth.onAuthStateChange` then confirm or correct it. Only `SIGNED_OUT` signs the user out, an event about the same account changes nothing, and the profile is read once per account and launch. `signOut` goes through [src/components/auth/SignOutGuard.jsx](../src/components/auth/SignOutGuard.jsx) when the device holds unsynced writes, and completes without a network by removing the stored session itself. The rules are in `docs/INVARIANTS.md`, "React / hooks discipline".

**Route guards** (in [src/routes.jsx](../src/routes.jsx)): `ProtectedRoute` redirects unauthenticated users to `/login`; the index route (`RedirectToRoleHome`) sends a signed-in user to the role home and waits while the role is not known; `RoleGate allowed="coach|student"` redirects on role mismatch. The guards protect paths — the database enforces access.

**RLS policies** (in [supabase/schema.sql](../supabase/schema.sql)): coach and student policies walk the session → program relationship via two helpers:

- `student_profile_for_session(sess_id)` — returns the assigned student's profile id.
- `coach_profile_for_session(sess_id)` — returns the owning coach's profile id.

Tables like `set_logs`, `session_confirmations`, `slot_comments`, `exercise_slots`, and `set_log_videos` all use these helpers so a policy boils down to `auth.uid() = student_profile_for_session(…)` (student side) or `auth.uid() = coach_profile_for_session(…)` (coach side).

**Who may execute a function.** The helpers are `SECURITY DEFINER`: they bypass RLS, which is what lets a policy on one table look at another without recursing into that table's policies — and what made them a lookup for anyone while every function of `public` was executable with the anon key alone. The grant model since migration `2026_10_11_03_function_grants_lockdown.sql`:

| Role | May execute |
|---|---|
| `anon`, `PUBLIC` | nothing in `public` |
| `authenticated` | the allow-list: the helpers the policies call (`student_profile_for_slot`, `student_profile_for_session`, `student_profile_for_set_log`, `student_profile_for_goal`, `coach_profile_for_session`, `coach_profile_for_goal`, `profiles_are_coach_student`, `is_coach`, `program_active_for_session`, `program_active_for_slot`, `program_is_own_draft`, `week_is_own_draft`, `session_is_own_draft`, `session_writable`, `session_writable_for_slot`, `session_is_confirmed`, `slot_for_set_log`, `set_video_slot`) and the RPCs the app calls (`adopt_swap`, `adopt_skip`, `decline_promote_request`, `approve_program`, `send_back_program`, `save_draft_tree`, `move_session`, `activate_program`, `reorder_sessions`, `reorder_weeks`, `duplicate_session`, `copy_sessions`, `duplicate_week`, `duplicate_program`, `ensure_set_logs`, `claim_push_subscription`, `schedule_rest_push`, `cancel_rest_push`) |
| `service_role`, `postgres` | everything |

Trigger functions are on no list: firing a trigger needs no privilege on its function. The list lives in the `FUNCTION PRIVILEGES` block at the end of `schema.sql`; a function `postgres` creates later is executable by `postgres` and `service_role` only, until a `GRANT` is written. Every function carries `SET search_path = public, pg_temp`. A request without a session is therefore refused — `permission denied for function …` — by every RPC and by every table whose policies call a helper, where it used to get an empty answer.

One function is on no list on purpose: `send_push_event(p_user, p_payload, p_options)` hands a push to the `send-push` Edge Function, and whoever may call it sends any text and any link to any account. It is executable by `postgres` and `service_role`, and `SECURITY INVOKER`: the functions that notify are `SECURITY DEFINER` and call it as their owner. What `send-push` receives from it — the contract between the database and the function — is one JSON object: `user_id` (the recipient's profile id), `payload` (what the service worker shows: `title`, `body`, `tag`, `data.url`), `ttl` (seconds the push service keeps the message for a device that is offline; 86400 unless the caller passes another), and whatever else the caller passed as options, at the top level next to them, never nested. A key the function does not know is ignored by it. The request carries `Authorization: Bearer <INTERNAL_BEARER>`, and the database waits ten seconds for the answer, which it never reads.

Two more are for the service role and the owner only: `claim_rest_push(p_id)`, which hands a rest push to whoever sends it — once — and `dispatch_due_rest_pushes()`, which the optional pg_cron job runs. The first is `SECURITY INVOKER`; the second calls `send_push_event` and is therefore `SECURITY DEFINER`.

`run_retention()` is for the same two and is `SECURITY INVOKER`: it deletes rows by their age in every account, and has no right of its own to do it with. Where pg_cron is switched on, `record_push_failures()` is one more: it reads a table of pg_net and writes a line into `client_errors` that no signed-in user may write, with the rights of the job that calls it.

**Who holds what on a table.** Row-level security decides which rows; the privileges decide whether the statement is looked at at all. Since migration `2026_10_13_14_table_grants_lockdown.sql`:

| Role | On a table or a view of `public` | On a sequence |
|---|---|---|
| `anon`, `PUBLIC` | nothing | nothing |
| `authenticated` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | `USAGE` |
| `service_role`, `postgres` | everything | everything |

The same holds for a table `postgres` creates later (default privileges). The block that says so is `TABLE PRIVILEGES` at the end of `schema.sql`. A request without a session is refused by every table — `permission denied for table …` — before a policy is evaluated; a signed-in user cannot `TRUNCATE` (which row-level security does not see), rebuild a table or attach a trigger to one.

**Who coaches whom.** Both helpers end at `public.students (profile_id, coach_id)`: one row per athlete, naming their coach. It is the root of the model — a coach reads and writes an athlete's programs, sets, videos, bodyweight, goals and messages because a row of this table says so — and it is written by the owner of the database only: the table has no `INSERT` and no `DELETE` policy, and `trg_check_students_link` requires, of every writer, a `coach_id` with the role `coach` and a `profile_id` with the role `student`. Each coach has a library (`exercise_library.coach_id`), written by a coach only (`is_coach()`), and the exercise of a slot or of a swap is taken from the library of the program's coach (two triggers, asked on insert and when the exercise changes). A new athlete is linked in the SQL editor: `docs/runbook/migrations/05-students-role-gate.md`, "Linking an athlete to a coach".

**Changing coach.** `public.transfer_student(athlete, new coach)` is the one way an athlete moves: it rewrites `students.coach_id` — which every "Coaches …" policy follows at once, so the new coach reads the programs, sets, videos and bodyweight and the former one none of them — and `goals.coach_id` of the athlete's goals in the same statement. It is called by the owner of the database or with the service-role key, runs with the rights of its caller, and refuses a request that carries a user id. The exercise library does not move: the athlete's slots and goals keep the ids of the former coach's exercises.

**Rows two sides write.** Three tables hold rows that an athlete may write and that also carry columns which are not theirs. Row-level security decides who may write the row; a `BEFORE` trigger puts the other side's columns back, silently, so the rest of the write is saved: `pin_set_log_targets_for_student` on `set_logs` (for the athlete of the set: the targets, `is_student_added`, `exercise_slot_id`, `set_number`), `pin_program_authoring_columns` on `programs` (for the author of a draft: `status`, `approved_at`, and `submitted_at` once set; `created_by` and `student_id` for everyone) and `pin_draft_session_columns` on `sessions` (for everyone, while the program is a draft: `reviewed_at`, `archived_at`, `performed_at`, `scheduled_date`). A pin is keyed on who writes only where no trigger writes the column on that person's behalf; `sessions.performed_at` is written inside the athlete's request by `sync_session_performed_at`, which is why the pin on sessions is keyed on the status of the program instead — and it is `STABLE`, so that it reads the status the policy read when the coach approves at that very moment.

**The tree of a draft.** A draft (`programs.status = 'draft'`) is written by its author: their own-draft policies on `weeks`, `sessions` and `exercise_slots`, and `save_draft_tree`, which replaces the whole tree on every save. The coach's policies on those tables are `FOR ALL` and do not look at `status`, so a trigger closes the tree to everyone else who carries a user id — `block_draft_tree_write` on `weeks`, `sessions`, `exercise_slots` and `set_logs` (`P0001` `draft_read_only`). The coach acts on the row of the program only: `approve_program`, `send_back_program`, a new name, the trash, a delete. `approve_program` marks the program approved before it writes anything, holds the row until it commits — an author's save that arrives meanwhile waits and is then refused by the author's `UPDATE` policy, which asks for a draft —, and writes every set from the exercise that has no set with a target. After the approval the block is the coach's to edit like any other.

**Accounts, names and roles.** An account is a row of `auth.users`, created by GoTrue — the dashboard's *Add user*, later an invitation; public sign-up is off. The `on_auth_user_created` trigger calls `handle_new_user`, which writes the `profiles` row: `role = 'student'`, and a `full_name` that is never empty (the name in the user metadata, else the part of the address before the `@`, else `'Athlete'`). Everything else follows from two writes only the owner of the database makes, in the SQL editor: `profiles.role = 'coach'` makes a coach, and a row of `students` gives a coach an athlete. `profiles_pin_immutable_columns` keeps the role for every request that carries a user id and refuses a role change that a `students` row stands against; `trg_check_students_link` refuses a link whose two sides do not have the roles. So `profile.role` — the one gate of the client — and `is_coach()` — the one the policies ask — can only be moved by the owner, and the two tables cannot be brought to disagree from either side.

**When you add a table**, add:

1. Both student-side and coach-side policies using these helpers (or equivalents). A new helper is `SECURITY DEFINER`, carries `SET search_path = public, pg_temp`, and is granted to `authenticated` in the `FUNCTION PRIVILEGES` block of `schema.sql` and in its migration — `supabase/tests/function-acl.test.js` fails until it is listed there. The table enables row-level security in the migration that creates it, with its `REVOKE ALL … FROM PUBLIC, anon, authenticated` and `GRANT SELECT, INSERT, UPDATE, DELETE … TO authenticated` next to it, and is defined above the `TABLE PRIVILEGES` block of `schema.sql`; a view is created `WITH (security_invoker = true)`. `supabase/tests/table-acl.test.js` fails otherwise, and `supabase/tests/rls-matrix.test.js` until the table has its insert probe.
2. A migration in the format of [supabase/migrations/README.md](../supabase/migrations/README.md) (file, audit, rollback, runbook page, manifest entry) *and* the same statements merged into [supabase/schema.sql](../supabase/schema.sql).
3. An insert probe for the table in `insertProbes()` of `supabase/tests/rls-matrix.test.js` — the test fails until the table has one.

## Rest push: scheduled by the database, sent once

The end of a rest is a row of `scheduled_pushes`. Migration `2026_10_13_16_rest_push_scheduling.sql` gave the table its state machine and the four functions that move a row through it; `supabase/tests/rest-push.test.js` holds them.

```
                 schedule_rest_push / the INSERT of an app from before wave 3
                                     │
                                  pending ──── cancel_rest_push, the next rest, ───▶ canceled
                                     │         or canceled_at written by an old app
              claim_rest_push(id)    │
              at the time of the push│         a minute after fire_at, unclaimed ───▶ expired
                                     ▼
                                  sending ──── the sender reports ───▶ sent | failed
```

**What the app calls** (a signed-in account; both functions are `SECURITY DEFINER` and ask who calls first):

| Call | Answer | Notes |
|---|---|---|
| `schedule_rest_push(p_seconds int, p_payload jsonb, p_endpoint text default null)` | `{ id, fire_at, mode }` | `fire_at` is `now() + p_seconds` on the server; `p_endpoint` is this device's push endpoint (left out or NULL: every device of the account); `mode` is `'cron'` or `'edge'` |
| `cancel_rest_push(p_id uuid)` | `{ canceled: true \| false }` | `false` is not an error: the row was sent, is being sent, is closed, or is not the caller's |

Refusals: `not authorized` (`42501`, no user id), and with `P0001` the fixed words `rest_seconds_out_of_range` (not 1–900), `payload_invalid` (not a JSON object, or over 2000 bytes) and `device_not_registered` (the endpoint is not one of the caller's `push_subscriptions` — or none was sent and the caller has no device). With `mode: 'edge'` the app then invokes the `dispatch-rest-push` Edge Function with `{ scheduleId: id }`; with `'cron'` it does nothing more. Where the functions are missing (`PGRST202`) the app falls back on its own `INSERT` and its own `UPDATE … SET canceled_at`, which the table's policies still allow.

**What a sender does** (the service role):

1. wait until `fire_at` — the Edge Function by its own means, `send-push` until the `not_before` it was handed;
2. `claim_rest_push(p_id)` → `{ id, user_id, payload, endpoint, fire_at }`, or NULL. NULL means: not yours — somebody else took it, it was canceled, it is more than a minute late, or it does not exist. Stop;
3. read `push_subscriptions` of `user_id`; when `endpoint` is not null keep the one with that endpoint. No device left: record `failed`;
4. send `payload` as it is, with a time-to-live of 60 seconds and high urgency;
5. record the outcome on the row, which is `sending`: `status = 'sent'` and `sent_at`, or `status = 'failed'` and `error`.

**The two modes.** Without pg_cron the app starts the sender itself (`mode: 'edge'`). With the job `sl-rest-push` of the optional migration 19 ("What runs on a timer", below), `dispatch_due_rest_pushes()` runs every ten seconds: it closes the rows more than a minute late and hands each row due within ten seconds to `send_push_event`, whose body `send-push` receives as `{ user_id, payload, schedule_id, not_before, endpoint?, ttl: 60, urgency: 'high' }`. The row is stamped `dispatched_at` and stays `pending`: `send-push` answers at once, waits until `not_before` and goes through steps 2 to 5. An app from before wave 3 still calls `dispatch-rest-push` for its own rows in either mode; step 2 decides which of the two sends.

**How the Edge Function waits.** `dispatch-rest-push` cannot hold a request until the end of a rest: a worker of the platform lives 150 seconds on the free plan, and takes new requests only during the first 75. So it answers `202` at once and works on under `EdgeRuntime.waitUntil`, a minute at a time (`supabase/functions/_shared/restPush.js`):

```
app ── POST { scheduleId }, the athlete's JWT ──▶ hop 1   auth server: whose token? · the row: theirs, still pending?
                                                   │       202 · wait ≤ 60 s · the row again: still pending?
          POST { scheduleId, hop: 2 }, x-internal-bearer
                                                   ▼
                                                 hop 2    the secret, in constant time · the row · 202 · wait ≤ 60 s
                                                   ⋮
                                                 hop n    wait what is left · claim_rest_push · push · sent | failed
```

A rest of 180 s is three requests, one of 900 s fifteen. A hop that finds the rest taken back, or sent by the other sender, ends the chain. A hand-over that fails is not tried again: the rest does not ring, and the log of the function says why. That is the difference with the job of pg_cron, which needs one step for a rest of any length.

**What bounds the table.** An account's rows older than 7 days are deleted when it next rests; rows are never deleted by a sender.

## Retention: what is deleted, and when

Most of the database is kept for good: what a coach planned and what an athlete trained are the point of the app, and no row of them is deleted by its age. Three tables are different — one row per event, of use for a while and of none afterwards:

| Table | What a row is | Of use until | Deleted |
|---|---|---|---|
| `scheduled_pushes` | the end of one rest, to ring on a locked phone | it is sent, taken back, or a minute late | 7 days after it was written — never while it is still to be sent |
| `notifications` | a line of the bell | its recipient has read it | 90 days after `read_at`; never while `read_at` is NULL |
| `client_errors` | what the app reported when it broke | the coach has looked at the list | 90 days after it was reported |

One function does it, `public.run_retention()` (migration `2026_10_13_18_retention.sql`), and answers how many rows of each table it deleted. Nothing calls it. The owner of the database runs it once a month — `docs/runbook/70-admin-procedures.md`, which is also where every other thing the owner does by hand is listed — or, where pg_cron is enabled and the optional migration 19 applied, a job runs it every night. A month without a run costs nothing but the rows that wait.

Two things bound a table without it. `schedule_rest_push` deletes the caller's own rest pushes older than 7 days at the start of every rest, so with the app that calls it only the rows of accounts that stopped training are left for a run; the app from before wave 3 inserts its rows itself, and those wait for a run. And pg_net deletes the answers of the requests the database sends (`net._http_response`) by itself, six hours after they arrive.

A run is safe next to the app: each `DELETE` takes its rows through `FOR UPDATE SKIP LOCKED`, so it never waits for a request that holds one — and that row goes with the next run. Every table of `public` is listed in `supabase/tests/retention.test.js` as deleted by a run, with its age, or as kept for good, with the reason.

## What runs on a timer: pg_cron, where it is switched on

Nothing in this app needs a timer inside the database: a rest push is sent by an Edge Function the app calls, the old rows are deleted by the owner once a month, and a push that could not be sent is in the log of a function. pg_cron is an extension the owner switches on to have the database do all three — `docs/runbook/50-pg-cron.md` is that decision — and the optional migration `2026_10_13_19_pg_cron_jobs.sql` then makes four jobs:

| Job | Schedule (UTC) | Runs | Instead of |
|---|---|---|---|
| `sl-rest-push` | every 10 seconds | `dispatch_due_rest_pushes()` | the app calling `dispatch-rest-push`, which waits in hops of a minute |
| `sl-retention` | 03:17 every night | `run_retention()` | the monthly routine of `docs/runbook/70-admin-procedures.md` |
| `sl-push-failures` | :07 every hour | `record_push_failures()` | reading the log of `send-push` |
| `sl-cron-history` | 03:47 every night | a `DELETE` on `cron.job_run_details` | nothing: pg_cron keeps one row per run — 8,640 a day for the first job alone — and deletes none |

A job runs as the role that made it (`postgres`), in this database. It is made with `cron.schedule(name, schedule, command)`, switched off and on with `cron.alter_job(jobid, active := …)` and removed with `cron.unschedule(name)`: `postgres` reads `cron.job` and may not write it.

`record_push_failures()` is the one function the migration creates. A push leaves the database as a pg_net request to `send-push` (`send_push_event`), sent after the transaction commits, and nobody reads the answer; pg_net keeps each answer in `net._http_response` for six hours. The function writes one line per hour that is over and in which a request was not answered with a status from 200 to 299 into `client_errors` — `role = 'database'`, `user_id` NULL, the hour as `url`, "how many of how many, and what kind" as the message, never what the function answered — and answers `{ hours, failed }`. An hour is written once; every hour pg_net still holds is caught up by the next run. It is `SECURITY INVOKER`, for the owner and the service role.

In `schema.sql` the function and the four `cron.schedule` calls stand inside one `DO` block that asks for the extension first; a database without pg_cron — production today, and the database the tests run on — has none of it, and its ledger does not record migration 19. The migration's rollback removes the jobs and the function and is never refused for a later migration; it also runs where the extension was switched off first, so that the migration can be applied again.

## Migrations and the ledger

Production gets its SQL by hand, one file at a time; the database tests load `supabase/schema.sql`. Three pieces keep the two the same database.

**The manifest.** `supabase/migrations/manifest.json` lists the migrations that follow the format, in apply order, each with a `kind` (`required`, `optional`, `contract`), its wave and checkpoint, whether its rollback is exact (`reversible`) and — on an `optional` migration that needs one — the `extension` the owner must have switched on first (`pg_cron`). `supabase/migrations/manifest.js` reads it and derives, from the name `YYYY_MM_DD_NN_<name>`, the four files of a migration: `supabase/migrations/<name>.sql`, `supabase/audits/<name>.audit.sql` (one read-only query), `supabase/rollbacks/<name>.down.sql` and `docs/runbook/migrations/NN-<name>.md`. The files dated before `2026_10` are history: they cannot be replayed and nothing reads them.

**The ledger.** `app_private.app_migrations (name, applied_at)`, created by migration 01. A migration file is one transaction — `BEGIN`, `SET LOCAL lock_timeout`, a guard, the change, the ledger insert, `NOTIFY pgrst, 'reload schema'` when the API surface changes (a table, a column, a primary, unique or foreign key, a function header of `public` — in the rollback file too), `COMMIT` — and its guard refuses a second run (`SLM01`) and a run before the migration it requires (`SLM02`); a migration that names an `extension` refuses where it is not switched on (`SLM06`). What a migration requires is the nearest `required` migration before it; a `contract` one requires the nearest `required` or `contract` one (`predecessorOf`). `schema.sql` ends with the same schema and table and an `INSERT` of the names of the migrations merged into it — a migration that names an `extension` in a statement of its own, which inserts the name only where the extension is there (`installedBySchemaSql` in `manifest.js` says which names a database installed from the file holds).

**The tests** (`npm run test:db`). `postgres.js` builds two templates per run: `sl_bare` (`shim.sql` only — a Supabase project before any user SQL) and `sl_template` (`sl_bare` + `schema.sql`). `scratchDatabase()` in `harness.js` clones either one for a test that loads SQL files itself, and `db.enableExtension('pg_cron')` switches on, in such a database, an extension production does not have: the stub `supabase/tests/shim-pg-cron.sql`, run as the platform. Neither template has it.

- `parity.test.js`: `sl_bare` + `fixtures/prod_baseline_2026_09_30.sql` (`schema.sql` as it was compared with production on 2026-09-30, frozen, SHA-256 pinned) + the `required` and `optional` migrations must have the catalog of `schema.sql` — twice: as production is, without the migrations that name an `extension`, against `sl_template`; and with each extension switched on right before the first migration that needs it, against `schema.sql` loaded into a project that has them. `catalog.js` reads a catalog as data (`catalogSnapshot`) and lists the differences one line per object (`diffCatalogs`); the rows a SQL file writes are compared one by one for the tables of `REFERENCE_DATA` (the ledger, the storage buckets, the jobs of pg_cron); `catalog.test.js` makes each kind of change, on objects of its own, and checks it is seen.
- `migration-conventions.test.js`: the rules of the format, on the text (`staticProblems`) and by running each migration on the baseline, in order (`checkMigration` in `migration-checks.js`): audit read-only → refused without the migration it requires → applied → refused twice → rolled back (catalog equal to before) → refused twice → applied again (catalog equal to the first time). A migration that names an `extension` gets it switched on right before its turn. A second pass on the baseline applies every migration that is not `optional` (`withoutOptionalProblems`): none may need an optional one. A third, without the extension, runs each migration that names one: it must refuse with `SLM06` and change nothing. The same code is run on deliberately wrong migrations, and the judge of the manifest (`manifestProblems`) on a temporary folder of its own.
- `migration-ledger.test.js`: no API role can read, write or reach `app_private`; the rollback of migration 01 refuses (`SLM04`) while the ledger records a later migration.
- `rls-matrix.test.js`: what six callers can do to every table, against `snapshots/rls-matrix.txt`.
- `rpc-auth.test.js`, `auth-accounts.test.js` and `push-secrets.test.js`: the commands and queries the runbook pages give, read off the page and run.

**The hand-over.** Applying a migration to production is the owner's step. [RUNBOOK.md](RUNBOOK.md) is the index: the rules, the table of checkpoints (which migrations, what else by hand, whether the app is published afterwards) and the sequence of each checkpoint that is ready. [runbook/00-before-you-start.md](runbook/00-before-you-start.md) says how a file is run and what each refusal means, and every migration has its page under `docs/runbook/migrations/`. `src/test/runbookIndex.test.js` holds the index to the manifest (a migration under the checkpoint its entry names; each one audited, applied, audited again, in order; its rollback and page named; the ledger read last) and to the pages (the index repeats their commands and introduces none).

**The deploy gate.** A push to `main` publishes the app, and the SQL that app needs is applied by hand, so `.github/workflows/deploy.yml` has a job between the tests and the publish: `migrations` runs `node scripts/check-migrations.mjs --verify`, which reads `app_private.app_migrations` in one read-only transaction and compares names with `supabase/migrations/manifest.json` of the commit being deployed. A `required` migration that is not in the ledger stops the deploy and is named with its checkpoint and its page; `optional` and `contract` entries are not asked for; a name the ledger has and the commit does not is noted and does not stop anything (an older commit put back). The check fails closed: when the ledger cannot be read — no secret, a refused password, a role without `USAGE` on `app_private` and `SELECT` on the table, a table that row-level security filters for that role — the answer is no, because an unread ledger and an empty one must not look alike. One exception: with no `SUPABASE_DB_URL` at all and the repository variable `ALLOW_DEPLOY_WITHOUT_LEDGER_CHECK` exactly `true`, the job is green without reading anything and leaves a warning on the run. That variable never lifts a migration found missing, nor a secret that is set and does not work. `scripts/lib/ledger-gate.mjs` holds the decision and its wording and opens no connection; the command around it connects the way the backup does (`scripts/backup/lib/connection.mjs`). The secret stays in the environment of that one step, in a job without a write token where no install script runs — never in the job that builds and publishes. [runbook/40-deploy.md](runbook/40-deploy.md) is the owner's page.

**Backups.** A backup is data only: the rows of `public`, the accounts and the storage metadata, as text, in one gzip file encrypted in the format of `openssl enc`. The dump reads them in one `REPEATABLE READ READ ONLY` transaction and holds ACCESS SHARE on every table from before the first row to the end: a snapshot does not protect a table against `TRUNCATE` or an `ALTER TABLE` that rewrites it (both leave the table empty for a snapshot taken earlier), so a migration sent while a dump runs waits for it — or gives up on its own `lock_timeout`. The structure is `supabase/schema.sql`, which `supabase/tests/parity.test.js` keeps equal to production; the header of a backup names the commit and the SHA-256 of that file, and lists every column it read. A restore loads the rows with triggers off (`session_replication_role = replica`) into a database built from `schema.sql`, never loads `app_private.app_migrations` (the target's ledger describes the target), and is only accepted when every table reads back equal to the file. `BACKUPS.md` has the commands and the limits.

## Set video uploads

Set videos live in `set_log_videos` (1:1 with `set_logs`, `UNIQUE(set_log_id)`) + private Supabase Storage bucket `set-videos`. Migration: `2026_04_23_set_log_videos.sql`.

- **Path convention**: `<profile_id>/<slot_id>/<set>-<uuid>.<ext>` — the athlete's profile id, then the exercise slot of the set. It is a rule of the database since migration `2026_10_12_08_session_write_gates.sql`: the athlete's INSERT and UPDATE of a `set_log_videos` row require `storage_path` to be under exactly those two folders, and the athlete's upload and delete policies on `storage.objects` require the first folder to be `auth.uid()` and the second (`public.set_video_slot(name)`) to be a slot of their own, in a session that is neither archived nor reviewed, of their active program. Reading: the athlete reads every file whose first folder is `auth.uid()`; a coach reads a file whose first folder is a `profile_id` of one of their athletes only when a `set_log_videos` row of that athlete names it (`storage_path = objects.name`, read under the coach's own policy of `set_log_videos` — migration `2026_10_16_25_storage_video_policies.sql`). A file no row names — the old file of a replace, the file of a deleted video, a cancelled upload — is its athlete's alone, and `docs/runbook/migrations/25-storage-video-policies.md` lists them.
- **The client checks the file before it sends anything** (`videoFileProblem`, `lib/setVideoFile.js`): one of the bucket's three types — `video/mp4`, `video/quicktime`, `video/webm`, compared without parameters and in lower case — not empty, and 25 MB at most (the bucket caps at 30 MB). `VideoUploadButton` asks when the file is picked and writes the reason under the set; the hook asks again for any other caller. A type with parameters (`video/webm;codecs=vp9`) is stored and sent under its bare type (`videoUploadBody`). No client-side re-encoding.
- **The upload is an `XMLHttpRequest`** (`uploadObject`, `lib/storageUpload.js`): `POST <VITE_SUPABASE_URL>/storage/v1/object/set-videos/<path>` with `apikey`, `Authorization: Bearer <the session's access token>` and `x-upsert: false`, and a multipart body whose part named `''` is the file — the request storage-js sends for a Blob. It reports the bytes that left (`upload.onprogress`) and stops on a signal; the service worker has no route for the API's origin, so the count is real. A dropped connection rejects with `code: UPLOAD_NETWORK`, a refusal with the `message` and `statusCode` of the Storage API's body, a cancel with an `AbortError`.
- **Progress and cancel** are kept by set in `lib/setVideoUploads.js` and read by the button through `useSyncExternalStore`: while a clip is on its way the upload/replace button is the cancel button, with the progress drawn around it and a `progressbar` line under the row. Listeners are told once per whole percent.
- **Errors**: a file refused before the upload is written under the set and starts no mutation; an upload that fails is one toast, pushed by the hook (`videoUpload.failed`, `videoUpload.connectionLost`, `videoUpload.wrongType`, or the key `mutationErrorKey` gives for a refusal of row-level security); a cancel says nothing. Deleting uses the query client's toast.
- **Signed URLs** have 1h TTL, keyed by `storage_path` in the query cache so they're reused across players.
- **Replacement uploads** upload the new file first, then UPDATE the row in place (`storage_path`, `mime_type`, `size_bytes` — `UNIQUE(set_log_id)` leaves no room for a second row), then remove the old file best-effort. A failed or cancelled upload leaves the previous video as it was. Deleting removes the row first and the file after it. See "The row of a set video always names a file that exists" in [INVARIANTS.md](INVARIANTS.md).
- **`record_video_set_numbers`** on `exercise_slots` (int[], default `{}`): coach flags any subset of sets per exercise. Student sees an amber "Record" badge on each matching `SetRow`. If the coach reduces `sets` below a picked number, stale entries just don't match any row (no crash). `commitVideoSets` in `ExerciseSlotRow` sorts + dedupes + filters before persisting.

### Coach-section persistence across tab switches

Two flows drive "pick up where you left off" for the rest of a launch, through three `sessionStorage` keys and a mark, all read and written by [src/hooks/useRememberCoachStudentsPath.jsx](../src/hooks/useRememberCoachStudentsPath.jsx); a cold launch starts with none of them, so each tab opens on its root. A fourth key, in `localStorage`, keeps the feedback being written:

- **`sl_last_coach_students_path`** — full pathname (+ search) of the coach's last Athletes-tab view: the athlete page, or the session editor beneath it. Written by `useRememberCoachStudentsPath()` ([src/hooks/useRememberCoachStudentsPath.jsx](../src/hooks/useRememberCoachStudentsPath.jsx)), called once in `CoachHome` — which is the route element for the athlete page *and* the parent of `s/:sessionId`, so one call covers the editor too. The bare roster path is on a skip-write list and can never become the restore target. Read by `CoachHome`'s restore effect when the route is `/coach/students` with no `:studentId`: it takes the athlete page of the saved path (`athletePageOf` — `/coach/students/:studentId`, plus its `?program=` when the saved path was that page; never the editor), checks the athlete is still on the roster, then `navigate(target, { replace: true })`. The full path is still what is written, so the mark below stays exact for a session editor that found nothing. **Cleared by the "‹ All athletes" header link and by a tap on the Athletes tab while it is open** — the coach's explicit "I want the roster" signals. Without that clear the restore effect would bounce them straight back into the athlete they just left, making the roster unreachable from an athlete page.
- **`sl_last_coach_students_path_forgotten`** — the path a page of the Athletes tab found nothing at (an athlete not on the roster, a session that is not there), written by `useForgetCoachStudentsPath` together with the removal of `sl_last_coach_students_path`. `useRememberCoachStudentsPath` does not write a path equal to it, and removes it when it writes another path.
- **`sl_last_coach_session`** — `JSON.stringify({ studentId, sessionId, from? })` for the last-open `SessionReview`; `from` is the coach route that opened it, when it said so. Read through `getLastCoachSession` by `SessionsFeed`'s mount effect (redirects into the saved review, unless the feed was opened with `?student=`), and by `SessionReview` itself to find its origin when the router state is gone. Written once the review's session is known to be there. Cleared by the review's back button, by its "editor" pill, and by the review itself when it learns its session is gone. A tap on the Sessions tab while it is open clears it too, with `sl_last_coach_sessions_student` (`clearLastCoachSessionsTab`).
- **`sl_last_coach_sessions_student`** — the student-id the coach last picked in `SessionsFeed`'s filter dropdown. Written by `handleFilterChange` (removed when the coach picks "All students"). On mount, a dedicated effect copies the saved id back into the `?student=` search param when the URL has none. The filter lives in the URL — the key just repopulates it on return to `/coach/sessions` within the launch, and a tap on the Sessions tab while it is open clears it.
- **`sl_feedback_draft:<sessionId>`** — the text of the feedback being written for that session, one key per session ([lib/feedbackDraft.js](../src/lib/feedbackDraft.js)), in `localStorage`. Written by `SessionFeedbackComposer` as it is typed (blank text removes it) and read when it mounts; removed when the feedback is sent, when the coach finishes without it, and by `SessionReview` once the session is reviewed.

### Back-button routing in coach deep views

Because these deep views are reachable from several entry points (a roster card, a week view, the sessions feed), the previous history entry is unpredictable, so `navigate(-1)` can land somewhere unexpected. Use logical parents instead:

- `SessionEditor` back → the athlete page on the session's block: `/coach/students/:studentId?program=<program_id>` when the session's block is not the active one (`useSession` carries `program_id` and `program_is_active`), the bare `/coach/students/:studentId` otherwise, and the editor URL's own `?program=` while there is no session. It navigates with `replace`, so the system's back from the athlete page does not open the editor again; deleting the session goes to the same place.
- `SessionReview` back → the page that opened it, passed as `location.state.from` (the Program Sheet, its archived drawer, the session editor, the feed with its filter), or `/coach/sessions` when there is none. Still an explicit destination, never `navigate(-1)`.

A page with no single logical parent uses `useBackOr(fallback)` (`src/hooks/useBackOr.js`): `navigate(-1)` when `history.state.idx` is above 0 — the app has a page behind this one — and `navigate(fallback, { replace: true })` on the first entry of the tab. Under a router that does not write to `window.history` (`MemoryRouter`) the first entry is the one whose `location.key` is `'default'`.

Signing in returns to the link that asked for it. `ProtectedRoute` and the unauthenticated catch-all of `routes.jsx` redirect to `/login` with `state: { from }` — the path and query, `loginState(location)` in [`lib/returnPath.js`](../src/lib/returnPath.js) — and `LoginPage` navigates to `returnPathFor(role, from)` once signed in: `from` when it is a string that starts with `/${role}/`, the role's home otherwise (another role's page, `/`, a value that is not a string, `//host`, an absolute URL).

### Nav tab active-state overrides

`BottomNav`'s "Athletes" (`/coach/students`) and "Home" (`/student`) links use `NavLink`'s `end` prop so they only match on exact routes — without it they stay active on all child routes.

The single-student view has **no tab strip** — the athlete is one page of collapsible sections at `/coach/students/:studentId`, with session editing as its only child route (`…/s/:sessionId`). `AppShell` restores each route's scroll offset instead of hard-resetting to top, so stepping into a session and back keeps the coach's place; see the persistence invariant in [INVARIANTS.md](INVARIANTS.md).

For coach tabs, **Students** and **Sessions** both live under the shared `/coach/student/:sid/…` prefix, so a plain `end: false` NavLink would light up BOTH tabs on any deep route. Each tab in `layout/navItems` instead declares a `matches(pathname)` predicate:

- **Students** matches `/coach/students*` OR `/coach/student/:sid/week/…`
- **Sessions** matches `/coach/sessions*` OR `/coach/student/:sid/session/…/review`

`BottomNav` / `SideNav` call `useLocation()` and use `customActive ?? navLinkIsActive`.

The same `matches(pathname)` decides a tap on the open tab: an item may carry `onReselect`, which the navs call from the `NavLink`'s `onClick` — before its navigation — when the item is active and the click is a plain primary one (`reselectOnClick` in `layout/navItems`). Athletes and Sessions use it to forget the place their root would bounce back to. An item may also carry `badge`: `'unread-messages'` draws `messaging/UnreadMessagesBadge` (Messages), `'to-review'` draws `layout/ReviewCountBadge` (Sessions, coach only — the hook behind it is never mounted in the athlete's nav).

## Scroll container

Only `main` (inside `AppShell`) scrolls. `html, body, #root` are `overflow: hidden; position: fixed; inset: 0;` so the mobile keyboard can focus a textarea (e.g. the Confirm-session note) without pushing the sticky `BottomNav` mid-page. `AppShell` is `h-full flex-col`, **not** `h-dvh` — on iOS Safari the two disagree and a second scrollbar appears on `body`.

## App updates

Three files, one per place the code runs, a fourth for what the page knows about its fields, and two for a page older than what is published.

- **The worker** — [src/lib/swHandlers.js](../src/lib/swHandlers.js), wired by three lines at the end of [src/sw.js](../src/sw.js). `handleInstall` waits (or takes over, on a device that has never run a worker of this kind), `handleActivate` leaves the mark for the next worker and claims the open pages, `handleMessage` takes over on `{ type: 'SKIP_WAITING' }`. They are functions of the worker's scope so that vitest can run them.
- **The updater** — [src/lib/appUpdate.js](../src/lib/appUpdate.js): `createAppUpdater({ container, reload, storage, buildId, readVersion })` and the app's one instance, `appUpdater`, started by [src/main.jsx](../src/main.jsx). It registers `sw.js`, follows the registration (`updatefound`, the workers' `statechange`, the container's `controllerchange`), asks the server for a new worker (`check`), and holds the state a component reads through `subscribe` / `getState`: `{ pending, applying, offered, failed }` — one frozen object per change, so `useSyncExternalStore` can read it. `pending` is "a new worker waits behind the active one", "the worker changed under this page" (`stale`) or "an attempt is under way". `apply()` posts `SKIP_WAITING` to the waiting worker — on a stale page there is no worker to tell, and it takes the one that serves the page — and waits for that worker (`awaited`) to be `activated`: `onWorkerState` then calls `arrive()`, which reloads. `controllerchange` comes about a second earlier in Chromium and reloads nothing; it makes the page `stale`. A stale page whose worker is `activated` already reloads at once. A worker that is not `activated` after `APPLY_TIMEOUT_MS`, or that becomes `redundant`, ends the attempt (`giveUp`): no reload, `failed`, and the update is offered again. `apply({ auto: true })` is the page acting on its own, and is the only form the loop guard and the second asking (in `arrive`) apply to.
- **The page** — [components/ui/UpdatePrompt.jsx](../src/components/ui/UpdatePrompt.jsx), mounted in `AppShell` before `ToastHost`. It answers the updater's one question (`watchForSafeMoment(probe)`), names the route change as a moment (`consider()` on `pathname`), and draws the card: "Updating…" while an update is applied — from the message to the worker until the page is replaced — and the offer with "Later" and "Update" otherwise — the sentence above, the two actions in a row below it, because side by side the French and German labels leave the sentence a column of two words on a phone. The card is fixed in the slot of the toasts, above the bottom nav; the offer is not drawn while a field is in use (`fieldWatch.inUse`). "Later" hides the offer until the next moment.
- **The fields** — [src/lib/fieldWatch.js](../src/lib/fieldWatch.js): `createFieldWatch(doc)` and the app's one instance, `fieldWatch`, which listens to the document (`focusin`, `focusout`, `input`, `change`, capture phase) while it has a subscriber — `UpdatePrompt`, through `useSyncExternalStore(fieldWatch.subscribe, fieldWatch.inUse)`. `hasFocus()` and `holdsTypedText()` are two of the probe's five answers; `inUse()` — the focus, or `FIELD_LEFT_MS` after it left a field — decides whether the offer is drawn. `isField` is the one definition of "a control that holds what someone is typing or choosing".
- **The minimum** — `version.json`, next to `index.html`: `{ build, minBuild }`. It is emitted by the plugin that writes the build id into `index.html` (`buildInfoPlugin` in [src/lib/buildInfo.js](../src/lib/buildInfo.js): `makeVersion` at build time, with `MIN_CLIENT_BUILD` from the environment of the build), read by `fetchVersion` (`cache: 'no-store'`, `null` for anything that is not the file) and judged by `isBelowMinimum(BUILD_ID, version)`. The updater takes the reader as `readVersion` and calls it from `readMinimum`: at `start()`, and in every `check()`. Below the minimum the page is `required`: `check()` ignores `CHECK_MIN_GAP_MS` while no update is pending, and `insist` runs every `REQUIRED_RETRY_MS` — `consider({ offer: false })`, the ordinary question without the offer.
- **The page that cannot load a file** — [src/lib/chunkRecovery.js](../src/lib/chunkRecovery.js): `isChunkLoadError(error)`, `createChunkRecovery({ storage, buildId, reload, isOnline, isBusy })` and the app's one instance, `chunkRecovery`, installed by `src/main.jsx` on `window` for `vite:preloadError`. `recover(error)` reloads once per build id when the device is online and `appUpdater.busy()` is not `true`; `reloadNow()` is the reload a person asked for; `isReloading()` tells `ErrorBoundary` to say "Reloading…". It is separate from the updater on purpose: it needs no worker and works where none is registered.

One update, on a phone in the middle of a session: the app comes back to the foreground → `check()` → the new worker installs and waits → `consider()` → a rest timer runs, so the update is offered, not applied → "Later", or nothing → the rest ends (not a moment) → the next return to the app finds nothing in progress → `SKIP_WAITING`, and the card says "Updating…" → `activating`, `controllerchange` → about a second, in Chromium, during which the page is still the old one and still in use → `activated` → the probe is asked once more → the reload, on the route the hash still names, some 15 ms later.

Two windows: the one with nothing in progress applies the update; the worker it activated claims the other one, which hears `controllerchange` without having asked and becomes `pending`: with nothing in progress it reloads by itself, once that worker is `activated` and the probe has been asked again; otherwise it offers the reload.

One page that three deploys went past, in a tab no worker serves (it was opened on Monday with a hard reload, which goes around the worker): the coach opens "Library" for the first time since then → the import asks the server for a file of Monday's build → three builds are kept, and Monday's is the fourth → 404 → Vite dispatches `vite:preloadError` → nothing is being written or typed, the device is online, this build has not reloaded itself yet → `location.reload()` → the page of the build that is published, on the same route. With a feedback half-written in another field of the page the reload does not happen: the import rejects, `ErrorBoundary` shows "A new version of the app is available", and "Reload" waits for the writes that are on their way.

Tests: `src/lib/appUpdate.test.js` and `src/components/ui/UpdatePrompt.test.jsx` run the real updater — and the real rest timer and a real `QueryClient` — over [src/test/fakeServiceWorker.js](../src/test/fakeServiceWorker.js) (`fakeBrowser()`: a container, a registration and workers, with the moves a browser makes, in the browser's order: `find`, `installed`, `waitingWorker`, `activating`, `activated`, and `takeOver` for the last two at once); `src/lib/fieldWatch.test.js` holds the fields; `src/lib/swHandlers.test.js` runs the handlers over a Cache Storage that outlives the workers; `src/sw.test.js` loads `src/sw.js` itself; `src/main.test.jsx` holds the registration and the two plugin options. `src/lib/chunkRecovery.test.js` holds the wordings and the guard, `src/components/ui/ErrorBoundary.test.jsx` the screen and its "Reload" over a real `QueryClient`, `src/lib/errorReporter.test.js` what reaches the list of errors, and the `version.json` half is in `src/lib/buildInfo.test.js` (the plugin's hooks run as a build runs them) and in the last `describe` of `src/lib/appUpdate.test.js`.

## What a deploy publishes

The `gh-pages` branch holds more than the last build:

```
index.html  sw.js  version.json  manifest.webmanifest  favicon.svg  icon-*.png   the last build's; every build overwrites them
assets/<name>-<hash>.js|css|woff2                                                the files of the last three builds
builds/<build id>.json                                                           one record per build that is kept
.nojekyll                                                                        written by the publish action
```

A record is `{ "build": "<id>", "files": ["assets/…", …] }`. The `deploy` job makes the tree in three steps: `git archive` of the branch into `published/`; `scripts/prune-gh-pages.mjs --site published --dist dist`; the action, with `publish_dir: ./published`.

The script is a command line over [scripts/lib/published-builds.mjs](../scripts/lib/published-builds.mjs), which talks to no git and no network — two folders in, one out:

- `readDist(dir)` — the id of the build (the same in `version.json` and in the `<meta>` of `index.html`, or it refuses) and its files under `assets/`.
- `readSite(dir)` — the files under `assets/` and the records of `builds/`; a folder that does not exist is a site nothing was published to.
- `planSite({ site, build, keep })` — decides and touches nothing: `kept` (this build, then the records with the latest ids), `pruned`, `remove`, `adopted` (the record made for a tree that had none), `unclaimed` (files no record names: left alone), `missing` (files a kept record names that are gone), `outOfOrder`.
- `applyPlan(plan, { siteDir, distDir })` — deletes `remove` and the pruned records, copies `dist/` over the tree (a file of the build replaces whatever is in its way, a link included), writes the record of the build, and the record of a tree it adopted.
- `render(plan)` — the lines of the log, and the annotations of the run on GitHub.

`SiteError` is a refusal: exit 1 and nothing written. `--dry-run` prints the plan. Tests: `scripts/prune-gh-pages.test.mjs` runs the command on folders (four deploys in a row from a tree without records, every refusal with the tree compared before and after) and `planSite` alone; `src/test/ciGuardrails.test.js` holds the workflow.

## Session & UI behavior patterns

- **`SessionView` exercise cards** auto-open only the first incomplete group. Every other group (complete or still pending) starts collapsed, so the student always sees exactly one "current exercise". As the last set of group N is marked done, group N collapses and group N+1 opens. Manual taps still win per-group via `manualOpen[groupKey]`. Supersets collapse as a single unit (grouping from `groupSlotsBySuperset`) since sets alternate across slots.
- **`SessionCard`** supports controlled and uncontrolled open state. Pass `open` + `onToggle` to control from the parent (this is how `StudentTraining` enforces single-open accordion behavior). Omit them and the card falls back to its own `useState(defaultOpen)`. `collapsible={false}` pins it open — used for the next-up card. `locked` drops the start affordance for a past block's read-only sessions; `hasLoggedSets` gives such a session the Review CTA when it is neither confirmed nor archived and one of its sets was logged.
- **Exercise Library filtering is client-side.** Search and type-filter state live in `ExerciseLibrary` and are applied with `useMemo` over the already-fetched list — no extra Supabase queries. They apply to the exercises on offer (`isActiveExercise`); the "Archived · N" drawer counts and lists every archived exercise. Search bar + pills are hidden when no exercise is on offer, to keep the add-first flow clean; a library whose every exercise is archived says so (`coachLibraryArchive.allArchived`) above the drawer.

## i18n: dictionaries and fragments

`src/lib/i18n/en.js`, `fr.js` and `de.js` are the base dictionaries. `src/lib/i18n/index.js` exports `messages` — each base dictionary plus that language's **fragments** — and `getMessage(lang, key, params)`, which looks a dotted key up in `lang`, then in English, then returns the key itself.

A fragment is how a package adds strings without editing the three dictionaries: `src/lib/i18n/fragments/<package-id>.<lang>.js`, default-exporting an object with one new top-level namespace. `index.js` loads them with one `import.meta.glob` per language (`fragmentModules`) and `mergeFragments` (`src/lib/i18n/mergeFragments.js`) merges them. The base dictionary always wins: a fragment can add a namespace, never replace one. One glob per language is deliberate, so a language loaded on demand takes its fragments with it.

The integrator folds the fragments into the dictionaries at the end of waves 4 and 9 (copy the namespace, delete the three files); call sites do not change. The rules are in `src/lib/i18n/fragments/README.md` and enforced by `src/lib/i18n/parity.test.js`: three languages with identical keys, a camelCase namespace that exists neither in the base dictionaries nor in another package, non-empty string values, and no file in the folder that no language loads. `src/lib/i18n/usage.test.js` checks every literal `t('a.b')` call in `src/components` and `src/hooks` against the merged English dictionary. Both tests also run on a fixture package (`src/lib/i18n/__fixtures__/fragments/`), so the rules stay tested while the real folder is empty.

**Formatting.** `src/lib/i18n/format.js` is what prints a value in the app's language: `LOCALES` / `localeOf` (language → Intl locale), `toDate`, `formatDate`, `formatTime`, `formatDateTime`, `formatDateRange`, `formatRelativeDays`, `formatNumber`, `dayNames` / `dayName` and `pluralCategory` / `pluralKey`. Every function takes `lang` as its first argument and is pure; the module imports neither React nor `index.js` (which runs under Vite only), so a plain Node script can use it. It holds no dictionary: `pluralKey` returns a key, and `t` resolves it.

## Testing

Unit tests live next to components as `*.test.jsx`. The shared wrapper [src/test/utils.jsx](../src/test/utils.jsx) stacks `ThemeProvider` + `QueryClientProvider` + a lightweight `AuthContext` + `MemoryRouter`. Hooks are stubbed per-file with `vi.mock(...)`. The `useI18n` + `useTheme` hooks both tolerate a missing provider and return no-op English/light defaults — so a component can render in isolation without pulling the whole tree in.

There are three suites, each with its own command and config. `npm test` (`vite.config.js`, jsdom) is the unit suite and excludes `supabase/tests/**` and `docs/**`. `npm run test:db` (`vitest.db.config.js`) is the database suite. `npm run test:docs` (`vitest.docs.config.js`, node) runs the tests under `docs/`; it has no test yet and passes empty. `src/test/docsSuite.test.js` keeps the three apart and checks the format of the snippets in `docs/_pending/`. `src/test/dbSuiteExitCode.test.js` holds, from the unit suite, the one thing CI reads from the database suite: a run with a failed test ends with a status other than 0 (the server library it loads would end the process with 0; `supabase/tests/postgres.js` keeps vitest's code).

The Edge Functions (`supabase/functions/`) are Deno programs, and Deno is not installed where the suites run; CI type-checks them (`deno check`, job `functions`) and nothing else there executes them. So their tests are part of `npm test`: a `*.test.js` next to the source, with `// @vitest-environment node`. `_shared/*.js` holds what a function decides, written against web standards only, and is tested directly. `_test/harness.js` is for the adapters: `loadFunction(name, { env, modules })` imports `<name>/index.ts` with a stand-in `Deno` global (`env.get`, `serve`) and each `jsr:` / `npm:` specifier replaced, and returns the handler; `fakeAdmin(tables)` is the part of a supabase-js client the functions use; `listen(handler)` serves a handler on a port of `127.0.0.1`, which is how `runbook.test.js` runs the runbook's check — a pasted `node` command — against the function.

`src/test/hardcodedScan.js` is test support for the per-folder "no hard-coded text" tests: `scanHardcoded({ root, allow })` parses every source file of a folder with ESLint's parser and lists JSX text, strings rendered as a JSX child and the literal values of text attributes (`aria-label`, `title`, `placeholder`, `alt`, and props such as `label`, `message` or `confirmLabel`). `allow.files` exempts whole files, `allow.text` exact strings or patterns, and `unused` names the allow-list entries that no longer exempt anything. It does not see a string that reaches the screen through a variable, an object or a function call.

`src/test/fakePostgrest.js` is the stand-in for `supabase.from()` in hook tests that read a table which grows: `fakePostgrest({ table: rows | { rows, count, error } | (request) => … })` returns `{ from, requests, requestsTo(table) }`, and a test wires it with `supabase.from.mockImplementation(db.from)`. It keeps the one server behaviour a resolved mock hides — a response is cut at `maxRows` (1000) whatever `.limit()` asked for — and the three things paging depends on: `.order()` sorts, `.gt()` / `.lt()` filter, `.limit()` cuts. Other filters are recorded, not applied; `select(…, { head: true })` answers with a count and no rows; `.maybeSingle()` gives the first row or null, `.single()` the row when there is exactly one and a `PGRST116` error otherwise. `src/test/fakePostgrest.test.js` holds that contract. Tables are served by name, so a test does not depend on the order in which a hook sends its reads.

A hook test that counts toasts ("the coach is told once") builds its client around the mutation cache handler of the app, not a copy of it: `new MutationCache({ onError: appClient.getMutationCache().config.onError })` with `appClient` imported from `src/lib/queryClient.js`, and `vi.mock('../lib/toast')` so that `pushToast` is a spy. Every toast then lands in one list, whether the cache or the hook pushed it, and `expect(pushToast.mock.calls).toEqual([[…]])` fails on a second one. `useDuplicate.test.jsx` and the `useArchiveSessions` tests of `useWeek.test.jsx` are written this way; a hook's own toast is asserted in English, which `useI18n()` falls back to without a provider.

Run the suite from WSL (see [docs/ENVIRONMENT.md](ENVIRONMENT.md)):

```bash
npm test -- --run     # single pass, CI-style
npm test              # watch mode
```
