## docs/INVARIANTS.md — Shell, routing, viewport

Replace the bullet that starts "**Bare `/sl_app/` (no hash) redirects to the role home.**" with:

- **Bare `/sl_app/` (no hash) redirects to the role home — and waits for a role it does not know yet.** iOS PWAs cold-launch at the manifest `start_url` (`/sl_app/`), not at the last-visited hash route, so an authenticated re-launch lands at HashRouter pathname `/`. The `RedirectToRoleHome` index route inside `AppShell` (in [routes.jsx](../src/routes.jsx)) bounces to `/${role}` — without it, the wildcard catches `/` and renders `NotFound`. ## docs/INVARIANTS.md — React / hooks discipline

Add after the bullet that starts "**Test auth is mocked, never provided:**":

- **Who is signed in comes from the device first; `auth.getSession()` only confirms it.** `AuthProvider` ([`hooks/useAuth.jsx`](../src/hooks/useAuth.jsx)) takes its first `user` from the session supabase-js stores (`readStoredUser` in [`lib/storedSession.js`](../src/lib/storedSession.js): `localStorage[supabase.auth.storageKey]`, read synchronously) and its first `profile` from [`lib/profileCache.js`](../src/lib/profileCache.js) (`sl_profile_cache`: `{ id, role, full_name }` of ONE account, the last row read or written; handed out only for that id and only with a role the app has). With both, `isLoading` is `false` from the first render and nothing is waited for. Do not go back to starting from `getSession()`: with an expired access token — an hour after the last refresh, so at most launches of an installed app — auth-js first attempts a refresh, for about 25 s without a network, twice at start-up (its own initialisation, then the call), and then answers `{ session: null, error }` although the session is still stored. The rules for what auth-js says afterwards:
  - **Only `SIGNED_OUT` signs the user out** (and a `getSession()` that answers "no session" *without* an error). A `getSession()` that answers with an error, or rejects, is "could not tell": the provider reads the stored session again (`asStored`) — auth-js keeps it when a refresh got no answer (`AuthRetryableFetchError`) and removes it itself, with a `SIGNED_OUT`, when the server refused. An event that carries no session and is not `SIGNED_OUT` (the `INITIAL_SESSION` of such a launch) says nothing about who is signed in.
  - **An event about the account that is already signed in changes nothing**: same `user` object, no request. auth-js emits `SIGNED_IN` on every return to the tab and `TOKEN_REFRESHED` every hour; a new `user` object re-renders every consumer of `useAuth`. `USER_UPDATED` is the exception (a new e-mail address). Consequence: `user` is the object of the first sighting — read `user.id` and `user.email` from it, nothing that moves with a token.
  - **A profile that is known is never replaced by a failed read**, and the profile is read once per account and launch (`ensureProfile`), again only after a failure: when the network returns (`online`), at the next auth event about the account, and every `ROLE_RETRY_MS` while no role is known at all. Offline it is not attempted. An answer that arrives after the account changed is dropped. `updateProfile` writes the cache too.
  - **`isLoading` means "not known yet who is signed in, or in which role"**, and it never waits for a request that cannot be made: a signed-in account whose role this device has never read goes through with `role: null` when the device is offline (the index route waits, a deep link renders — `RoleGate` lets an unknown role pass).
  - **The cached profile is a copy for the screen.** Anyone can edit their own `localStorage`; nothing is allowed because of it, and no client check may stand in for a policy.
  - **`lib/storedSession.js` follows the library**, and `src/lib/storedSession.test.js` holds it to the real client (stubbed transport): the storage key and the shape of what is stored, "no session" after a refresh that got no answer with the session left in place, the session removed after a refused refresh, and `auth.signOut()` leaving the device signed in when the logout request gets no answer. `src/hooks/useAuth.authjs.test.jsx` runs the provider itself on that client, with time faked: a cold load on a good token (one profile request with a network, no request without), two minutes offline on an expired token, the network back, a refused refresh, the three kinds of sign-out — and the offline one at four moments, one inside each of auth-js's refresh attempts, each followed by the network alone, by a sign-in that fails and by another account's sign-in. An upgrade of `@supabase/supabase-js` that fails either file changes one of the assumptions above.
- **A sign-out always ends signed out, and it is the only thing besides another account that discards what the device holds for an account.** `signOut` of `useAuth`: asks the registered guard first (`guardSignOut` — [`components/auth/SignOutGuard.jsx`](../src/components/auth/SignOutGuard.jsx), mounted once under `AuthProvider` in `App.jsx`), then asks the server (`supabase.auth.signOut()`) unless the device is offline, reads the returned error, and when the server could not be told removes the stored session itself (`forgetStoredSession`). auth-js is not told of that removal and tells no other tab: a second tab of the app learns it from the browser's `storage` event (`isStoredSessionRemoval` in [`lib/storedSession.js`](../src/lib/storedSession.js), listened to by the provider, which then reads the device again) and shows nobody as well — for that tab a session that went away, not a sign-out of its own, so it keeps what it holds for the account. The event of a removal is not proof of one by the time it arrives (that tab may have signed in again): only `readStoredUser()` says, and a session that is written is never taken from the event — who signs in is auth-js's to say (`SIGNED_IN`). `auth.signOut()` removes the stored session only once the server has answered the logout request — with `scope: 'local'` as well, in auth-js 2.103 — so ignoring its error showed the login page on a device that was still signed in at the next launch. Each completed sign-out increments `signOuts` in the context, which is how `ClearOnUserChange` tells it from a session that went away by itself (next section). After a sign-out made here only a sign-in signs the device in again (`signedOutHere`): the flag is cleared by the `SIGNED_IN` event and by nothing else — not by `signIn` itself, so an attempt with a wrong password changes nothing — and until then any other event that carries a session is not heard, the session it stored is removed again, and a late answer of the start-up `getSession()` is dropped. The reason is the refresh of an expired token: without a network auth-js attempts it for about 25 s at a time, one attempt after the other (its initialisation, the provider's `getSession()`, the listener's first event, then its 30-second timer), so an offline sign-out nearly always finds one on its way. When the network returns before that attempt gives up, it comes back with a session, stores it and says `TOKEN_REFRESHED` — and `INITIAL_SESSION` as well, carrying the same session, when it was the attempt behind the listener's first event. The same attempt can land after ANOTHER account has signed in, and auth-js has then stored the session of the account that left over theirs: a `TOKEN_REFRESHED` about another account than the one that is signed in removes the stored session, signs that account out (`signOuts` does not move: it is not a sign-out of theirs, and what the device holds for them stays) and puts the device back under the rule above — they sign in again. A change of account is always a `SIGNED_IN` first, so a refresh about somebody else is never anything but that late attempt. Online, the sign-out is auth-js's default `scope: 'global'`, as in the app that is deployed: it ends the session on every device of the account. The other devices learn it at their next refresh (`SIGNED_OUT`, which is not a sign-out of theirs), so they keep their cache and their unsynced writes for the next sign-in of the same account; `scope: 'local'` would leave them signed in — a product choice nobody has made, to be asked before it is changed. `signOut` waits for `auth.signOut()` for as long as auth-js takes — a second on a network that answers, over a minute on one that reports online and answers nothing while a token is being refreshed. Do not race that call against a timer and fall back to `forgetStoredSession()`: it cannot be taken back, and when it finally completes it removes whatever session the device stores by then — the next account's (tried on the real client: a logout request that hangs, another account signs in, the request gets its answer, the device holds no session). The tap gets its feedback from the control: `signOut` returns a promise that settles when the sign-out is over, or was declined at the guard, and a busy state follows that promise — neither `ui/UserMenu` nor `student/StudentProfile` shows one today. Every "Sign out" of the app must call `signOut` of the context and nothing else: that is what puts it behind the guard, which opens a question (`authOffline.signOut…`) while the client holds a write of the queue that has not settled (`isQueuedWrite`) or a draft that is ahead of the server (`hasUnsyncedDraft`).

## docs/INVARIANTS.md — Offline-safe student writes

Replace, in the bullet that starts "**The persisted blob says whose it is, and a blob left by another account is wiped at launch.**" as `core-persister-wrapper` writes it, the sentences from "That component wipes memory (`queryClient.clear()`) and device (`removeClient()`) in two cases:" up to and including "A blob without `owner` (written before the blobs said) is kept, as before, and labelled with the account that opens it." with:

That component wipes memory (`queryClient.clear()`) and device (`removeClient()`) in exactly three cases: **another account** is signed in than the owner of the cache, **the user signed out of this device** (`signOuts` of `useAuth` moved), or **the cache has no owner and nobody is signed in**. The owner is `cacheOwner.get()` of [`lib/queryClient.js`](../src/lib/queryClient.js): the persister's `getOwner()`, or a variable of that module on a browser without IndexedDB. It is one answer on purpose — the gate of the queue asks the same one (`queueOwner`), and it asks first: a sign-in replays the queue from the auth listener before `ClearOnUserChange` has run, so an owner that only the component knew held no write back, and one account's queued set left under the session of the next. "Nobody is signed in" is, for a cache that HAS an owner, none of the three: it is also what a session looks like that went away without anyone asking — a refresh the server refused, a sign-out on another device or in another tab — and what the device holds then stays, labelled with its owner, for the same account to find again; another account falls under the first case. Wiping on any change of the signed-in user deleted the unsynced workout on the reconnect that should have sent it (nobody → the same person, after an offline launch on an expired token). A cache WITHOUT an owner — a blob written by a build that did not label it (every device of the app as deployed at `main@fc7a552` holds one), or what was read since the last wipe — is taken for the account the device is signed in as when it is opened, and labelled. Opened by nobody it can be kept for no one, and it is wiped at that moment, not when the next account arrives: a write without a label is held back by nothing (`ownsQueue`), and it would leave under the newcomer's session on the replay their sign-in starts. The component decides nothing while auth is loading, and nothing while the blob is still being read (`useIsRestoring()`): a wipe then would be followed by the restore it was meant to prevent, so a sign-out seen in that moment — and the fact that nobody was signed in — is remembered and acted on once the restore is over. It labels the cache only with a KNOWN account.

## README.md — Offline Support (Student Session Logging)

Replace the bullet that starts "- **Per-user scoping**" as `core-persister-wrapper` writes it with:

- **Per-user scoping** — the persisted blob records the account it belongs to. `ClearOnUserChange` in [App.jsx](src/App.jsx) wipes both the in-memory queryClient and the IndexedDB blob when another account is signed in than the one the cache belongs to — also at launch, when the blob was left by another account — and when the user signs out of the device; until then a queued write is not sent under another account's session. A session that goes away by itself (an expired token that cannot be refreshed, a sign-out elsewhere) wipes nothing: the same account finds its cache and its unsynced writes again. A cache that does not say whose it is belongs to the account the device is signed in as, and is wiped when nobody is.

- **Signed in without a network** — an installed app opened offline starts from the session the device stores and the role it remembers ([src/lib/storedSession.js](src/lib/storedSession.js), [src/lib/profileCache.js](src/lib/profileCache.js)): no spinner, no login form, whatever the age of the access token. The role is remembered from the first launch that could read it: a device that has not had one since it got this version (or since the account signed in) opens offline on a sentence that says the account will open once it is back online, not on the app. Signing out works offline as well, and asks first when the device still holds changes it has not sent ([src/components/auth/SignOutGuard.jsx](src/components/auth/SignOutGuard.jsx)).
