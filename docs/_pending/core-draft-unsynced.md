## docs/INVARIANTS.md — Offline-safe student writes

Add after the last bullet `core-mutation-contracts` adds to this section (it starts "**`sl_rejected_writes` (localStorage) is the journal of refused replays, and the only copy of what they carried.**"):

- **A draft tree that holds edits the database does not have says so in its own data, and no read of the server replaces it.** The marker is `tree.unsynced = { rev }` on the `['draft-tree', programId]` entry ([`lib/draftTree.js`](../src/lib/draftTree.js): `markUnsynced`, `markSynced`, `isUnsyncedDraft`, `unsyncedRev`, `nextDraftRev`). It is part of the cached DATA on purpose: the persister stores the data, so the marker is still there after the app was killed — a save that failed is not, React Query only stores paused mutations. `useCreateDraft` and `commit` in [`hooks/useAuthoring.js`](../src/hooks/useAuthoring.js) write the edit and its marker in ONE `setQueryData` and put the same `rev` in the save's variables (`{ tree, rev }`); the `onSuccess` default of `saveDraftTree` (`draftSaved` in [`lib/offlineMutations.js`](../src/lib/offlineMutations.js)) removes the marker only when the tree still has that `rev`, so the answer to one save says nothing about an edit made after it. While the marker is there: the query functions of `useDraftTree` and `useMyDraft` answer from the cache — before asking the server and again when its answer arrives — so a refetch from any source (remount, focus, reconnect, `invalidateQueries`) makes no request and replaces nothing, and `my-draft` keeps the pointer of a draft the server has no row for yet; and `resumeMutationsAndReconcileDrafts` skips its invalidation (`hasUnsyncedDraft`: a marked tree, or a draft write — save or discard — still pending). Whoever adds a write to the draft tree marks it the same way, and whoever adds a read of `draft-tree` or `my-draft` outside those two hooks repeats their guard: an unguarded read puts the tree of before the edits back, or answers "no draft" for one created offline, and the next edit then saves that over the server. `buildSnapshot` (same file as the marker) copies field by field, so the marker never reaches `save_draft_tree`.
- **A marked tree is sent again until the database has it — on reconnect, at launch, when a session appears and on return to the app — and a tree in sync is read again on those same occasions.** `resumeMutationsAndReconcileDrafts` does both and decides between them: `sendUnsyncedDrafts` builds a save from every marked tree that no pending `saveDraftTree` mutation already carries (same key, same `draft-tree` scope and retry policy, variables `{ tree, rev, resend: true }`; offline it pauses, which is what the persister stores), then the reconcile invalidates `my-draft` and `draft-tree` only if nothing is unsynced. Its four callers: the persister's `onSuccess` and the auth listener (through `replayQueuedWrites`), the `online` listener of `AppShell`, and the `focusManager` listener of [`lib/queryClient.js`](../src/lib/queryClient.js) — the return to the app, which is also how a draft the coach sent back or approved shows up without a reload. What a failed save leaves is decided in `draftSaveErrorHandler` (a mutation default, so a save restored or re-sent without a hook behaves the same): **no answer** after the retries of the queue (`isTransientError`) → the tree stays marked, one toast, and the re-sends that follow by themselves are silent; **refused** (`exercise_unavailable`, or any other coded answer) → the tree stays marked, the toast is shown, and that `rev` is remembered in memory (`turnedDown`) so the same snapshot is not sent again by itself — the next edit makes a new `rev`, and a relaunch tries once more; **`draft_not_editable` / `23505` / `42501`** → the server won: the marker is dropped FIRST (it is what keeps the read out), then both roots are invalidated. A refused snapshot that carried a submission takes `submitted_at` back to NULL on the tree and on the `my-draft` pointer: the save is one transaction, so the database did not record it, and a submitted draft cannot be edited — it would stay locked on a tree the athlete has to change. A submission that got no answer is not taken back; it is re-sent, which is the only way it ever leaves, since a submitted draft has no "next edit".
- **`my-draft` and `draft-tree` are kept in the cache for 14 days (`DRAFT_GC_MS`, set with `setQueryDefaults` in `lib/queryClient.js`), not the default five minutes.** An entry nobody observes is collected after its `gcTime`, and what leaves the cache is written out of IndexedDB on the next persist: with the default a marked tree would be gone once the athlete has spent five minutes on another page, or has launched the app without opening the builder. Whatever prunes the persisted cache (by age, by root) must leave a marked tree alone — it has no other copy.

## README.md — Offline Support (Student Session Logging)

Replace the paragraph that starts "Program **authoring** is offline too:" with:

Program **authoring** is offline too: a student can draft a whole program (weeks → sessions → exercises) with no connection. Each edit is an optimistic local write with client-minted ids that syncs as one idempotent whole-tree snapshot (the `save_draft_tree` RPC). Until the database has accepted it, the tree on the device is marked as unsynced: it is never replaced by a read of the server, it survives a relaunch, and it is sent again when the device reconnects, when the app is opened and when the student comes back to it. A draft in sync is re-read on those same occasions, so a draft the coach sent back shows up without a reload. See [src/lib/draftTree.js](src/lib/draftTree.js).
