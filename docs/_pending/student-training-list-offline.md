## docs/INVARIANTS.md — Training is a QUEUE; the calendar is a consequence

Add after the bullet that starts "**Everything already trained sits in a closed `Drawer`**".

To the integrator, before the text: rule 4 of the last bullet depends on the per-root `gcTime` that `core-persist-defaults` (lane offline-core) gives `lib/queryClient.js` in this same wave. Without it the read-ahead lasts five minutes — the client's default — and live item N1 is NOT fixed: this package is not to be counted as closing N1, nor published, before that one is merged. `src/components/student/StudentTraining.offline.test.jsx` says so as an `it.fails`, "the session read ahead stays in memory for as long as the device stores it": once both lanes are in the tree the run turns red on it ("expected to fail"). Delete `.fails` there, replace its `STORED_FOR_MS` by `PERSIST_MAX_AGE_MS` of `lib/queryClient.js`, and fold that snippet before this one. The text below describes the test as it is after that step.

- **The training list is built from two reads, both of them kept on the device, and from nothing else.** [`useStudentProgramDetails`](../src/hooks/useStudentProgramDetails.js) reads `studentProgramDetailsKey(userId)` — `['student-program-details', userId, 'active']`, the one variant of that root `shouldPersistQuery` stores — and `useMyConfirmedSessionIds` reads `['my-confirmed-session-ids', userId]`. A list that reads any other key works on a network and is empty at the next launch without one. The entry is `{ weeks, pastPrograms }`: the tree of the block being trained, and the other blocks as `{ id, name, sort_order, session_count, archived_count }` — two requests in one `queryFn`, failing together, so a block the coach switched off never shows in both places. Before them the `queryFn` reads the athlete's `students` row with `.maybeSingle()`: an account its owner has not linked to a coach yet has none, and those zero rows are the answer `{ weeks: [], pastPrograms: [] }` — stored like any other — not the `PGRST116` error `.single()` makes of them, which the page would show as "couldn't be loaded" over a "Try again" that can never succeed. The header request selects nothing of a session but `archived_at`; a column added to it grows what is re-serialised to IndexedDB on every change of the cache. `select` reads a bare array (the entry of a build that cached the list of weeks) as a block with no past blocks known. `src/hooks/useStudentProgramDetails.test.jsx` holds the key against `shouldPersistQuery`, and `src/components/student/StudentTraining.offline.test.jsx` saves the cache the way the app does, restores it into a client without a network and renders the page on it.
- **The sessions of a past block are a read of their own, made when its drawer opens, and never stored.** `useStudentPastProgram(userId, programId)` — key `studentPastProgramKey`, `['student-program-details', userId, 'past', programId]` — is mounted by `PastBlockSessions`, the body of the drawer, so a closed drawer costs no request (the same `renderBody` rule as above). The row of a closed drawer is made of the header alone: its name, and `session_count` minus `archived_count` unless the archived toggle is on; the toggle's own count adds the `archived_count` of every past block to the archived sessions of the active one. Both keys sit under the root every writer of a program invalidates (`['student-program-details']`).
- **"No program assigned yet" is said by a read that answered, and by nothing else.** `readState` in [`StudentTraining.jsx`](../src/components/student/StudentTraining.jsx) names what the reads of a part of the page amount to — `ready` (each holds data), `loading` (one is on its way, the cache is still being read back from IndexedDB — `useIsRestoring` — or the account is not known), `offline` (one waits for the network, `isPaused`, or `navigator.onLine` is false), `failed` (`isError` on a network) — and the page renders the list only on `ready`. Data always wins: a refresh that failed leaves `isError` next to the last answer, and the answer is shown. The list needs BOTH reads: the block without the confirmations puts the athlete back on its first session, so a missing `my-confirmed-session-ids` is a missing list, not an empty set. `offline` and `failed` render `Unavailable` — what happened, and a "Try again" that calls `refetch({ cancelRefetch: false })` on both reads — under the page's greeting; an open past-block drawer does the same for its own read. Testing `isLoading` alone is the trap: a read that is paused, errored or not yet restored is not loading and has no data, and the empty state of the page is a claim about the athlete's program. The opposite trap is a `queryFn` that throws on an answer: "no row" from the server (an athlete without a coach link, a block put in the trash) is returned as an empty value, never thrown, or the page reports a failure that no retry can clear.
- **When the network returns and the list has nothing to show, it asks again by itself — once.** An effect in `StudentTraining` compares `useOnlineStatus()` with its previous value and calls the same `retry` on the offline → online step when the list is not `ready`. It is a step, not a state: a read that keeps failing while the device is online stops at its message and its button. A client whose `onlineManager` follows `navigator.onLine` resumes a paused read on its own, and the effect's `refetch` joins it; a client that believed it was online at launch has an errored read that nothing else picks up.
- **The next session is read ahead while the list is on screen.** `readAheadSession` hands `sessionQueryOptions(nextId)` (exported by [`useSession.js`](../src/hooks/useSession.js)) to `queryClient.fetchQuery`, then `setLogsQueryOptions(nextId, session.exercise_slots)` (exported by [`useSetLogs.js`](../src/hooks/useSetLogs.js)) to `prefetchQuery` — the two reads `SessionView` holds its spinner for, under the keys and in the shapes its hooks mount, both roots stored on the device. Without it a session that was never opened on the device had nothing to show in the gym. Four rules. (1) The sets are asked for with the slots of the session ROW just cached, not the list's: `useSetLogs` builds its key from the row, and the list may be one coach edit behind it. (2) The effect runs for the next session only, when the list is `ready` — confirmations included, or the first session of the block would be read — and again each time the list is read again (`dataUpdatedAt`), when the network returns and when the queue of writes empties; `fetchQuery` answers from the cache while the copy is fresh, so this is at most one read of the session per stale time. (3) It does not run offline, nor while a mutation is pending or paused (`useIsMutating`): the answer of a read sent before a queued set reached the database would put the ticked sets back as they were. (4) `sessionQueryOptions` and `setLogsQueryOptions` carry no `staleTime`, `gcTime` or `refetchOn…`: those are set per root in `lib/queryClient.js`, and it is that file's `gcTime` which keeps an entry nobody observes — a session read ahead and not opened yet — in memory and therefore on the device. The tests of the page build clients that keep everything for ever (`gcTime: Infinity`) and cannot see this; the last one of `StudentTraining.offline.test.jsx`, "on the client of the app", renders the page on the app's own `queryClient` and asks both entries for their `gcTime` after the read-ahead: at least `PERSIST_MAX_AGE_MS`. What is NOT read ahead: the session's notes, swaps, videos, confirmation and "Last time" hints — the page renders without them, and shows them once it has been opened on a network.

Add after the paragraph that starts "A query may derive from another one instead of reading the network:":

A read can be made before the page that shows it is opened. `useSession` and `useSetLogs` are each a thin `useQuery` over an exported options object (`sessionQueryOptions(sessionId)`, `setLogsQueryOptions(sessionId, slots)`), and the athlete's training list hands the same objects to `queryClient.fetchQuery` / `prefetchQuery` for the next session of the queue (`readAheadSession` in `StudentTraining.jsx`). One definition per read is the point: what was read ahead sits under the key the page asks for, in the shape its `queryFn` builds. A read that should be available before its page is opened gets an options export of this kind; it does not get a second `queryFn`.

## README.md — Offline Support (Student Session Logging)

Add after the bullet that starts "- **Read cache**":

- **Training list and next session** — the list (`/student`) is built from two of the persisted reads, the block being trained and the confirmed sessions, so it opens at launch without a network exactly as it was last seen, past blocks included as closed rows; the sessions of a past block are read when its drawer is opened and are not kept. While the list is on screen with a network, the next session of the queue and its sets are read ahead into the same cache, so the session can be opened in the gym even if it was never opened on that device. When the device holds nothing — a first launch without a network — the page says so and offers "Try again", and it loads by itself when the network returns. "No program assigned yet" is only ever the answer of the server.
