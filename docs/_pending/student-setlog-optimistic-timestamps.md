## docs/INVARIANTS.md — Offline-safe student writes

Add after the bullet that starts "**`sl_rejected_writes` (localStorage) is the journal of refused replays**" (the last one the snippet of `core-mutation-contracts` adds to this section — fold that snippet first).

To the integrator, before the text: the second bullet below depends on the `onSettled` default that `core-mutation-contracts` (lane offline-core) gives the set-log keys in `lib/offlineMutations.js` in this same wave. Without it a set-log write made through the hooks is followed by NO read of the sets. `src/hooks/useSetLogs.optimistic.test.jsx` says so as an `it.fails`, "one read follows the last of them, and it has both": once both lanes are in the tree the run turns red on it ("Expect test to fail"). Delete `.fails` there — nothing else changes in the test — and fold this snippet. The text below describes the tree with both lanes in it. Checked on 2026-10-13 on a throw-away clone that stacks this lane on the head of `lane/w2-offline-core`: the lane's commits apply without a conflict, the test passes once `.fails` is gone, and the suites of `lib/offlineMutations`, `lib/persistence` and `lib/queryClient` pass on top of these hooks.

- **Each step of a set-log write touches one row, and of that row the fields it changed.** The athlete ticks the next set while the last one is still on its way, so several of these writes are alive at once — a dozen when a workout logged without signal is replayed. `useOptimisticSetLogMutation` in [`hooks/useSetLogs.js`](../src/hooks/useSetLogs.js), behind the five set-log hooks, therefore never handles a list. `onMutate` merges `buildPatch(variables)` onto the row (`writeRow`) and returns `{ written, previous }` — the patch, and what those fields held before; that context is stored with every queued write, so it is a few values and not the cached lists. `onError` takes back field by field, and only a field that still holds what this write put there (`Object.is`): a newer write to the same row — the RPE given after a tick that is then refused, a "failed" that wrote over the tick — and every other row keep what they show. `onSuccess` writes the row the database answered into the cache, which is what puts a row right again when a read sent before the write came back without it; it is skipped while another write to the same row is pending (`hasPendingSibling` — found by `logId`, told apart by the identity of the variables object), because that write's optimistic state is newer than this answer and its own answer carries both. `writeRow` answers `undefined` to `setQueriesData` for a list that does not hold the row: a list that is written, even with the same rows, is stamped as read just now, and the lists of the other sessions would look fresh after every tap of this one. Restoring a snapshot of the lists on error is the bug this bullet is about: it took every set ticked since off the screen. The cases are in `src/hooks/useSetLogs.optimistic.test.jsx`, whose requests stay open until the test answers them one by one.
- **The set-log hooks read nothing again by themselves.** They set `onMutate`, `onError` and `onSuccess`, and no `onSettled`: the read of `['set-logs']` once the last set-log write has settled is the default of their mutation key (`refreshAfter` in [`lib/offlineMutations.js`](../src/lib/offlineMutations.js)), which also serves a write replayed after a relaunch and stands down while a replay is being refused. An `onSettled` on the hook would replace that default for every write made live — and a read made between two queued writes comes back without the second one. Two things follow. The `onSuccess` of the hook is the only handler of that name for these keys: an `onSuccess` registered in the defaults of a set-log key would never run for a write made live. And the default finds its mutation by the identity of the variables object, so the hook hands React Query ONE object per write (`atTheTap` builds it, nothing copies it afterwards). `useAddStudentSet`, `useRemoveStudentSet` and `useEnsureSetLogs` are not on these keys and still invalidate `['set-logs']` themselves: they add or remove rows.
- **The moment of a set is put into the variables by the hook, when `mutate` is called.** `useOptimisticSetLogMutation` returns its own `mutate` / `mutateAsync`, which add `at` (ISO) to the variables before React Query sees them — `mutate` is called in the handler of the tap or of the swipe, so that is the gesture. `SetRow` does not pass it and its tests pin `{ logId, done }`. A caller that does pass `at` keeps it. `useToggleSetDone` and `useSetFailed` build their optimistic patch from the same value (`patchForDone(done, at)`, `patchForFailed(failed, at)`), so the row on screen and the row sent carry one timestamp. A new set-log hook goes through the helper, or it sends writes that the mutation layer can only date by `state.submittedAt`. Tests: `src/hooks/useSetLogs.tapTime.test.jsx`.

## docs/INVARIANTS.md — Rest timer

Replace, in the bullet that starts "**Rest timer is an app-wide singleton with one rendering site.**", the sentence "SetRow only writes to the singleton on done/undone transitions; it never reads or renders remaining time." with:

SetRow only writes to the singleton, from its gesture handlers (next bullet); it never reads or renders remaining time.

Add after the bullet that starts "**Rest timer is an app-wide singleton with one rendering site.**":

- **The rest timer and the RPE selector follow the athlete's gestures, never a change of the row.** In [SetRow.jsx](../src/components/student/SetRow.jsx) the handlers of the tap and of the swipe call three functions: `markDone` (the write, `startRestTimer` when the set was pending, the RPE selector opened), `markFailed` (the write, `startRestTimer` when the set was pending) and `clearFailed` (the write, `clearRestTimer`); `handleSkip` clears the rest as well. Between done and failed nothing moves: that rest is already running. There is no effect on `log.done` / `log.failed`, and there must not be one: the row changes for other reasons than a gesture — a queued write that lands, a read that comes back without it, a write that is taken back — and an effect turns each of those into a rest restarted, a selector reopened after the athlete closed it and a rest push scheduled, once per set when a workout logged offline is replayed. The consequence to keep in mind: a tick the database turns down leaves its rest running (the row goes back to pending by a rollback, which is not a gesture). `src/components/student/SetRow.test.jsx` holds every gesture next to its "the row changes by itself" counterpart (a `rerender`), and `SetRow.replay.test.jsx` plays three gestures offline, a read without them and the replay, on the real hooks and cache: two rests started, none cleared, one selector open.
