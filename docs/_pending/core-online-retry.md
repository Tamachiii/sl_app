Replace, in the same bullet, "`AppShell` calls `resumePausedMutations()` on every `online` event;" with:

`AppShell` calls `resumeMutationsAndReconcileDrafts` on every `online` event, which replays nothing while no session can be read;

Add after the bullet that starts "**A confirm is insert-or-nothing: the first confirmation of a session is the one that stays.**":

- **React Query is offline when the device is — the state is read from `navigator.onLine`, not waited for.** `onlineManager` starts at `true` and only moves on a window `online` / `offline` event, and no event fires at launch: left alone, an app opened without signal believes it is online, replays the queue restored from IndexedDB at once, and every write fails and is dropped from the next persist. `syncOnlineManager` in [`lib/queryClient.js`](../src/lib/queryClient.js) sets the manager from `navigator.onLine` when the module is evaluated — before anything can run — and again on `online`, `offline`, `pageshow` and `visibilitychange`. The last two are not decoration: iOS resumes a suspended PWA without firing `online`, and a manager stuck on "offline" holds back every read and every write. Do not seed it later (in an effect, in `App.jsx`): the persister's `onSuccess` runs before the first effect of anything below it. `navigator.onLine === false` is trusted, `true` is not — a request can still fail, which is the retry policy's business. The cases are in `src/lib/queryClient.test.js`, which evaluates the module again for each "launch".
- **A read without a network waits; it is not attempted.** Queries run with `networkMode: 'online'` (`lib/queryClient.js`). Offline, a query is `fetchStatus: 'paused'` at once — `isPaused: true`, `isLoading: false`, and no `error` — and React Query runs it on the manager's offline → online step. Data restored from IndexedDB is rendered in every mode; this setting only decides what happens to the request. Two consequences for a page. It must render "not loading, no data, no error" as *waiting for the network*, not as *empty*: testing `isLoading` alone shows the empty state the moment the page mounts offline. And a test client that claims to mirror the app's defaults says `networkMode: 'online'`. `'offlineFirst'` is the trap here: it always makes one attempt, nothing can answer it (the service worker caches no API response), and postgrest-js re-sends a failed GET after 1 s, 2 s and 4 s — so every read of an offline launch spins for 7 s, twice with `retry: 1`, and ends as an error instead of a paused read.
- **A queued write is not sent without a session, and is not dropped for lack of one.** supabase-js puts the anonymous key on a request when `auth.getSession()` gives it no session — and that is also its answer while an expired token cannot be refreshed, the usual state of a phone coming back to a bad network. The database refuses the anonymous write *with a code* (`PGRST116` on an update, `42501` on an insert), which looks like any refusal and is final. So every function of `MUTATION_FNS` ([`lib/offlineMutations.js`](../src/lib/offlineMutations.js)) first reads the session and throws `AuthNotReadyError` instead of sending; `mutationRetry` ([`lib/networkErrors.js`](../src/lib/networkErrors.js)) retries that error without limit, at most 15 s apart, and React Query turns the wait into a paused mutation as soon as the device is offline or the page hidden. Three things hang on it. (1) The gate is active on the clients `registerOfflineMutationDefaults` ran on — it is that call which makes `AuthNotReadyError` a wait; on a bare `QueryClient` it would be a permanent failure, so there the write is sent as before. A test that registers the defaults on its client must therefore give its mock of `lib/supabase` an `auth.getSession`; without one the write fails at once with a `TypeError`, on purpose. (2) `resumeMutationsAndReconcileDrafts` replays nothing and re-reads no draft while there is no session, and `useAuth` calls `replayQueuedWrites` when one appears: a `SIGNED_IN` where none was known, and every `TOKEN_REFRESHED`. Whoever rewrites the auth listener keeps that call, and keeps it un-awaited (the callback runs inside supabase-js's auth lock). (3) A waiting write sleeps between two attempts and `queryClient.clear()` cannot stop it, so before each attempt the function checks that its mutation is still in the client's cache (`mutationOf`, by identity of the variables object) and otherwise never settles: no request with the next account's session, and no `onError` rollback writing the previous account's rows into the emptied cache. Clearing the client is therefore enough to drop the queue — nothing else has to cancel anything.
- **A queued write that got no answer is sent again; one the database refused is not; and only the queue retries.** `mutationRetry` / `mutationRetryDelay` are set per mutation key by `registerOfflineMutationDefaults`, so a hook that names a `MUTATION_KEYS` key gets them live as well. *No answer* (`isTransientError`) is: `fetch` failed or the body was not JSON — postgrest-js hands both back as an object with an **empty** `code`; a gateway answered in PostgREST's place — an object with no `code`; or the database said "not now" — `PGRST000`–`PGRST003`, classes `08` and `53`, `57P01`–`57P03`, `57014`, `55P03`, `40001`, `40P01` (the schema-cache reload that ends every migration is one of them). Such a write is retried five times, 1, 2, 4, 8 and 16 s apart, and a retry that comes due offline pauses the mutation instead of failing it. Any other code is a refusal and fails once. Waiting for a session does not count against the five (`rankTransientFailure`). The classification reads the *shape* of the error, never its message: Safari words a failed fetch in the language of the phone. The client-wide default stays `retry: 0` and must: a write outside the queue is usually a bare INSERT, and re-sent after an answer got lost it is a second row. Anything added to `MUTATION_FNS` must be idempotent for the same reason.
- **The pages wait for the replay of the queue while it moves, and only then.** `PersistQueryClientProvider` lets no query fetch until the promise of its `onSuccess` settles. That is wanted: a read that came back before the queued writes reached the database would replace the ticked sets on screen with the rows as they were, and nothing refreshes a cache after a replayed write (a hydrated mutation has no hook around it). It is fatal if unbounded: the promise of `resumeMutationsAndReconcileDrafts` settles when the replay has — after the retries of a write, never while one waits for a session — and every page would sit on its spinner behind one queued set. `App.jsx` therefore passes `replayQueuedWrites` (`lib/queryClient.js`), whose promise settles when the queue has been replayed **or** as soon as the replay has to wait: the device is offline, an attempt failed and will be made again, or nothing has settled for `REPLAY_PATIENCE_MS` (5 s: a request that hangs, a token refresh that does). Never hand the provider the replay's own promise, and never hand it nothing. React Query applies the same order on its own on `online` and on focus (`await resumePausedMutations()`, then the refetch), without the limit: while a resumed write waits, that refetch waits with it.

## README.md — Offline Support (Student Session Logging)

Replace "`networkMode: 'online'` parks them as paused; `AppShell` calls `resumePausedMutations()` on every `online` event." with:

`networkMode: 'online'` parks them as paused; the queue is replayed when the cache is restored, on every `online` event and when a session appears — and only while someone is signed in.

Add after the bullet that starts "**Conflict policy**":

- **Failure policy** — a queued write the database refused (a policy, a constraint: an error with a code) fails once. One that got no answer — no network, a gateway page, a database that is restarting — is sent again five times over half a minute, and pauses if the device goes offline meanwhile. And while nobody is signed in (an expired token that cannot be refreshed counts) nothing is sent at all: the write waits for its owner, because supabase-js would send it with the anonymous key and the database would refuse it for good. The rules are in [src/lib/networkErrors.js](src/lib/networkErrors.js). Reads wait as well: without a network a query is paused, not attempted, and runs when the device is back.
