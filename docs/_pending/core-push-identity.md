Add after that bullet:

- **A device's push subscription belongs to the account that is signed in on it, and `claim_push_subscription` is what writes that down.** A browser holds ONE subscription for the app, whoever is signed in, and `push_subscriptions` holds one row per endpoint. [`lib/pushNotifications.js`](../src/lib/pushNotifications.js) never inserts or updates the table: `enablePush` (the toggle), `reconcilePushSubscription` and `resumePushSubscription` (the look of [`usePushAutoHeal`](../src/hooks/usePushAutoHeal.js)) all register the device with `supabase.rpc('claim_push_subscription', { p_endpoint, p_p256dh, p_auth, p_user_agent })` — no user id is sent, the function asks who calls. A subscription the previous user of the device left behind (a session that went away, a sign-out that could not release it, an app deployed before a sign-out released anything) therefore moves to the account that is signed in now, at its first look: that account receives here and the other one stops. Do not go back to an upsert: under the owner-only policies it is refused for the second account of a shared device, which is review P15 — that account could never switch notifications on, and the phone went on showing the first account's message previews. The app still reads (`isPushEnabled`) and deletes (`disablePush`, `releasePushSubscription`) its own rows directly, under those policies. `endpoint_keys_mismatch` — another account holds the address under keys that are not this browser's — is repaired only by `enablePush`, on the user's tap: the browser gives the address up and takes a new one, once. A look never does that.
- **A sign-out releases the device before the session ends, and only this device.** `signOut` of [`hooks/useAuth.jsx`](../src/hooks/useAuth.jsx) calls `releasePushSubscription({ userId })` after the guard has said yes and BEFORE `supabase.auth.signOut()`: the row of the browser's own subscription is deleted (`delete().eq('endpoint', …)` — found by the address of this device, never by the account: `eq('user_id', …)` would switch every phone of the account off) and the browser gives the subscription up (`unsubscribe()`). The order is the rule: the row is the account's own and only its session can delete it, so auth-js is asked once the delete has been answered. The step is best-effort and bounded, and it never throws — a sign-out is never stopped by it. The two halves go at the same time and either is enough (without the row nothing is sent here; without the subscription the push service answers 410 and send-push drops the row); offline the row is not asked for and the browser alone gives the subscription up; a request that hangs holds the sign-out for `RELEASE_TIMEOUT_MS` (4 s) at most. It reads the registration with `navigator.serviceWorker.getRegistration()`, not `ready`, which never settles in a browser where no worker took control. A session that goes away WITHOUT a sign-out (a refused refresh, a sign-out elsewhere) releases nothing: the same account is expected back, and another one takes the subscription over. `src/hooks/useAuth.push.test.jsx` holds the order and each way the release can fail, on the real provider and the real library.
- **Notifications come back with the account that had them on — and a look makes a subscription for nobody else.** Releasing the device at sign-out would by itself switch notifications off, without a word, for an athlete who signs out and in again and for two accounts that share a phone, at every switch. So `releasePushSubscription` writes the account down when it finds a subscription to release (`localStorage['sl_push_resume']`: user ids, newest last, eight at most — ids only), and when that account signs in on the device again the look of `usePushAutoHeal` calls `resumePushSubscription`: the browser takes a subscription and it is claimed. The list is what keeps the old rule true in its new form: **only the toggle and a resume ask the browser for a subscription**, and a resume only for an account on the list, only while `Notification.permission` is still `granted` (nothing is prompted), only when the device holds no subscription. An account leaves the list when the device is registered for it again (`enablePush`, `reconcilePushSubscription`, `resumePushSubscription`), when it switches notifications off (`disablePush`), and when the browser wants the user's own tap for a subscription (`NotAllowedError`, noted as `permission_denied`) — the toggle is the way then, and the look does not ask again. Whether iOS grants a subscription outside a tap, with the permission already given, is not something the test suite can say: on a device where it does not, the account finds its toggle off after signing back in, as it would without this.
- **What stops a notification toggle is a code of `lib/pushNotifications.js`, and the toggle prints `errorKey`.** Every failure of `enablePush`, `disablePush`, `isPushEnabled`, `reconcilePushSubscription` and `resumePushSubscription` is thrown as an `Error` with a `.code`: `unsupported`, `not_signed_in` (also a request that left without a session: `42501`), `permission_denied`, `sw_not_ready`, `offline` (the request got no answer — `isNetworkError` — or the device has no network, in which case nothing is sent and, in `enablePush`, the permission is not even asked for), `endpoint_refused` (`23514` naming `push_subscriptions_endpoint_known_push_service`: the browser's push service is not one the database accepts), `keys_mismatch`, `generic`. `PUSH_ERROR_KEYS` names the sentence of each code and `pushErrorKey(code)` answers `common.pushError.generic` for anything that is not in it. [`usePushSubscription`](../src/hooks/usePushSubscription.js) returns `errorKey` next to `errorCode`, and a toggle renders `t(errorKey)` — never `t('common.pushError.' + errorCode)`, which printed the key itself for an SQLSTATE or the number of a `DOMException`. A new code gets an entry in `PUSH_ERROR_KEYS` and its sentence in the three languages; `src/lib/pushNotifications.test.js` fails on a key the dictionaries do not have. Two things the hook does with a failure: a switch-off that removed neither the row nor the browser's subscription leaves the toggle ON (the device still receives), and a toggle that cannot ask the database whether the device is registered shows what the device itself last wrote (`lastHeal(userId).ok`) with the `offline` sentence, not a plain "off". When it opens, it also prints a failure of the background look that does not go away by itself (`LASTING`: `endpoint_refused`).
