## docs/INVARIANTS.md — Offline-safe student writes

Add after the bullets `core-online-retry` adds to this section (the last of them starts "**The pages wait for the replay of the queue while it moves, and only then.**"):

- **A set is dated at the tap: `logged_at` and `failed_at` are never read from the clock of the request.** A set ticked without signal is sent when the phone finds a network again — the evening, or days later after a relaunch — and `performed_on` (the earliest `logged_at` of the session), "N days ago", the recent records and the bodyweight of a ×BW ratio all follow that timestamp. So the moment travels with the write: a set-log hook puts `at` (ISO) in the mutation variables, where its optimistic patch reads it too, and `patchForDone(done, at)` / `patchForFailed(failed, at)` in [`lib/offlineMutations.js`](../src/lib/offlineMutations.js) build the patch from it. The variables are what the persister stores. A write that carries no `at` (queued by an older build, or by a hook that does not send it) is dated by `state.submittedAt` of its mutation — React Query sets it on the tap and it is persisted with the queue — which `queuedWrite` hands to the function as `madeAt`; only a call that knows neither reads the clock. A value that is not a date is skipped, not sent. Whoever adds a write that stamps a moment takes it from the variables the same way (`tapTime`); `new Date()` inside a function of `MUTATION_FNS` is the bug this bullet is about.
- **The reads a workout write makes stale are refreshed by the defaults of its mutation key, not by the hook.** A hook exists while its page does; a workout logged offline is usually replayed after the app was killed and opened again, by mutations that have nothing but the defaults `registerOfflineMutationDefaults` registered. `refreshAfter` is their `onSettled`: confirm and undo invalidate `session-confirmation`, `my-confirmed-session-ids`, `week-confirmed-session-ids`, `program-confirmed-session-ids`, `student-progress-stats`, `student-records` and `student-lifetime-stats`; a note or a deviation invalidates `['slot-comments', sessionId]` / `['slot-deviations', sessionId]` (the whole root when the variables name no session — `[root, undefined]` matches nothing); a set-log write invalidates `['set-logs']` once, when no other `set-log` write is left unsettled. That last test is not `isMutating(...) === 1`: sets restored after a relaunch leave in parallel (see the "Replay ordering" sentence replaced below), and when two answers arrive in the same turn each write still sees the other as pending — so `settling` counts out the writes already in their `onSettled`. Three things follow. (1) A hook on one of these keys adds `onMutate` and `onError` (the optimistic update and its rollback) and **no `onSettled`**: an option set by the hook REPLACES the default of the same name, it does not run next to it, and its list would be the one that silently stops matching. (2) A new read that a confirmation changes is added to `CONFIRMATION_READS`, not to a hook. (3) The refresh is started and never returned: `onSettled` keeps its mutation pending for as long as the promise it returns, and with it the next write of the FIFO scope.
- **A write that waited and is then refused because its session was closed gets one message, a journal entry and no refresh.** An athlete's write is accepted while their program is the block being trained (with 72 hours of grace after a block switch once migration 17, `replay_grace_window`, is applied) and the session is neither archived nor reviewed. Past that, every write of a workout logged offline comes back with `PGRST116` (an UPDATE read back with `.single()` that matched no writable row) or `42501` (an INSERT its policy turned down, or the trigger on undoing a reviewed confirmation) — `isClosedToAthlete` in [`lib/mutationErrors.js`](../src/lib/mutationErrors.js). `queuedWrite` treats such a failure apart when the write had WAITED: its mutation was restored from IndexedDB, was paused while the device was offline, or was kept waiting for a session (`waited`; a mutation that is "paused" behind another one of its scope on a working network has not waited). Then: the error is marked (`isRefusedReplay`), the client's `MutationCache.onError` in [`lib/queryClient.js`](../src/lib/queryClient.js) shows no toast for it, and `refuseReplay` pushes `offlineReplay.refused` ONCE per replay — from the first refusal until no workout write is pending; the write is appended to the journal; and `refreshAfter` is skipped until the queue is empty, so the mutation layer does not replace the workout on screen with the rows the database kept. A refusal of a write that had not waited, and any other code, stay ordinary failures (generic toast, the hook's rollback, the refresh). Draft writes are outside all of it: `draftSaveErrorHandler` has its own answer to `42501`.
- **`sl_rejected_writes` (localStorage) is the journal of refused replays, and the only copy of what they carried.** `recordRejectedWrite` appends `{ refused_at, made_at, user_id, write, variables, code, message }` — `write` is the name in `MUTATION_KEYS`, `variables` what the athlete did (set id, done or failed, RPE, actuals, note, tap time). Capped at `REJECTED_WRITES_CAP` (300) entries, oldest out first; reading and writing never throw. It is not part of the query cache: `queryClient.clear()` and the IndexedDB wipe leave it, so signing out does not destroy the only copy. Entries carry the `user_id` of the session that sent them: a reader shows a user only their own, and the code that handles a real change of account decides what becomes of the others (`clearRejectedWrites` empties the journal). Nothing in the app reads the journal yet.

Replace, in the bullet that starts "**Offline-safe student writes are wired through one allow-list.**", the sentence that starts "**Replay ordering is scope-based:**" (it says that hydrated-after-reload mutations replay strictly FIFO in the `offline-writes` scope, which React Query 5.100 does not do for a write whose hook set a scope) with:

**Replay ordering is scope-based:** the registered defaults carry `scope: { id: 'offline-writes' }`, so the writes whose hook sets no scope — the confirmation, a note, a deviation — replay strictly FIFO; the set-log hooks set a per-row scope (`useSetLogs.rowScope`), so two writes to the same row stay in order (done → un-done cannot land reversed) while different rows never head-of-line-block each other. React Query stores a mutation's `scope` with it (`dehydrateMutation`), so a set-log write restored after a reload KEEPS its per-row scope: after a relaunch the sets of different rows go out in parallel, and the confirmation can reach the database before the last of them — one more reason the session lock is `reviewed_at`. Anything that needs "the queue has drained" therefore looks at the mutations still pending, the way `refreshAfter` does; there is no "last one in order" to wait for.

## README.md — Offline Support (Student Session Logging)

Add after the bullet that starts "**Conflict policy**" (and after the "**Failure policy**" bullet of `core-online-retry`):

- **When a set was done** — `logged_at` / `failed_at` are the moment of the tap, carried in the queued write, not the moment the request is sent: a workout logged offline and synced the next day keeps its day.
- **A workout the database no longer accepts** — if the coach closed the session or switched block while the phone was offline (past the 72-hour grace), the replayed writes are refused. The athlete gets one message for the whole workout instead of one error per set, and each refused write is kept in `localStorage` under `sl_rejected_writes` (what was done, when, by whom) so it can be read back and entered by hand. See [src/lib/mutationErrors.js](src/lib/mutationErrors.js).
