# Street Lifting Coach (sl_app)

A responsive React application for coaches and students to plan, track, and execute street-lifting / calisthenics training programs. Mobile-first design with a bottom tab bar; on desktop (≥ 768px) the nav promotes to a left sidebar and content caps at `max-w-5xl`. Coaches design a block as an ordered list of sessions (optionally grouped into named phases); students work through it at their own pace, logging sets, reps, weight, RPE and completion. The calendar records what actually happened rather than dictating it.

Deployed to GitHub Pages: https://tamachiii.github.io/sl_app/

## Quick Start

### 1. Install
```bash
npm install
```

### 2. Configure env
Create `.env` (gitignored):
```
VITE_SUPABASE_URL=https://<project>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon-key>
VITE_VAPID_PUBLIC_KEY=<base64url public key>   # optional, enables rest-timer Web Push
```
See `.env.example`. Generate the VAPID pair once with `npx web-push generate-vapid-keys --json`; ship the **public** key here and put the **private** key + `mailto:` subject in Supabase function secrets (`VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`). The Web Push feature degrades gracefully when these are unset — the Profile toggle just shows "not supported".

### 3. Database
Apply `supabase/schema.sql` to a fresh Supabase project (creates tables, RLS policies, and a trigger that auto-creates a `profiles` row on signup). It is the install path: a database made from it starts with every migration recorded as applied.

An existing project is brought up to date one migration at a time, by hand, following [docs/RUNBOOK.md](docs/RUNBOOK.md) — never by pasting `schema.sql` again.

### 4. Run
```bash
npm run dev       # dev server
npm run build     # production build → dist/
npm run preview   # serve dist/
npm run lint      # eslint, correctness-only, with a warning ceiling of 26; also runs in CI
npm test          # unit suite (vitest, 1421 tests)
npm run test:db   # database suite: schema.sql and the migrations on a real PostgreSQL 17 (see Database Tests)
npm run test:docs # tests about the docs (under docs/); empty — the tests that would hold the docs to the code are in docs/BACKLOG.md
npm run deploy    # emergency-only manual publish (CI deploy is the normal path)
```

## Domain Model

```
profiles (id, role: 'coach'|'student', full_name)
  ↓ 1:many (coach_id)
programs (id, student_id, name, sort_order, is_active)  -- periodization blocks; ≤1 active per student
  ↓ 1:many
weeks (id, program_id, week_number, label)
  ↓ 1:many
sessions (id, week_id, title, day_number?, sort_order, scheduled_date?, performed_at?)
  -- day_number / scheduled_date are RECOMMENDATIONS; performed_at is the day it was really trained
  ↓ 1:many                                ↓ 1:1
exercise_slots (…, notes,               session_confirmations (session_id UNIQUE, student_id,
  record_video_set_numbers)               confirmed_at, notes)
  → exercise_library (…)
  ↓ 1:many
set_logs (…)
  ↓ 1:1
set_log_videos (set_log_id UNIQUE, storage_path, mime_type, size_bytes)
```

Each coach has their own exercise library; each student can have many **programs** (periodization blocks) but only one is active at a time. Students see only the active program; coaches browse all. When a program becomes inactive, its sessions become read-only on the student surface — Confirm/Undo are hidden, set logs lock, and the student-side RLS policies on `set_logs`, `session_confirmations`, and `slot_comments` reject writes. Coach edits stay open across all blocks.

`set_logs` doubles as both prescription and log: each row carries the coach's per-set targets (`target_reps`, `target_duration_seconds`, `target_weight_kg`, `target_rest_seconds`) alongside the student's actuals (`done`, `rpe`, `weight_kg`). The compact "3 × 10 @ 80kg" UI is shown when every set's target matches; otherwise a per-set list appears (drop sets, back-offs). Coaches toggle "Customize sets" in the editor to expose a per-set table; "Reset to uniform" syncs every row back to set 1.

When a student can't follow a set as written, they log what they **actually** did via `set_logs.actual_reps` / `actual_weight_kg` — an "Actual" control on each set, prefilled from the target. Anything left equal to the prescription is stored as `null`, so a populated `actual_*` always marks a real deviation; the coach sees these in an "Off-plan" band on the session review. The coach-owned `target_*` columns stay immutable to students at the DB level via the `pin_set_log_targets_for_student` trigger.

Students can also take a session off-script structurally without touching the coach's plan: **swap** an exercise for another from the coach's library or **skip** it entirely (the `slot_deviations` table, one row per slot), **skip** a prescribed set or **add** an extra one (`set_logs.skipped` / `is_student_added`). The coach is notified the first time a slot goes off-script (`notify_coach_on_slot_deviation` → in-app bell + Web Push) and sees the swap/skip and any skipped/extra sets on the session review. Substitutes are library-only (no free-text) so volume/progress stats stay intact.

What the app does in more than one row at a time is a function of the database, called through `supabase.rpc()`: the draft save and its approval (`save_draft_tree`, `approve_program`, `send_back_program`), adopting or declining an athlete's deviation (`adopt_swap`, `adopt_skip`, `decline_promote_request`), moving a session (`move_session`) and — in the database since the migrations of wave 1, called by the app from wave 2 — setting a block active and reordering (`activate_program`, `reorder_sessions`, `reorder_weeks`), copying (`duplicate_session`, `copy_sessions`, `duplicate_week`, `duplicate_program`), adding a session's missing sets (`ensure_set_logs`) and registering a device (`claim_push_subscription`) — and, from wave 3, scheduling and taking back a rest push for this device (`schedule_rest_push`, `cancel_rest_push`) and reading the coach's sessions to review and conversations in one request each (`coach_review_counts`, `my_conversations`, of the optional migration 26: without it the app reads the same lists page by page). Who may execute what is in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), "Auth and Row-Level Security".

Deep architectural details — RLS helpers, React Query invalidation, routing/persistence, set-video storage, calendar history overlay — live in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Roles & Flows

**Coach**
1. Logs in → the **Athletes** roster (`CoachHome` at `/coach/students`) — a searchable, attention-first list of athletes. Athletes who need you are listed under **To follow**, the others under **Up to date**. Each row carries one status by urgency — **no active program**, **sessions to review** (a link to their sessions), **quiet for N days** —, the athlete's position in their block ("Session 7 of 24") and the day of the next session, and the week's dots: trained, today, next — there is no "missed", because a recommended day passing just leaves the session next in the queue. All derived client-side, no new query. Ordered attention-first, then A–Z; a search box filters by name/program. The old Dashboard is merged in here (`/coach/dashboard` redirects), and the client-error triage collapses at the bottom. Tap a card to open their single-student view.
2. **Single-student view** (`/coach/students/:studentId`) — the whole athlete on **one page, no tabs**: a "← All athletes" back link, then the athlete's name as the page title, a row of two actions (**Message** and **Sessions**), then collapsible sections. **Programming** is open by default (the **Program Sheet**: a block picker over the block's sessions, one section per phase — its name and the places its sessions hold — and one row per session: its place in the block, its name, whether it is done or in progress, its recommended weekday and how many exercises it holds; the sessions already done at the head of a phase fold into one row, so the whole plan is readable without navigating. Tap a session to edit its exercises in a full-width pane that stays *inside* this shell, so the athlete context never disappears. Once the athlete has trained a session — confirmed it, or logged a set in it — the same tap opens its review instead, and the review has an **editor** button: a confirmed session is read-only there, and a session in progress has its logged sets locked while the rest stays editable. A row's ⋯ duplicates it and sets — or clears — a *recommended* day; « Choose » selects sessions across phases to copy or archive them from a bar at the bottom; each phase's ⋯ menu duplicates, copies or deletes it; the program menu can **duplicate** a whole block — an inactive copy of every week/session/target, no logged training — to seed the next one), with **Goals** and **Stats** collapsed beneath it. Section open/closed state is remembered, and a collapsed section is unmounted rather than hidden so it costs no query. Opening a session keeps the header and restores your exact scroll position and open week on return; the editor also carries a **Last time** panel showing the equivalent earlier session, labelled with the date it was actually trained, so you can write against what the athlete really did without navigating. Every former tab URL (`…/programming`, `…/progress`, `…/profile`, `…/goals`, `…/stats`, `…/messaging`) redirects to the page.
3. **Sessions tab** (`/coach/sessions`) — a needs-review inbox by default (confirmations awaiting review, with a pending count); the **All** toggle restores the full history. Arriving for one athlete — from the roster's "to review" chip or the athlete page's **Sessions** action — opens on that athlete's sessions to review, or on their full history when none is left. The review's back button returns to the page it was opened from. Tap a card to open `SessionReview`.
4. **Messages tab** (`/coach/messages`, `/coach/messages/:otherProfileId`) — conversation rollup over every student, plus "start a conversation" cards for students with no thread yet. Unread count appears as a dot on the bottom-nav icon (count chip in the side-nav). Tapping the kebab on an outgoing chat bubble opens a confirm dialog and deletes the message for both sides via realtime; coach session-feedback bubbles (the "Re: <session>" cards) are pinned and don't expose the action. The most recent outgoing bubble carries an iMessage-style "Sent" / "Read · {time}" caption fed by `messages.read_at` so the sender knows whether the recipient has opened the thread. Realtime updates via the Supabase `messages` channel keep threads + the badge live across tabs.
5. **Library tab** — exercise CRUD with search + type filter. Deleting an exercise first shows where it is used (program slots, goals, athlete swaps) and is offered only when nothing uses it.

**Student**
1. Logs in → **Training tab** (`/student`) — one page, one list (the Parc design, `design/parc/screens/Entrainement.dc.html`). Under the title, the block and their place in it (« Force tirage, séance 7 sur 24 ») and the week in seven dots; then the next session as an open panel — when, its exercises with what each asks for, « Commencer la séance » —, the sessions after it under « Ensuite », and « Historique »: closed rows for this block's finished sessions (ordered by the day they were really trained) and one per past block, read only when opened. Miss a Sunday and it is still simply next — nothing to re-date. There is deliberately no Mon–Sun grid with arrows: the month calendar in Stats is where "when did I train" belongs.
2. The **session** (`/student/session/:id`) shows one exercise at a time: the set in progress in large digits with **last time** under it (« Il y a 7 jours, 5 × 5 à 17,5 kg »), the sets as rows, « Valider la série n » at the bottom and the RPE in a sheet after it; a long press marks a set failed, with « Annuler » in a toast.
3. **Stats tab** (`/student/stats`, `design/parc/screens/Stats.dc.html`) — the block chosen in chips; **performance-aware** volume per week as pull and push columns over the real calendar weeks trained, with the sets done of the last week; « Progression »: per exercise, the last session's tonnage and how it moved, the chart of an exercise on a date axis opening under its row (dashed planned reference when you deviated); **records** per exercise (estimated 1RM via Epley, best set, « Nouveau » for a recent best, the strength relative to bodyweight); the **bodyweight** with its last six weeks and « Saisir mon poids »; the summary (sessions, sets, average RPE) and the month calendar of the days really trained (active block + muted history dots).
4. **Messages tab** (`/student/messages`) — single thread with the assigned coach (resolved via `students.coach_id`). Realtime + unread-count badge same as the coach side.
5. **Profile** (`/student/profile`, reached by tapping the avatar in the header — not a tab) — display name + initials avatar, "Your coach" card with a Message shortcut, lifetime totals (sessions completed, sets done, total volume), the active goal (with a "View all" link into the full Goals page), theme/language preferences, and account controls (email, change password, sign out). The student-side `UserMenu` retired its popover when this page shipped; everything that used to live there now lives here. Coach-side `UserMenu` keeps the popover.
6. **Goals** (`/student/goals`, reached from Profile's "Active goal" card) — `MyGoals`. The student-side bottom nav is 3 tabs; Goals is a Profile-routed surface rather than a top-level tab.

## Design System, Theming, and i18n

The app is drawn with Parc, the design system in [design/parc/](design/parc/): its rules in `design/parc/README.md`, its values in `design/parc/tokens.json`, a mock per screen in `design/parc/screens/`. [docs/DESIGN_SYSTEM.md](docs/DESIGN_SYSTEM.md) says where it lives in the code. Working notes for agents live in [CLAUDE.md](CLAUDE.md). System architecture (data model, React Query invalidation, RLS, routing persistence) lives in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Environment setup (WSL recommended) lives in [docs/ENVIRONMENT.md](docs/ENVIRONMENT.md).

Quick summary:

- **Theme**: light only — the Parc tokens (`src/styles/parc-tokens.css`) and the `pk-*` classes (`src/styles/bundle.css`), no theme class, no `dark:` variant.
- **i18n**: `I18nProvider` (`src/hooks/useI18n.jsx`) with EN/FR/DE dictionaries in `src/lib/i18n/`. Sentence case, no capitals, no middle dots, no emoji. Language persists in `localStorage.sl_app_lang` and mirrors to `<html lang>`. `useI18n()` has a no-op English fallback for isolated tests. A package adds strings as a fragment — `src/lib/i18n/fragments/<package-id>.<lang>.js`, one new namespace, in the three languages — which `src/lib/i18n/index.js` merges into the dictionary of its language; fragments are folded into `en.js` / `fr.js` / `de.js` at the end of waves 4 and 9 (`src/lib/i18n/fragments/README.md`).
- **Toggles**: there is no theme toggle. `LanguageSelect` (a segmented control) lives inside `ui/UserMenu`'s coach-side popover. On the student side the popover has been retired — the language selector lives on the dedicated `StudentProfile` page (the avatar `<Link>`s to it directly when `profileHref` is passed).
- **Notifications**: a `NotificationBell` lives next to the avatar in `ui/UserMenu` so every top-level page surfaces them. Two event kinds today: `session_completed` fires when a student inserts a `session_confirmations` row (notifies the coach); `session_feedback` fires when the coach submits a feedback message at the end of `SessionReview` — i.e. inserts a `messages` row with `session_id` set — and notifies the student with a deep link to the session view. Both use SECURITY DEFINER triggers writing to the `notifications` table (no client INSERT policy). Realtime via the same Supabase channel pattern as messages. Adding a new event type = new trigger + new `describeNotification` case + new i18n key.
- **Coach feedback flow**: `SessionReview` ends with `SessionFeedbackComposer` — an optional textarea + "Send feedback" / "Finish without feedback" pair — once the athlete has confirmed the session. For a session that is not confirmed (still in progress, or confirmed and then undone) the page says so and offers no form: a review needs a confirmation. On send, it inserts a normal `messages` row with `session_id` attached; the DB trigger fires the notification, and the message renders in the existing coach↔student thread with a "Re: <session>" reference card above the bubble. Tapping the card deep-links to the session (coach → review screen, student → session view). The card is rendered by `messaging/SessionReferenceCard` and metadata for visible refs is fetched in one batch by `useSessionRefsForMessages`.
- **Student-side feedback surface**: feedback shows up in two places on the student side. `SessionView` reads `useSessionFeedback(sessionId)` and renders a "Coach's feedback" card between the progress bar and the slot groups when a feedback row exists — this is what the deep-link from a feedback message lands on. The training list says « Coach’s feedback » on the row of a session that has feedback; `StudentTraining` sources that flag from `useMyFeedbackSessionIds()` (a single batched query for the student's feedback rows), so a student can tell at a glance which sessions have a follow-up to read. Once the coach has reviewed a session — with feedback or without — `SessionView` shows it read-only: the sets, notes and videos stay as the coach read them, and where "Undo confirmation" was the page says that the coach has reviewed the session and links to Messages, the way to ask for a correction.

## Offline Support (Student Session Logging)

Students can fully record their sessions without a connection — RPE, set validation (done/failed), off-plan actuals (actual reps/load), set skips, exercise swap/skip, session confirm/unconfirm, and slot comments all work offline and replay automatically when the device reconnects. (Adding a brand-new extra set is the one online-only action — a new-row INSERT can't be safely queued offline.)

Program **authoring** is offline too: a student can draft a whole program (weeks → sessions → exercises) with no connection. Each edit is an optimistic local write with client-minted ids that syncs as one idempotent whole-tree snapshot (the `save_draft_tree` RPC). Until the database has accepted it, the tree on the device is marked as unsynced: it is never replaced by a read of the server, it survives a relaunch, and it is sent again when the device reconnects, when the app is opened and when the student comes back to it. A draft in sync is re-read on those same occasions, so a draft the coach sent back shows up without a reload. See [src/lib/draftTree.js](src/lib/draftTree.js).

How it works:

- **App-shell precache** — `vite-plugin-pwa` (`injectManifest`) compiles [src/sw.js](src/sw.js) into `dist/sw.js`, which precaches the page, the JS/CSS bundles and the icons, and caches Google Fonts as they are used. The page loads with no network at all.
- **Updates** — the page registers the worker itself and decides when a new version takes over ([src/lib/appUpdate.js](src/lib/appUpdate.js)). It asks for one on every return to the app (at most every 15 minutes) and once an hour; the new worker installs and waits. With nothing in progress — no write pending or queued, no rest timer, no field being typed in, no text typed and not sent yet, no dialog open — the page applies it and reloads by itself, about a second later. Otherwise a card above the bottom nav offers it ("Update" / "Later"), and it is applied at the next return to the app or the next page where nothing is in progress.
- **A screen whose file is gone** — every screen is a file fetched when it is first opened. On a page older than the files the server keeps, that request fails: the page reloads once by itself when nothing would be lost ([src/lib/chunkRecovery.js](src/lib/chunkRecovery.js)), and otherwise shows a screen with "Reload" instead of "Something went wrong". It is not written to the coach's list of errors.
- **Read cache** — what the student needs offline (the session and its sets, notes, swaps, videos and confirmation, the active block, the list of confirmed sessions, the "Last time" hints, the exercise library, a draft being written) is persisted to IndexedDB via `@tanstack/react-query-persist-client` + `@tanstack/query-async-storage-persister` (storage shim built on `idb-keyval`). On reload while offline, the cached state hydrates and the app is fully readable. An entry is kept for 14 days after it was last read, in memory and on the device alike — a session opened at home is still there at the gym — and it is kept when a later refresh fails. The entries of a session are dropped from the device a week after its confirmation. The allow-list (`PERSISTED_QUERY_ROOTS`) and the rules live in [src/lib/queryClient.js](src/lib/queryClient.js).
- **Fewer requests during a workout** — unlocking the phone after a rest does not re-read the session, its notes and swaps, the exercise library or the "Last time" history: they are read when the page opens, refreshed by the app's own writes, and left alone on a return to the app for four hours. Only the sets and the confirmation are re-read on unlock.
- **Training list and next session** — the list (`/student`) is built from two of the persisted reads, the block being trained and the confirmed sessions, so it opens at launch without a network exactly as it was last seen, past blocks included as closed rows; the sessions of a past block are read when its drawer is opened and are not kept. While the list is on screen with a network, the next session of the queue and its sets are read ahead into the same cache, so the session can be opened in the gym even if it was never opened on that device. When the device holds nothing — a first launch without a network — the page says so and offers "Try again", and it loads by itself when the network returns. "No program assigned yet" is only ever the answer of the server.
- **Opening a session** — writes nothing. The page shows the session and the sets the device holds, and asks the database to add a prescribed set only when it finds one without a row and the device is online (`ensure_set_logs`, which reads the exercises in the database): nothing is ever "waiting to sync" because a session was opened. A session that is not on the device and cannot be read — it was never opened and was not the next one of the list — is shown as that: "This session isn't on this device yet" without a network, "couldn't be loaded" with one, a "Try again", and no "Confirm session". It opens by itself when the network returns.
- **Confirming a session, and notes** — a confirmation made without a network closes its dialog at once and shows on both pages: the session page says "Session confirmed" with "Saved on this device. It will be sent as soon as you're back online.", and the training list moves on — the next session becomes "Next", the confirmed one joins "Done" with the day it was trained. It stays so after the app is closed and opened again, and the confirmation is sent, with its note and its day, when the network returns. Undoing it, and confirming again, work the same way and are sent in order. A note for the coach shows on its exercise as soon as its field is left. The dialog states how many sets are logged before it confirms, and asks a second time when none is.
- **Write queue** — student-side mutations (`set-log/{toggle-done,set-failed,set-rpe,log-actual,set-skipped}`, `session-confirmation/{confirm,unconfirm}`, `slot-comment/save`, `slot-deviation/save`, and the draft's `draft-tree/{save,discard}`) are wired to stable mutation keys in [src/lib/offlineMutations.js](src/lib/offlineMutations.js). Their `mutationFn` is registered both inline and via `queryClient.setMutationDefaults`, so a mutation paused while offline can resume after a cold reload — react-query reattaches the persisted variables to the registered fn keyed by mutationKey. `networkMode: 'online'` parks them as paused; the queue is replayed when the cache is restored, on every `online` event and when a session appears — and only while someone is signed in.
- **Conflict policy** — each write is targeted at one `set_log` / `slot_comment` / `slot_deviation` / `session_confirmation`, and payloads are field-scoped. Set logs, comments and deviations are last-writer-wins; DB CHECKs (`set_logs_done_xor_failed`, `set_logs_no_rpe_when_failed`) are encoded in the patch helpers, so replays stay constraint-safe. A confirmation is first-writer-wins: `useConfirmSession` inserts or does nothing (an upsert on `session_id` with `ignoreDuplicates`), so a confirm replayed against a session that is already confirmed keeps the first note and training date. Changing a confirmation is undo, then confirm again. `useUnconfirmSession` is naturally idempotent (DELETE WHERE missing-row = no-op), `useSaveSlotComment` upserts on `exercise_slot_id` and turns empty bodies into deletes.
- **Failure policy** — a queued write the database refused (a policy, a constraint: an error with a code) fails once. One that got no answer — no network, a gateway page, a database that is restarting — is sent again five times over half a minute, and pauses if the device goes offline meanwhile. And while nobody is signed in (an expired token that cannot be refreshed counts) nothing is sent at all: the write waits for its owner, because supabase-js would send it with the anonymous key and the database would refuse it for good. The rules are in [src/lib/networkErrors.js](src/lib/networkErrors.js). Reads wait as well: without a network a query is paused, not attempted, and runs when the device is back.
- **When a set was done** — `logged_at` / `failed_at` are the moment of the tap, carried in the queued write, not the moment the request is sent: a workout logged offline and synced the next day keeps its day.
- **A switch of block in between** — an athlete writes only in the block they are training, and a coach may set the next block active while a workout is still waiting on a phone. The database keeps a block open for its athlete for 72 hours after it is switched off (`programs.deactivated_at`, migration 17), so the queue is saved in the session it was logged in when the phone is back; the screens show that block as a past one, read-only, from the moment of the switch. After the 72 hours, and for a block in the trash, a replay is refused.
- **A workout the database no longer accepts** — if the coach closed the session or switched block while the phone was offline (past the 72-hour grace), the replayed writes are refused. The athlete gets one message for the whole workout instead of one error per set, and each refused write is kept in `localStorage` under `sl_rejected_writes` (what was done, when, by whom) so it can be read back and entered by hand. See [src/lib/mutationErrors.js](src/lib/mutationErrors.js).
- **UX** — `OfflineBanner` (mounted in `AppShell`) shows the connectivity state + the number of writes still queued. The count is the number of writes this device still owes the database — `isQueuedWrite` in [src/lib/persistence.js](src/lib/persistence.js), the same test that decides what is stored for the next launch — so a page that merely opened offline is not announced as "1 change waiting to sync". It is **derived**, never mirrored into local state: `useIsMutating` is a `useSyncExternalStore` read over the mutation cache, so the banner can never `setState` in the middle of another component's render. Two bands cover the states: hidden while online, and warn-coloured ("Offline · N waiting to sync") while offline, collapsing again as soon as the connection returns and the queue replays.
- **Per-user scoping** — the persisted blob records the account it belongs to. `ClearOnUserChange` in [App.jsx](src/App.jsx) wipes both the in-memory queryClient and the IndexedDB blob when another account is signed in than the one the cache belongs to — also at launch, when the blob was left by another account — and when the user signs out of the device; until then a queued write is not sent under another account's session. A session that goes away by itself (an expired token that cannot be refreshed, a sign-out elsewhere) wipes nothing: the same account finds its cache and its unsynced writes again. A cache that does not say whose it is belongs to the account the device is signed in as, and is wiped when nobody is.
- **Signed in without a network** — an installed app opened offline starts from the session the device stores and the role it remembers ([src/lib/storedSession.js](src/lib/storedSession.js), [src/lib/profileCache.js](src/lib/profileCache.js)): no spinner, no login form, whatever the age of the access token. The role is remembered from the first launch that could read it: a device that has not had one since it got this version (or since the account signed in) opens offline on a sentence that says the account will open once it is back online, not on the app. Signing out works offline as well, and asks first when the device still holds changes it has not sent ([src/components/auth/SignOutGuard.jsx](src/components/auth/SignOutGuard.jsx)).
- **What survives an update, a long pause and a kill** — the write queue. Every queued write that has not reached the database is stored, also one whose request was out or that was waiting for a retry when the app was killed, and it is replayed at the next launch. Changing `CACHE_BUSTER` in [src/lib/persistence.js](src/lib/persistence.js) — the way to discard cached reads whose shape changed — or leaving the app closed for more than 14 days drops the cached reads and keeps the queue (and a draft that is ahead of the server). Because of that, a mutation key of [src/lib/offlineMutations.js](src/lib/offlineMutations.js) is never removed or renamed; a write whose variables change shape gets a new key.

Out of scope for the current implementation:

- **Video uploads** — `VideoUploadButton` is gated on `useOnlineStatus()` and the CTA flips to "Connect to record video" when offline. Supabase Storage has no resumable background-upload story we can lean on safely on mobile, so an upload is one request: it shows its progress, can be cancelled, and starts again from zero if the connection drops. A file that is not an MP4, MOV or WebM video, or that is above 25 MB, is refused before anything is sent. Replacing a video keeps the previous one until the new one is saved, so a failed or cancelled upload loses nothing.
- **Coach surfaces** — only student-side writes are queued. Coach mutations still require a connection.

## Rest Timer (in-app + Web Push)

The student rest timer is an app-wide singleton ([hooks/useRestTimer.js](src/hooks/useRestTimer.js)). The session page draws it in its ActionBar ([SessionView.jsx](src/components/student/SessionView.jsx), `RestControls`): the countdown and « +30 s ». [RestTimerHost.jsx](src/components/student/RestTimerHost.jsx), which the student shell mounts on every page, runs the two effect hooks below and the hidden status region a screen reader hears — "Rest 1:30" when a rest starts, "Rest done" when it ends, nothing in between — so a change of tab in the middle of a rest keeps the beep, the wake lock and the push.

A rest that is running is also written to `localStorage` (key `sl_rest_timer`). iOS kills a PWA in the background — opening the Camera app to film a set is enough — and when the athlete opens the app again the rest is still running, with the time it really has left. A rest that ended in the meantime is dropped.

- **In-app polish — [useRestTimerEffects](src/hooks/useRestTimerEffects.js):** while a rest timer is active, the hook acquires `navigator.wakeLock` so the phone screen stays awake — and acquires it again each time the athlete comes back to the app during the rest, because the browser releases it when the page is hidden — schedules a synthesized WebAudio beep + `navigator.vibrate` at expiry, and mirrors a `Rest m:ss · <title>` countdown into `document.title` while the page is hidden. The AudioContext is unlocked on the first `pointerdown` so iOS lets the cue play unattended. On an iPhone the beep asks for the `playback` audio session (`navigator.audioSession`) for its own length, so that it is heard with the ring/silent switch on; the session goes back to what it was right after, so that the app does not hold the phone's audio against the athlete's music. With the app in the background or the phone locked there is no sound — iOS plays no Web Audio from a background PWA — and the push below is the signal.
- **Background / lock-screen push — [useRestTimerPush](src/hooks/useRestTimerPush.js):** when a student has enabled "Rest end notification" in their Profile, the hook asks the database for one push with `schedule_rest_push` — the seconds left, the text in the app's language, the session to go back to, and this device's endpoint, so that only this device rings. The database computes the time on its own clock and says who sends: its pg_cron job (`mode: 'cron'`), or the [`dispatch-rest-push`](supabase/functions/dispatch-rest-push/index.ts) Edge Function, which the hook then invokes (`'edge'`). A rest that ends early is taken back with `cancel_rest_push`. The function answers at once and waits for `fire_at` after its answer, a minute at a time — a function of the platform cannot wait longer in one go, so a longer rest is handed from one request of the function to the next ([`_shared/restPush.js`](supabase/functions/_shared/restPush.js)). At the time of the push it asks the database whether the push is still its to send (`claim_rest_push`: never a rest that was taken back, never one that was sent already) and sends a VAPID-signed Web Push to the devices of that user. The custom service worker ([src/sw.js](src/sw.js), handlers in [src/lib/swHandlers.js](src/lib/swHandlers.js)) shows the notification — always: with the app in front of the athlete, where the in-app cue already plays, it is shown without sound and closed a few seconds later, never skipped (a push that shows nothing costs an iPhone its subscription). A tap brings the app to the front and leaves a window alone that is already on the page the notification names; a "Rest done" still on the lock screen is closed when the app is opened again.

iOS Live Activities / Dynamic Island are not exposed to web — Web Push is the closest the platform offers a PWA. iPhone users must install the app to the Home Screen (iOS 16.4+) for push to work. Otherwise the in-app cues still cover them.

The DB tables ([2026_05_11_push_notifications.sql](supabase/migrations/2026_05_11_push_notifications.sql)) are RLS-scoped to the owning user. Since migration 16 the database also holds the schedule itself: `schedule_rest_push` computes the time on the server for one device and says who sends (`mode` `cron` or `edge`), `cancel_rest_push` takes a rest back, and whoever sends asks `claim_rest_push` first, which answers a row once — never a canceled one, never one more than a minute late. The Edge Function asks `claim_rest_push` before it sends; the app calls `schedule_rest_push` and `cancel_rest_push`, and falls back on its own insert only where they are missing (`PGRST202`). The Edge Function runs as service role and double-checks `user_id` on every row. The function waits for a rest of up to 15 minutes, and the app asks for a push for any rest of 1 to 900 seconds (`useRestTimerPush`). Detailed invariants live in [docs/INVARIANTS.md](docs/INVARIANTS.md) under "Rest timer" and "Web Push".

**Coaches** can opt into push too, from the header user-menu popover ([`PushToggleRow` in `UserMenu`](src/components/ui/UserMenu.jsx)) — the same role-agnostic `push_subscriptions` plumbing, so a subscribed coach receives the chat-message pushes the direction-agnostic trigger already fans out. **Subscription self-healing** ([`reconcilePushSubscription`](src/lib/pushNotifications.js) via [`usePushAutoHeal`](src/hooks/usePushAutoHeal.js) — checked on load and on focus, written at most once an hour, or at once when the endpoint changed or another account signed in — plus a `pushsubscriptionchange` re-subscribe in the SW) re-syncs a rotated endpoint into the DB so delivery doesn't silently stop after `send-push` reaps the stale row. **The subscription follows the signed-in account**: a device is registered through the `claim_push_subscription` function, so on a phone two accounts share, the one that is signed in receives and the other does not; signing out releases the device first (its row is deleted and the browser gives the subscription up, also without a network), and the account that had notifications on finds them on again when it signs back in. A toggle that cannot do what was asked says why — no connection, notifications blocked, a browser whose push service is not supported.

A second Edge Function, [`send-push`](supabase/functions/send-push/index.ts), is the fan-out the database's notification triggers call through pg_net (feedback, session confirmed, off-plan exercise, chat message, draft submitted, approved or sent back). It is internal: the database presents a shared secret, `INTERNAL_BEARER`, which one function — `send_push_event` — reads from Supabase Vault (`app_internal_bearer`, or `app_service_role_key` while the secret has not been renamed, next to `app_functions_url`) and sends with a time limit of ten seconds, and the function's gate — [`_shared/auth.js`](supabase/functions/_shared/auth.js): POST only, the bearer in constant time, a body of 8 kB at most, no CORS — lets nobody else in.

What it does behind the gate is in [`_shared/push.js`](supabase/functions/_shared/push.js). An event goes to every device of its user, kept one day for a phone that is offline; the answer is `200 {"delivered":N}`, or `502` when the user has devices and none took the message — and every device that did not take it is a line of the function's log, with the push service's status and host. It sends only to the four push services ([`_shared/pushHosts.js`](supabase/functions/_shared/pushHosts.js)). Where pg_cron is switched on, the database also hands it the rest pushes that are due: those are answered `202`, sent at their time after `claim_rest_push` has said the row is still to be sent, and recorded on the row.

Deploying the functions, their secrets, rotating `INTERNAL_BEARER` and the check to run after a deploy are in [docs/runbook/30-edge-functions.md](docs/runbook/30-edge-functions.md). In short:

```bash
supabase functions deploy send-push --use-api
supabase functions deploy dispatch-rest-push --use-api
```

No `--no-verify-jwt`: [supabase/config.toml](supabase/config.toml) says which function runs without the gateway's JWT check, and the flag would override it. The VAPID pair comes from `npx web-push generate-vapid-keys --json` (public key in `.env` as `VITE_VAPID_PUBLIC_KEY`, both halves and a `mailto:` subject as function secrets); the vault's copy of the bearer is written with `vault.create_secret` and changed with `vault.update_secret`, never with `UPDATE vault.secrets`.

## Database Tests

All of the app's authorization lives in SQL. `supabase/tests/` loads `supabase/schema.sql` — unmodified — into a real PostgreSQL 17 and exercises it as an anonymous caller, a signed-in student, the coach or the service role: RLS policies, triggers and RPCs. No Docker and no local Postgres: the server binaries come from npm (`embedded-postgres`, pinned to production's 17.6), and a run takes about two and a half minutes.

```bash
npm run test:db                            # single run — also the `db` job in CI
npx vitest --config vitest.db.config.js    # watch: saving schema.sql rebuilds the database and reruns
DB_TEST_LOG=1 npm run test:db              # same, with the Postgres server log (RAISE WARNING, …)
```

`npm test` does not run these files, and they do not need `.env`. A run reports 34 files and `1320 passed` at the head of wave 3, with no expected failure: every hole of the 2026-09-30 review that `known-holes.test.js` holds is closed, and is a plain test there. Its exit status is what CI reads: 0 for such a run, 1 as soon as one test or one file failed.

**How it works.** One cluster per run. `shim.sql` recreates what a Supabase project provides before any user SQL runs — the `anon` / `authenticated` / `service_role` roles, `auth.users` and `auth.uid()`, `storage`, stubs for `pg_net` and Vault, the realtime publication, and Supabase's default privileges on `public` — then `schema.sql` is loaded as `postgres`, the same non-superuser role the SQL editor uses. That template is cloned into a fresh database for each test file. The database right after `shim.sql` is kept as a second template (`sl_bare`), for the tests that build a database from SQL files themselves.

Two lines of `postgres.js` are there for the gate, not for the tests. The server starts with `autovacuum=off`: a file drops its database as `postgres`, which is not a superuser and may not end an autovacuum worker, so a worker that happened to be in the database made the drop fail — a file reported as failed with every test green, in about one run out of two. And the process keeps the exit code vitest chose: the server library (`embedded-postgres`) ends a process that runs out of work with `process.exit(0)`, which is how vitest ends, so a run with a failed test used to exit 0 and the `db` job could not go red. `src/test/dbSuiteExitCode.test.js` holds the second from the unit suite — whose exit status does not depend on it — by running vitest on `supabase/tests/fixtures/exit-code/`: the database suite's configuration, no server, one test that fails.

**Writing a test.** Add a `*.test.js` file to `supabase/tests/`:

```js
import { beforeAll, expect, it } from 'vitest';
import { asUser, attempt, scenario, seed } from './harness.js';

let ids;
beforeAll(async () => { ids = await seed(); });   // coach, students A and B, programs, messages

it("a student cannot log a set in another student's program", () => scenario(async (q) => {
  const theirs = ids.programB.setLogs[0];
  const tried = await attempt(() => asUser(ids.studentA, (a) => a(
    `update set_logs set done = true where id = $1`, [theirs],
  )));
  expect(tried.value?.rowCount ?? 0).toBe(0);                      // refused, or matched no row
  expect(await q.value(`select done from set_logs where id = $1`, [theirs])).toBe(false);
}));
```

- `asAnon(fn)`, `asUser(user, fn)`, `asService(fn)` and `asAdmin(fn)` run `fn(q)` in one transaction as that role, the way PostgREST does (`SET LOCAL ROLE` + `request.jwt.claims`), and **roll it back**. `q(sql, params)` returns the `pg` result; `q.rows`, `q.one` and `q.value` unwrap it.
- Two top-level calls are two transactions and do not see each other's writes. `scenario(fn)` opens one transaction that every helper called inside joins — arrange as `postgres`, act as a user, read the truth as `postgres`.
- A statement that raises does not abort the transaction, so a test can attempt something forbidden and then inspect the state. `attempt(fn)` turns a throw into `{ ok, value, error }`.
- Fixtures: `seed()`, `createUser()`, `createProgram()`, `createDraftProgram()`, and `pastBlock(q, program)` — a block switched off more than 72 hours ago, which is what "a past block" means since migration 17; `enablePush()` + `httpCalls()` to assert the Web Push fan-out — `enablePush({ bearerName: 'app_internal_bearer' })` stores the bearer under its new vault name, and each call of `httpCalls()` carries its `timeout_milliseconds`. Each is documented in `harness.js`.
- `q.dryRun(sql, params)` runs one statement and undoes it at once — the result comes back, the database is untouched. `scratchDatabase()` gives a test a database of its own to load SQL files into (`db.runFile`, `db.runSql`, `db.readOnly`, `db.query`), starting from an empty Supabase project or from a copy of `schema.sql`; `db.platform(sql)` runs one statement there as the platform's own role, which owns `net` and `vault` — for a test about a project whose pg_net is not production's, never for what the app or a migration does.
- `known-holes.test.js` holds the findings of the 2026-09-30 review as tests that assert the secure behaviour: `it.fails` while the hole is open, a plain `it` once a migration has closed it (the comment above it names the migration). To fix one: delete `.fails`, watch it go red, write the migration and merge it into `schema.sql`, keep the control tests next to it green. Since the migrations of wave 1 (03 to 14) none is open: a new finding joins the file as an `it.fails`.
- `rpc-auth.test.js` calls the five coach-only SECURITY DEFINER RPCs as every kind of caller, and the four that act for the account that calls (`ensure_set_logs`, `claim_push_subscription`, `schedule_rest_push`, `cancel_rest_push`) as every caller without a user id. A new SECURITY DEFINER function that a client can call must be added to its table of calls, and one that no client can call to `NOT_FOR_A_CLIENT` with the reason: the test that lists them fails otherwise.
- `function-acl.test.js` holds who may execute what: no function of `public` for `anon` or `PUBLIC`, an explicit list for a signed-in user, everything for the service role, and `search_path = public, pg_temp` on every function. A migration that adds a function adds it to `HELPERS`, `RPCS` or `NOT_FOR_USERS` in that file (a trigger function joins none), and to the `FUNCTION PRIVILEGES` block at the end of `schema.sql` when it is granted — the rules are in `supabase/migrations/README.md`.
- `asPlatformRole(role, fn)` runs `fn(q, owner)` as a role `postgres` cannot become — `supabase_auth_admin`, the role GoTrue creates accounts as. It has a connection and a transaction of its own, rolled back at the end: it sees committed fixtures (`seed()`), not what an enclosing `scenario()` wrote.
- `history-guards.test.js` holds the rule "logged training is never deleted or rewritten": each way a set becomes logged, every level a delete can start from (with the upper guards switched off, to prove the one on `set_logs` alone), the writes of the session editor replayed in the order the app sends them, the pin on targets, `app.allow_history_delete`, and `adopt_swap` / `adopt_skip`. A test that needs to delete logged rows on purpose says `set local app.allow_history_delete = 'on'` first, as `postgres` or the service role.
- `students-gate.test.js` holds the rule "the coach–athlete link cannot be forged": who may write a `students` row (nobody through the API), what a row may say for every writer, the exercise library written by a coach only, and whose exercises a slot and a swap may take. A fixture that links an athlete does it as `postgres` (`createUser({ coach })`), and the coach must have been promoted first: the trigger judges fixtures too.
- `pins.test.js` holds the rule "a row two sides write keeps the other side's columns": the athlete's pin on a set, the pin on the sessions of a draft, the submission made once. All three are silent — the statement is accepted and the column keeps its value — so a test about a pin reads the row back; an `attempt()` that did not throw proves nothing. One of its tests is not a `scenario()`: three transactions of their own — a row held, the author's stamp waiting for it, the coach's approval committed meanwhile — because a policy and a trigger can only disagree across connections. It is the pattern for any "what if the coach does X while the athlete's request is on its way" test: helpers called OUTSIDE `scenario()` each open their own transaction (`{ commit: true }` to keep it), `pg_stat_activity.wait_event_type = 'Lock'` says the second one is waiting, and the test deletes what it committed.
- `profiles.test.js` holds the two rules of `profiles`: a new account always has a name, and a role is written by the owner of the database only. An account is created there the way production creates one — `asPlatformRole('supabase_auth_admin', …)`, an `INSERT` into `auth.users` made as GoTrue with its own `search_path` — because the function behind it is the one piece of the schema that runs for a role holding nothing on `public`. Since migration 07 `createUser()` without a `fullName` gives a profile named after the address (`alex` for `alex@sl.test`), and `createUser({ role: 'coach' })` promotes with the plain `UPDATE` the owner runs; a fixture that needs an account with an empty name writes it (`update public.profiles set full_name = ''`), as `auth-accounts.test.js` does for the accounts made before the migration.
- `session-gates.test.js` holds the rule "an athlete writes in a session only while it is theirs, of the block being trained, and neither archived nor reviewed". A refused write has two shapes — an INSERT raises, an UPDATE or a DELETE reaches no row and says nothing — so "0 rows" proves nothing by itself: the file keeps every write of the app in one list (`everyWrite`), shows each of them going through on the open session with `tryAll` (each statement run with `q.dryRun`, so the rows stay as they are), closes the session, and only then expects the refusals and compares everything under the session with what it was. A new athlete write joins that list. The RLS matrix has a session in progress for the same reason: with every row of an athlete in a reviewed session, a rewrite that closed all sessions would have left its cells at 0.
- `review-lifecycle.test.js` holds "a review needs a confirmation, and closes it". Three of its tests are about two requests that cross — a review and an undo sent in the same instant — and one connection cannot show that: `cross({ first, second })` runs the first request and holds it open, uncommitted, starts the second, waits until `pg_stat_activity` shows it waiting for a lock, and only then commits the first. They commit what they write, so they have an athlete and a block of their own. A rule that a policy or a `STABLE` function holds alone gets such a test: both judge the database as their statement saw it when it started.
- `goals.test.js` holds what a deleted exercise or account takes with it, and who reads a goal's attempts. A test that deletes a profile asserts `23503` and that nothing went — not which foreign key said so: PostgreSQL names the first one it meets, and that order changes with the internal names of the constraints' triggers, from one database to the next. Where the name matters, the test builds the case in which one key alone is in the way.
- `atomic-rpcs.test.js` holds the three functions that do in one statement what the app did in several requests. A request that is lost half-way is a trigger that raises on the write it would have made (`loseTheRequestThat`): each `q()` of the harness is one request, so the same failure shows what the function leaves and what the requests leave. Two requests that cross need two connections and committed rows (`cross`), and have an athlete of their own.
- `copy-rpcs.test.js` holds the four functions that copy. The requests the app sent before wave 2 are written out in it (`app` — what `src/hooks/useDuplicate.js` did before it called the functions), so that a copy made by a function is compared with the copy those requests make of the same block, row for row and column for column (`sessionOf`, `weekOf`, `programOf` read whole rows as JSON, without ids). The block it copies is dressed so that every column holds something — a column that is NULL in the source is NULL in a copy whether it is copied or not — and a test fails when a column is not. A request that is lost is a trigger that raises on the `INSERT` it would have made (`loseTheInsertThat`).
- `ensure-claim.test.js` holds the two functions that write for the account that calls. The requests of the app that is deployed are written out in it (`app.ensure`, after `useEnsureSetLogs` as it was until wave 2, takes the exercises "as the app has them in its cache" — the hook calls `ensure_set_logs` now; `app.subscribe`, after `upsertSubscriptionRow`), so each finding is shown on the same rows as the function that closes it. What a set carried when it was inserted is read by a trigger the test adds for the length of one scenario (`watchInserts`); the trigger of the contract migration that is not written yet stands in the same way (`test_pin_insert`). Requests that cross have an athlete of their own, and commit.
- `rest-push.test.js` holds "the end of a rest is scheduled by the database, and a rest push is sent once". The requests of the app and the statements of the `dispatch-rest-push` function that are deployed are written out in it (`app`, `deployedFunction`), because the migration is applied while both are live. A row is put into any state with `plant(q, user, secondsFromNow, { status, takenBack, endpoint, handedOver, daysOld })` and read back as one word (`stateOf`: `'pending handed-over'`, `'canceled taken-back'`). pg_cron is not in the suite: the tests about `mode` make its table of jobs themselves (`makeCron`, `job`). Requests that cross — two senders, a cancel and a claim, two rests of one account, the job and a row that is held — commit, on the rows of one athlete, and delete them again.
- `replay-grace.test.js` holds "a block stays open for its athlete for 72 hours after it is switched off". A test cannot wait 73 hours: it moves the time of the switch back as the owner of the database — `pastBlock(q, program, '73 hours')` — which is the one caller the column can be written by. Inside a `scenario()` the clock is one instant, so a block switched off there was switched off exactly now (`switchedOff(q, id)` answers `0`, in hours). The coach's requests and the nine writes of the athlete's queue are written out as the deployed app sends them (`coachApp`, `queue`, after `useProgram.js` and `lib/offlineMutations.js`), and a workout is sent whole (`send(workout(session))`) and compared with `SAVED` or `REFUSED`.
- `retention.test.js` holds "the rows nobody reads any more are deleted by one function, and nothing else is". A test cannot wait 90 days: it writes rows with the dates of the past, as the owner — `push(q, user, { age: '8 days', status, due, takenBack })`, `line(q, user, { written, read })`, `report(q, user, age)` — and inside a `scenario()` the clock is one instant, so "exactly 7 days ago" is exact. `left(q, table, planted)` answers the labels of the rows that are still there. Its two lists, `DELETED_BY_A_RUN` and `KEPT_FOR_GOOD`, name every table of `public`: a new table joins one of them.
- `cron-jobs.test.js` holds the optional migration 19: four jobs of pg_cron and `record_push_failures()`. None of it is in the database the suite runs on, so its tests build their own: `scratchDatabase()`, `await db.enableExtension('pg_cron')`, then `schema.sql` (`home`) or the baseline and the migrations (`production()`). Nothing runs a job in the stub: `runJob(db, 'sl-retention')` runs its command as `postgres`, which is what pg_cron does at its time, and a run is a row the test writes into `cron.job_run_details`. What pg_net was answered is a row the test writes into `net._http_response` (`answered(hoursAgo, { status, timedOut, error })`). A request of a user of the API is a transaction that sets the role and the claims (`story`, `request`), because `asUser()` does not see a scratch database.
- `drafts-readonly.test.js` holds "the tree of a draft is its author's" (migration 20): every write of the coach's editor on a draft refused with `draft_read_only`, the coach's approve, send back, rename, trash and delete still accepted, and `approve_program` giving every set its target.
- `small-hardening.test.js` holds migrations 21 to 24: an RPE in half steps and a weekday from 1 to 7 or none, who reads a client error and the cap of 30 an hour, the exercises of a former coach read by the athlete and the new coach, and the indexes.
- `storage-policies.test.js` holds migration 25: a coach reads the file of a set video only through a video that names it.
- `coach-list-rpcs.test.js` holds the two read functions of the optional migration 26 against copies of the app's folds, past 1000 rows.
- `table-acl.test.js` holds who holds what on a table: nothing for `anon` or `PUBLIC`, `SELECT`, `INSERT`, `UPDATE` and `DELETE` for a signed-in user, everything for the service role — and row-level security on every table, `security_invoker` on every view. A migration that adds a table changes nothing in it unless the table must give a signed-in user less (`LESS_FOR_USERS`); it fails on a table without row-level security. The finding is run on the frozen baseline as the role an API request arrives as: `truncate public.profiles cascade` goes through before the migration, for `anon` and for an athlete, and is refused after.
- `auth-accounts.test.js` runs the account list of `docs/runbook/20-auth-config.md` — the query is read off the page — on the accounts an open sign-up leaves behind.
- `backup-roundtrip.test.js` runs the backup scripts (`scripts/backup/`) as child processes against a database seeded to look like production: dump, verify, restore into a database that only had `schema.sql`, and every table compared in SQL. It also holds what a backup must refuse (a clear file on a CI runner, a path inside the repository, a role that row-level security filters, a Supabase host as restore target), that a `TRUNCATE` or a rewriting `ALTER TABLE` sent during a dump waits for it and one committed just before its locks stops it, that a changed byte or a wrong passphrase fails the verification, and that nothing printed contains the connection string, the password or the passphrase. The three commands of `docs/runbook/00-before-you-start.md` section 2 and the `openssl` line of `BACKUPS.md` are read off their page and run. It creates two login roles in the cluster with the suite's superuser (`supabase_admin`) and drops them at the end.
- `push-secrets.test.js` runs the vault statements of `docs/runbook/30-edge-functions.md` — looking at the two secrets, rotating the bearer, creating it — read off the page, and checks that the triggers then send the new value.
- `push-plumbing.test.js` holds "a push leaves the database through one function". It reads the text of every function of `public` — one may read the vault or call pg_net, and the eleven that notify call it inside an `EXCEPTION` block of their own — and fires the eleven events the way the app does, with pg_net raising, the function raising and the function gone: every write and every bell row is there all the same. The requests the eleven hand to pg_net are compared before the migration, after it and after its rollback, on the frozen baseline: the same address, bearer and payload, with the time limit added. What a device's endpoint may hold comes from `fixtures/push-endpoints.json`, three lists the Edge Functions' own list of hosts can be held to as well. A new function that sends a push joins `LATER_SENDERS` at the top of the file (`THE_ELEVEN` is the list of migration 15).
- `deploy-gate.test.js` runs the deploy gate (`scripts/check-migrations.mjs --verify`) as a child process against databases in the states production can be in: everything applied, one migration off the record, an empty ledger, no ledger at all, and the frozen baseline with the `required` migrations applied one file at a time — the gate opens after the last one and not before. It also holds what the gate must not take for an answer: a role that may not read the ledger, a ledger that row-level security filters, a password the database refuses. The commands of `docs/runbook/40-deploy.md` are read off the page and run. It creates two login roles in the cluster and drops them at the end.

**Migrations.** A database change is written as a migration (format: `supabase/migrations/README.md`) and merged into `schema.sql`. Four test files hold that together:

- `parity.test.js` — the frozen production baseline (`fixtures/prod_baseline_2026_09_30.sql`) plus every migration of `supabase/migrations/manifest.json` has the same catalog as `schema.sql` — in a project as production is, without the migrations that wait for an extension, and in one that has pg_cron switched on. The failure names the object and the side that lacks it.
- `migration-conventions.test.js` — every migration is one transaction with a lock timeout, refuses to run twice or before the migration it requires, signs the ledger, has a read-only audit, and has a rollback that gives back the catalog it started from. Each one is run: applied, rolled back, applied again — and the list once more without the optional ones.
- `migration-ledger.test.js` — `app_private.app_migrations` is out of reach of every API role.
- `rls-matrix.test.js` — what anon, two athletes, their coach, another coach and the service role can read, insert, update and delete in every table, compared with `supabase/tests/snapshots/rls-matrix.txt`. After a deliberate change: `npx vitest run --config vitest.db.config.js supabase/tests/rls-matrix.test.js -u`, then read the diff of that file.

Nothing here applies SQL to production. That happens one checkpoint at a time, following [docs/RUNBOOK.md](docs/RUNBOOK.md): by the owner, or by Claude when the owner asks for a checkpoint.

**Limits of the shim.**

- It is PostgreSQL with stand-ins, not Supabase. There is no GoTrue (`auth.users` is a subset; rows are inserted directly, as `postgres` or — with `asPlatformRole('supabase_auth_admin', …)` — as the role GoTrue uses), no PostgREST (its role switch and claims are reproduced, not HTTP — no `max_rows`, no embedding), no Storage API (the two tables and `storage.foldername()` only) and no Realtime (the publication exists, nothing listens).
- `net.http_post` only records the call in `net.http_request_queue`; nothing is sent. Vault is an unencrypted table, empty unless a test calls `enablePush()`. Both are registered as extensions by hand so that `CREATE EXTENSION IF NOT EXISTS` in `schema.sql` is a no-op. `net._http_response` is there and stays empty: nothing answers a request, a test writes the answer. `pg_cron` is absent, as in production; a test that needs it switches a stub on in a scratch database (`db.enableExtension('pg_cron')`, `supabase/tests/shim-pg-cron.sql`), in which nothing runs a job and `postgres` may read `cron.job` and not write it, as on Supabase.
- `postgres` reaches `storage.objects` policies through membership in the owning role (production uses `supautils`), so DDL on `storage.*` that production would refuse succeeds here. Role-level settings such as the API statement timeouts are not applied.
- `postgres` does not own `auth.users` here either, and cannot drop or disable a trigger on it. A test that needs the table without `on_auth_user_created` drops the function with `CASCADE` and creates it again (`profiles.test.js`, "where nothing gives a new account its profile …"). Whether `postgres` may create a trigger on `auth.users` in production today is the platform's decision, and nothing here tests it: a migration never re-creates that trigger.
- A `scenario` is one transaction, so `now()` does not advance between its steps; production runs each API call in its own. Pass `{ commit: true }` to a helper when a flow needs really separate transactions.
- The behaviour tests run against `schema.sql`; the migrations of `manifest.json` are replayed on the frozen baseline and must give the same catalog (`parity.test.js`). The files of `supabase/migrations/` dated before `2026_10` are not replayed. The baseline is `schema.sql` as it stood when the live review compared it with production: where production differed inside a function body (two `RAISE WARNING` strings, comments), the baseline has the repository's text.
- Cluster-wide state (roles, `ALTER ROLE … SET`) is shared by every database of a run and is not part of the catalog comparison.

## Deployment

Pushing to `main` deploys automatically. `.github/workflows/deploy.yml` runs three jobs, each waiting for the one before it: the full test suite (the reusable `test.yml`, which also runs on every `dev` push / PR); then `migrations`, which reads the list of applied migrations in production (`app_private.app_migrations`) and stops the deploy when a `required` migration of `supabase/migrations/manifest.json` is missing; and only then the build and the publish of `dist/` to the `gh-pages` branch. What the check needs, what each refusal means and how to re-run it: [docs/runbook/40-deploy.md](docs/runbook/40-deploy.md). Vite `base` is `/sl_app/`; the router uses `HashRouter` so deep links survive static hosting.

Every deploy is a new version for every device, including one that changed no source: `index.html` carries the id of its build (`<meta name="sl-build">`, the UTC time of the build), so the service worker that lists it is new each time. An open app finds the deploy when it next returns to the foreground, or within the hour, and reloads once nothing is in progress. The `<head>` of the published `index.html` says which build is live.

A deploy does not replace what is published: the new build goes on top of it, and the files of the two builds before it stay (`scripts/prune-gh-pages.mjs`, a step of the `deploy` job). An app that was left open through a deploy, or two, still finds the screens of its own build. One left open through three or more reloads by itself when it opens a screen whose file is gone — once, and only when nothing is being written or typed — or says "A new version of the app is available" with a "Reload". Next to `index.html`, `version.json` names the build that is published and, when the repository variable `MIN_CLIENT_BUILD` is set, the oldest build still allowed to run: an open app older than that applies the update as soon as nothing would be lost, instead of offering it.

Supabase env vars are passed in at build time — ensure GitHub Actions secrets `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and `VITE_VAPID_PUBLIC_KEY` are set. The `migrations` job needs a fourth secret, `SUPABASE_DB_URL` (the one the nightly backup reads): without it the deploy stops, unless the repository variable `ALLOW_DEPLOY_WITHOUT_LEDGER_CHECK` is `true`.

`npm run deploy` still exists as an emergency-only manual path — it publishes whatever is in the local working tree and goes around both gates, the tests and the check of the ledger, so prefer the Actions pipeline. Before it, the owner runs the check by hand: `node --env-file=.env scripts/check-migrations.mjs --verify`. It also replaces the whole published tree with the local build: the files of the builds before it are gone, and an app that was open since before reloads at the next screen it opens for the first time.

**Backups:** the project is on the free plan, which keeps none. A backup is one encrypted file written by `scripts/backup/dump.mjs` — Node and `pg` only, one read-only transaction — on the owner's machine before each change to production ([docs/runbook/00-before-you-start.md](docs/runbook/00-before-you-start.md), section 2) and every night by `.github/workflows/backup.yml` once its two secrets are set, which is a step of the first push. `scripts/backup/verify.mjs` checks a file without a database, `scripts/backup/drill.mjs` restores it into a throw-away PostgreSQL and compares. What a backup holds and does not (the video files, the Vault and function secrets, the Auth settings), the passphrase, and what has never been run against production: [BACKUPS.md](BACKUPS.md).

**Auth hardening note:** every new account gets `role='student'` (`handle_new_user` does not trust sign-up metadata) and a name that is never empty — the one it was created with, else the part of its e-mail address before the `@`. A coach is made by the owner, in the SQL editor: the statement is in [docs/runbook/migrations/07-profile-rules.md](docs/runbook/migrations/07-profile-rules.md), "Making a coach". No signed-in user changes a role, and the database refuses to make a coach of an account that is somebody's athlete. An athlete is linked to a coach by the owner, in the SQL editor — the statement is in [docs/runbook/migrations/05-students-role-gate.md](docs/runbook/migrations/05-students-role-gate.md), "Linking an athlete to a coach". The API refuses to create, move or delete a `students` row, and the database refuses a link whose coach is not a coach or whose athlete is not a student. The app is invite-only: public sign-up is switched off in the Supabase dashboard (Checkpoint A0 of the runbook), and accounts are created there. That setting and the other Auth settings production must have are listed in [docs/ENVIRONMENT.md](docs/ENVIRONMENT.md); the steps and the check are in [docs/runbook/20-auth-config.md](docs/runbook/20-auth-config.md). They are set by hand and never pushed from the repository (`supabase config push` is forbidden).

**Production changes by hand:** SQL, dashboard settings and the order they go in relative to a deploy are in [docs/RUNBOOK.md](docs/RUNBOOK.md) — the checkpoints of the 2026-09 review, each with its migrations, their audits and their rollbacks. The review ends with Checkpoint C1; what it left undone — the translation and accessibility of every screen, the product features, the contract migrations, the SQL performance and tooling packages — is in [docs/BACKLOG.md](docs/BACKLOG.md). The database goes first: a build of the app needs every `required` migration of its wave in production before it is published.
